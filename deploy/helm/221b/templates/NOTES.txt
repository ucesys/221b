{{- if eq .Values.auth.mode "oidc" }}

People sign in with {{ default "the OIDC provider" .Values.auth.oidc.providerName }} at {{ .Values.auth.oidc.issuer }}; register the callback
{{ if .Values.auth.oidc.redirectURL }}{{ .Values.auth.oidc.redirectURL }}{{ else }}https://<the console's host>/signin/callback{{ end }} with the client {{ .Values.auth.oidc.clientID }}.
{{- else if eq .Values.auth.mode "ldap" }}

People sign in with their directory account ({{ .Values.auth.ldap.url }}). Only members of a group listed under
auth.ldap.roles may sign in; the console reads their groups again every {{ .Values.auth.kubernetes.accessTTL }}.
The search account's password is read from the Secret {{ .Values.auth.ldap.existingSecret }}, key bind-password.
{{- else if eq .Values.auth.mode "local" }}

People sign in with the console's own accounts.
{{- if not (or .Values.auth.local.users .Values.auth.local.existingSecret) }}
No account exists yet: the first visit to the console shows a page that asks for the first administrator's
name and password. That person becomes a SuperAdmin, and the page never shows again.
{{- if or .Values.auth.setupToken .Values.auth.setupTokenSecret }}
It also asks for the setup token you gave (auth.setupToken).
{{- else if $exposed }}

WARNING: the console is reachable from outside the cluster and auth.setupToken is empty, so whoever reaches it
first can create the administrator. Set auth.setupToken before exposing it, or create the first account in values
(auth.local.users) instead.
{{- end }}
{{- end }}
{{- else }}

Sign-in is off (auth.mode=none): anyone who can reach the console sees the cluster and is an administrator.
Set auth.mode=oidc, ldap or local before exposing it.
{{- end }}

No administrators are named (auth.admins, auth.adminGroups): everyone who signs in can only read what Kubernetes lets
them read, and nobody can change the settings or manage connections until one is.
{{- else if or .Values.auth.admins .Values.auth.adminGroups }}

SuperAdmins named in values, who manage connections, settings and users: {{ join ", " (concat .Values.auth.admins .Values.auth.adminGroups) }}.

{{- if .Values.rbac.create }}

Roles: the ClusterRoles 221b-viewer, 221b-super-viewer, 221b-admin and 221b-super-admin are installed, Admin as the
{{ .Values.rbac.roles.admin.template }} definition and SuperAdmin as the {{ .Values.rbac.roles.superAdmin.template }} one. Admin and Viewer are bound to groups, one namespace at

{{- if and (eq .Values.rbac.roles.admin.template "readOnly") (eq .Values.rbac.roles.superAdmin.template "readOnly") }}

{{- if eq .Values.connections.store "secrets" }}

Other clusters are added from the cluster menu by an administrator. Each connection is kept as a Secret
named {{ include "b221.fullname" . }}-cluster-<id> in this namespace, which the console may manage Secrets in:
keep it in a namespace of its own. List them with

Connections to other clusters are kept in memory (connections.store=memory) and lost on restart.

{{- if .Values.secrets.read }}

Secrets are read (secrets.read), so each namespace lists its Secrets by key name and size and the Helm tab
reads release records; a Secret's values never leave the server. Set secrets.read=false to grant no access
to Secrets at all, which also hides the Helm tab.
{{- else }}

Secrets are not read (secrets.read=false): the ClusterRole grants nothing on Secrets, namespaces list no
Secrets and there is no Helm tab, since Helm keeps its release records in Secrets.
{{- end }}
