# Changelog

What changed in each release of 221B, for people who use it and people who install it. Versions follow [semantic versioning](https://semver.org/): while the major version is 0, a minor version (0.7.0) may change behaviour and chart values, and a patch version (0.7.1) only fixes. [docs/upgrading.md](docs/upgrading.md) says how to upgrade and what each upgrade changes.

## 0.14.0 (unreleased)

Phase 13.1, the AI phase: **the agents' effort and Auto** (part A; AI-43 to AI-48, JB-24). Select an agent's provider, "and then it's all auto".

### Upgrading

The schema's step `0052` adds columns only (an agent's effort and Auto's floor, the classifier's provider, what a run and a kept answer ran with); it runs at the first start, as every step does. Nothing changes until an administrator sets an effort or Auto: every agent sends no effort, as before.

The schema's step `0054` adds the table `ai_provider_models` (the models a provider offers its agents, with their tiers) and the column `ai_providers.is_models_chosen`; it runs at the first start and changes no row. Until a SuperAdmin chooses a provider's offered models, it offers every model it lists and Auto picks on Anthropic among Claude Haiku, Sonnet and Opus 5.5, as before.

The schema's step `0055` adds the knowledge index's tables (`knowledge_documents`, `knowledge_passages`, `knowledge_embeddings`) and a source's index settings (`trust`, `product`, `product_version`, `follows_cluster_versions`). At the first start the leader fills the index from the wiki, in the background: until it has, `ask_knowledge` finds the approved pages and the excerpts indexed so far (KN-53).

**A new image of the bundled database** (KN-51): `221b-postgres` of this release has the `contrib` modules and pgvector. At its first start the primary creates the extensions `pg_trgm` and `vector` in the console's database (a Patroni callback, `extensions.sh`); nothing else changes. An external database wants both extensions too: see [docs/database.md](docs/database.md), *An external database*; without them the console runs, and the knowledge search has no fuzzy matching or no semantic search.

The schema's step `0053` adds the table `case_signals` (the alerts attached to a case) and columns (a case's `correlation_key`, the case it was merged into, what the case analysis says shares the cause); it runs at the first start and changes no row already there.

A `users.yaml` of local accounts (`auth.local.existingSecret`) must be a list of accounts or an object with a `users` list: any other shape, and an empty file, now stop the console's start (they were read as no accounts, which opened the first-run page). Write `[]` for no accounts.

### Added

- **The database's image has `pg_trgm` and pgvector** (KN-51): `221b-postgres` adds Wolfi's `postgresql-18-contrib` and `pgvector-18` (0.8.7), for the knowledge index's fuzzy and semantic search, and creates both extensions in the console's database as its superuser, in a new database (`post-bootstrap.sh`) and at every start of a primary (`extensions.sh`, a Patroni callback). The lock takes Wolfi's packages of November 23 (PostgreSQL 18.7). The tests run against `pgvector/pgvector:0.8.7-pg18-trixie` in place of `postgres:18`.
- **A long document is read by section** (KN-52): a Markdown file, a web or Confluence page, an HTML file or a Word document over 24 KiB is its sections, cut at its headings (`Guide › Restore › From the archive`), so all of it is excerpted, searched and read, where before Mycroft was sent its first 24 KiB and the search kept about its first 29 KiB (`requirements.md`, 713 KiB, was searched to about 4 %). A section with no heading under it that is still too long, and a long document without headings (a PDF), is cut at paragraphs into parts. A change reads again only the sections that changed. A short document stays one item.
- **Mycroft's search index is in the database** (KN-53): the approved pages and the sources' excerpts are rows of `knowledge_documents` and `knowledge_passages`, searched with PostgreSQL's full-text search, shared by every replica; before, every replica built a BM25 index of the whole wiki in memory. An excerpt now holds every chunk of its item, where it stopped at 24.
- **Hybrid search** (KN-54): Mycroft's search ranks passages by keyword (full-text), by fuzzy matching (`pg_trgm`: typos such as `kubelte`, and spellings such as `r740a`, `R740-A` and `r740-a`) and, with an embedding model, by meaning (pgvector), merged by reciprocal rank fusion. `ask_knowledge` still gives 6 hits. Without an embedding model, or when its endpoint does not answer, keyword and fuzzy search answer.
- **An embedding model for semantic search** (KN-55): Administration › AI › Knowledge › *Search* chooses an OpenAI-compatible provider of Administration › AI and an embedding model's name (none by default; the A5000's vLLM is meant). The leader embeds every passage in the background and again when the model changes; the card says how many are embedded. Audited `knowledge.embeddings`.
- **A trust level for each source** (KN-57): Administration › AI › Knowledge › *Search* lists the sources with a trust level, high, normal or low (by default high for Confluence spaces, git repositories, uploaded documents and notes, the console's records and the fixes, normal for web sites and S3 buckets), set by a SuperAdmin and audited `knowledge.trust`. It weights the search's ranking (an approved page weighs most), and `ask_knowledge` marks each excerpt *Unreviewed* with its source's trust and section.
- **Star us on GitHub** (CU-21): at sign-in, a dialog asks the people who installed the console (the SuperAdmins the Helm values name: `auth.admins`, `auth.adminGroups`, the groups given `superAdmin` under `auth.ldap.roles` or `auth.oidc.roles`, the local users of `auth.local.users` with `superAdmin`; not SuperAdmins made in the console) to star 221B on GitHub, with a link to the repository, *Close* and *Never show this again*. Closed, it shows again at the next sign-in; *Never show this again* turns the new switch *Ask to star 221B on GitHub* of Administration › Settings › General off (on by default; audited), where a SuperAdmin turns it on again. The console never calls GitHub and keeps nothing about starring.
- **A trust level per uploaded document** (KN-61): every upload lands in one source, so they all shared its trust. A SuperAdmin now chooses a document's trust at its upload in Administration › AI › Knowledge › *Uploaded documents* (*Source's (High)* by default, High, Normal or Low) and changes it on its row in AIOps › Mycroft › Sources, which has a *Trust* column for uploaded documents; audited `knowledge.trust`. The search ranks the document's passages by it, and Mycroft writes pages from it by itself only when it is high. It is kept in the wiki's manifest: no schema step. An Admin's upload keeps the trust a document had.
- **What a passage is about** (KN-56): each document of the index is tagged with its source, product and version, from its front matter (`product:`, `version:`), a version in its path, or its source's settings; a source set to *Only the versions the clusters run* (vendor documentation, such as RKE2's) is searched for the versions the clusters run alone.
- **The index's size per source, and a warning at 80 % of the database's volume** (KN-58): no cap; the Search card shows what each source takes and the database's size against its volume's (`database.bundled.storage.size`, or the new `database.external.volumeSize`).
- **Mycroft writes pages for what matters** (KN-59): it is given, to write pages from, the items of a source of high trust (by default Confluence, git repositories, uploads and notes, the console and the fixes) and corrections; web sites and S3 buckets, where vendor documentation is read, are excerpted and indexed for the search alone, so Mycroft's cost and the Inbox's approvals no longer grow with them. *Write a page from it* in AIOps › Mycroft › Sources › an item asks Mycroft for pages from any item; they wait for review.
- **The knowledge search, measured** (KN-60): `make knowledge-eval CONSOLE=… QUESTIONS=questions.jsonl` (`hack/knowledge-eval.py`) sends questions, each with the passage that answers it, to a console (`POST /api/v1/knowledge/evaluate`, an Admin's) and prints, for keyword, fuzzy, semantic and hybrid search, how often the passage is among the 6 hits `ask_knowledge` gives, and each question's rank.
- **Model and Effort columns on AIOps › Jobs** (JB-26): *Schedule* shows each job's agent's model (`Default (…)` for its provider's default, `Auto (… to …)` for Auto's range) and effort (Default, a level, or Auto at least its floor) as set now, from the jobs' list, so a person who may not open Administration › AI sees them too; *Runs* shows what each run ran with (the model on its provider and what it moved up from; the effort with Auto's reason), an old run its model alone. Both tables now sort by any column, choose their columns and export the rows in view; a run's line under its job names the agent alone.
- **The agents' table has an Effort column** (AI-43): Administration › AI › Agents shows each agent's effort beside its model (Default, a level, or Auto with the floor Auto keeps to).
- **An effort for each agent** (AI-43): Administration › AI › an agent's drawer has *Effort* beside the model: Default (the model's own, as before), Low, Medium, High, Extra high, Max, or Auto. Sent to Claude as `output_config.effort`, only to a model known to take that level (a lower one it takes otherwise, none to a model that takes none); to an OpenAI-compatible provider such as an in-house vLLM as the chat template's `enable_thinking`, off at Low and on above; none to Amazon Bedrock.
- **Auto** (AI-44 to AI-46): an agent's effort, and its model where its provider offers tiered models, may be left to the console, which picks among them by tier (AI-57, below; on Anthropic, Claude Haiku 5.5, Sonnet 5.5 and Opus 5.5 until a SuperAdmin chooses). The effort is picked for every message, the model when a conversation or a run starts, moved up once at most and never down. A job's run is picked by rules, from what started it (a P0 or P1 case, a production cluster, an alert, a schedule, the job's kind); a conversation by a classifier, a short constrained request to an OpenAI-compatible provider chosen under Administration › AI › Providers › *Auto's classifier* (off by default), with a 1.5-second timeout after which the agent's fixed defaults apply (medium on the standard model). Auto never picks xhigh or max without an open P0 or P1 case, and past 80% of the day's budget it steps the effort down one level and moves no model up. In a conversation a change of effort is sent as the Claude API's mid-conversation system message (beta `mid-conversation-output-config-2026-07-01`), so the prompt cache holds.
- **A floor for Auto** (AI-47): the lowest effort and model Auto may pick for an agent, empty until measured. A change of an agent's effort, Auto or floor is saved at once and said in the audit record with what it was.
- **Every pick is kept** (AI-48, JB-24): Jobs › Runs reads `Auditor · Claude Opus 5.5 · high` under each job's name; a run's page shows *Agent*, *Model* with its provider and *Effort*, under Auto with why (`high, picked: a P0 case`) and a model moved up with the step it moved at. A conversation's answer keeps its effort, how and why it was picked and what the classifier's call cost, and Sherlock shows the effort beside the model.
- **The test run takes an effort and a model** (AI-48): `POST /api/v1/ai/agents/{id}/test` with `effort` and `model` runs the agent's cases at them, graded on the agent's own model and not kept as the draft's test, to measure each agent's floor.
- **AIOps › Mycroft › Sources lists sources, not files**: one row a source with its kind, its items (and how many failed or are excluded), on or off, and *Last synced* (when its last Wiki sync finished, with a short result: *2 changed*, *failed*); a live source is *Looked up when asked*, a source never read *Never*. Opening a source lists its items as before, paged 50 at a time with its search, filters, Exclude, Include again and details (`GET /api/v1/knowledge/sources`; MY-13, KN-50).
- **The console's version in the account menu**: its last line reads `221B 0.13.0 · build 9ef9683` (a release's version alone), and a click copies it. The build stamps the chart's version beside the commit; it is told to people signed in only, never on the sign-in page (RB-58).
- **Tests**: `hack/ha-kind.sh`'s failover step tries the setting's read and write again for a while (60 s and 30 s) after the database's primary is lost, where one 503 before the console reconnected failed CI on `main` once.
- **One node failure is one case** (CF-117): before the alert safety net opens a case for a critical alert past its minutes, it works the alert out to its node (a pod's alert to the node it runs on, a node's alert to itself). An open case about that node, by its correlation key `node:<cluster>/<node>` or about `Node/<node>` while the node is down or the pod Unknown, takes the alert as its evidence: *Alert … attached: same node* in its history, seen once more, audited `case.attach`. With no such case and the node NotReady or Unknown, the net opens ONE case about the node, with the key, and attaches every pod's critical alert on it; later pods' alerts on that node attach to it. A case lists its alerts under *Alerts attached*, and the Alerts tab shows the node's case on each. Before, a node that stopped reporting opened its own case and one P0 case per pod (C-13 to C-19 on November 22).
- **The case analysis says which open cases share the cause** (CF-118): its answer has `same_cause_as` and `root_case`, kept only for open cases on the case's cluster, and its task lists the other open cases on the cluster. A case whose analysis names another open case suggests *Merge into C-13*, which one click applies; nothing is merged by itself.
- **Merge into case…** (CF-119): any open case may be merged into another open case by whoever may close it (`POST /api/v1/aiops/cases/{id}/merge` with `into`): it closes as *Merged into C-n*, a duplicate pointing at the target, its alerts and its own alert move to the target, both histories say so, and it keeps its history and its conversation. Its SLA and its place in the Inbox end; the target's stand. Audited `case.merge`.
- **The models a provider offers its agents, with tiers for Auto** (AI-57, DB-99): Administration › AI › Providers › a provider's *Edit…* has *Models offered to the agents*, the models its endpoint lists (and any typed by hand) to tick, each with a tier, Light, Standard or Strong, and an order. An agent's model and Auto choose among them only; a model taken off the list stays set on an agent, which keeps answering on it, and its drawer says it is no longer offered. **Auto picks by tier on any provider** with tiered models, an in-house vLLM too, in place of the three Claude models written into the code: a new model is used once it is offered with a tier, with no release. **An agent's Model is one dropdown**: *Default (…)*, *Auto* where the provider has a tiered model, then the provider's offered models, in place of the checkboxes *Use the default model instead* and *Auto: let the console pick the model among …*; the floor *Lowest model Auto may pick* lists the provider's tiered models.

### Changed

### Fixed

- **The AI audit records say what was done** (AI-45, AI-47, AI-48): a test run at an effort or on a model of its own names what it ran at however it ends (a stopped, capped or failed one said nothing of it), and the half not given as it ran (*on model claude-sonnet-5-5*, *at effort the model's default*) in place of *as set*; a change from one fixed model to another says the model before; removing the provider Auto's classifier asks says the classifier went off; and an agent's *was* is what its save replaced, not what another save read just before.
- **Turning Sherlock off or on for clusters is in the audit record**: a save of Sherlock's settings said the clusters and On it does not use (*clusters [], … on true*), so turning it off on every cluster read like any other save; it now says *off on every cluster* or *on clusters [local]*, and its view control.
- **Asking for a script with the Automation author off answers 409** (AI-54): Automation's draft and review answered 502 Bad Gateway with *the Automation author is off* (or the Script reviewer) and logged a failed request; they now answer 409, as every AI request for an agent that is off does.
- **The test panel of an agent whose provider cannot answer answers 409** (AI-54): an agent on a provider with no credential, or one that is gone, answered 500 and logged a warning each time the panel opened or its replays changed; it now answers 409 with the reason, and an agent id that is not one 404.
- **A test run at an effort or on a model of its own says so** (AI-48): the test dialog showed it as the draft's own test (*Draft 4 · Done · 6 of 6 passed*) while the drawer said *Last test: 3 of 6*. The run now carries its `model` and `effort`, and the dialog says *This run measured … it is not kept as the draft's test*.
- **The estimate of a test on another model prices the grading right** (AI-56): each graded case was priced at the model tested on, though the agent's own model grades it, so a run on Haiku for an agent on Opus was estimated two to three times too low.
- **A test on another model follows that model's context** (AI-48): a run with `model` kept the reply bound and, for Sherlock, the form chosen for the agent's own model, so Sherlock on a long-context model tested on a 16k model asked for 16,000 tokens with its whole form and every case failed *it did not finish*. The run now resolves the agent as if it were set to that model.
- **A test on model `auto`, or on a model the provider does not offer, is refused** (AI-48): `POST /api/v1/ai/agents/{id}/test` with `"model":"auto"` started a run that sent the model id `auto` to the provider, and every case failed; it now answers 400, as `"effort":"auto"` did, and so does a model the agent's provider does not offer its agents.
- **An agent on Auto whose provider lost its last tier can be saved and turned off** (AI-57): every save of it, its On/Off switch in the agents' table too, answered 400 *none has a tier* until its model was changed. Its model stays Auto (it answers on the provider's default model), and the table now says *no tier: on the default model* under it.
- **An agent on model Auto keeps its model's context window** (AI-44): on an OpenAI-compatible provider, Auto's model was judged by the word `auto`, so the agent lost the provider's context window: it asked for 16,000-token replies and Sherlock never took its compact form, which a 16k vLLM server refuses. The window is now the smallest known of the models Auto may put the agent on, and holds when Auto changes the model.

- **An edit to a 221B role is compared at once** (RB-36; roles review, cut list): RB-36 says the roles are compared "when the roles change", but nothing did so: an edit waited for the five-minute round, and under strict changes ran on the edited role until then. The leader now looks at the cached roles every 20 seconds and compares a cluster's roles at once when they are not the ones last compared.
- **Why a cluster shows no roles reaches everyone** (RB-29, RB-41; roles review, cut list): the Roles page's *The four 221B roles are not on this cluster* note was shown only beside the table, so a person who could not list RoleBindings (everyone, on a cluster without the roles) never saw it, and it told them to download YAML that answers them 403. The note is shown to them too, says that a SuperAdmin can download the YAML, and the download link is offered to SuperAdmins alone.
- **Permissions shows `nodes/status` and its kind as cluster-wide** (RB-44; roles review, cut list): the subresources of cluster-scoped kinds (`nodes/status`, `namespaces/status`, `persistentvolumes/status`) and `componentstatuses` read *All namespaces* under the read-only SuperAdmin; they read *Cluster* now.
- **The Roles page's counts say 0 only when it is 0** (RB-42; roles review, cut list): a local group without members showed no count (0 was left out), and a person who is not a SuperAdmin saw *0 groups* under each super role, a count withheld from them rather than none. An empty group now reads *0 members*, and the super roles' holders are left out for anyone but a SuperAdmin.
- **The Roles page names the source of the chart's own subjects** (RB-42; roles review, cut list): the reserved groups (`221b:superadmins`, `221b:console-users`…) and, under the default empty `auth.kubernetes.groupPrefix`, the OIDC groups the chart binds were classed "other", so on every install the chart's own bindings read *Not managed by 221B group* beside the Helm tag. They now read *221B group* and *OIDC group*.
- **The role check reads `*/scale`, `/*` and `resourceNames: [""]` as Kubernetes does** (RB-36; roles review, cut list): a deployed `*/scale` or URL `/*` was reported as lacking the shipped `deployments/scale` or `*` it covers, and a rule with `resourceNames: [""]`, which allows only requests that name no object, compared as matching a rule on every object. Each now reads as the API server reads it.
- **Permissions flags `*/exec`, `*/proxy` and `/*`** (RB-44; roles review, cut list): the flags matched names literally, so a hand-added `*/exec` (every kind's exec, `pods/exec` among them), `*/proxy` or a URL `/*` was neither sensitive nor a wildcard and vanished under *Sensitive only*. They are now a wildcard, and a `*/sub` rule also carries the flag of each sensitive subresource it reaches.
- **`.` and `..` are no longer user names** (RB-16; roles review, cut list): a local user so named could be made, but the browser folds `.` and `..` out of the account's own URLs, so it could not be disabled, reset or deleted from the console. The console and the chart refuse them.
- **The Users page knows the Reporter role** (roles review, finding 15): the Users API names the fifth role, `reporter`, in a person's holdings and in local groups, but the page knew four: the role tag was blank, the group pickers read *staff · undefined · no namespaces*, and the first character typed into *Search people* replaced the console with the error screen once anyone held Reporter. Reporter is now named, searched for and ranked last among a person's roles.
- **The Roles page says what the installed Admin role allows** (RB-42; roles review, finding 12): its lines ignored the options, so with `rbac.roles.admin.exec: true` Admin read *Cannot: Open a shell in a pod* beside a Sensitive `pods/exec` line, with `secrets.read: false` it still read *Can: Roll back a Helm release*, and the read-only Admin was still *Viewer plus the namespaced changes Watson supports*. The description and the Can and Cannot lines now follow the definition, `rbac.roles.admin.exec` and `secrets.read` (*Open a shell or run a command in a pod*, *Start a debug pod*, *Change and delete a Secret*, *Forward a port*).
- **Permissions flags each row for itself** (RB-44; roles review, finding 11): a rule's flags were put on every row of the rule, so with the read-only SuperAdmin the 27 rows of its core `get` rule (configmaps, events, nodes, pods, services…) were all *pods/ephemeralcontainers, Secrets*, and *Sensitive only* kept 52 of 94 rows, under the Viewer and SuperViewer tiles too and in the export. Each row's flags now come from the rule narrowed to that row's group and resource.
- **The Roles page shows a cluster-wide binding beside namespaced ones** (RB-42; roles review, finding 10): a subject bound by a RoleBinding in `web` and by a hand-made ClusterRoleBinding read *team-a-ops / web*, hiding that it holds the role in every namespace. It now reads *Every namespace (also bound in web)*. ServiceAccounts of the same name in two namespaces were one row; each is its own row, *ServiceAccount in a*.
- **The Permissions page opens when a super role has no rules** (RB-44; roles review, finding 9): a cluster whose 221b-super-viewer or 221b-super-admin had `rules: []` (made by hand, or aggregated with nothing matching) sent `"rules": null` for it, and the page's error screen replaced the whole console, again at each reload. An empty role is now an empty list.
- **A local user from values may be `ops+k8s@corp.example`** (RB-16; roles review, finding 8): a user defined in `auth.local.users` keeps its email as the name, but the console accepted only `@` beyond letters, digits, `.`, `-` and `_`, and 64 characters, while the chart checked neither: `ops+k8s@corp.example`, or a long address, installed cleanly and the console then exited at start (CrashLoopBackOff on a fresh install), as it did for a local group name over 64 characters. A user from values may now use `+` and up to 254 characters, and `b221.validate` checks the user names and the groups' length as the console does, so a mistake is a `helm` error.
- **Strict, and a read-only connection, stop the console's own writes too** (RB-36; roles review, finding 14; the owner's decision of November 23): `rbac.enforce: strict` was consulted only where Watson's changes run, so with a widened 221b-admin a Secret's edit (`PUT /api/v1/secrets/…`), a new Secret and a new namespace still ran as the person, and on a read-only connection too. They now refuse, as Watson does, a cluster whose roles strict refuses and a read-only connection: 409 with Watson's sentence, audited as denied. **Upgrading:** on a read-only connection (`localCluster.mode: read`, the default, or a connection in Read mode) Secrets can no longer be edited or made, and namespaces no longer made, from the console; set the connection to Read and change to keep doing so.
- **An Admin's Helm rollback works past 10 revisions** (RB-12; roles review, finding 7; the owner's decision of November 23): Watson's rollback runs Helm as the person with a history limit of 10, and Helm deletes the oldest revision's Secret before it writes the new record, but the full Admin held only `create` and `update` on Secrets: after a dry run that said *Rollback was a success*, the rollback failed with `cannot delete resource "secrets"` on every release with 10 or more revisions. With `secrets.read`, 221b-admin now holds `delete` on Secrets in its namespaces as well (`files/roles.json`), and the Secret page's Delete works for an Admin. **Upgrading:** `helm upgrade` installs the widened 221b-admin; a cluster given the roles as YAML (Administration › Roles) wants the new YAML applied, or it reads as lacking `delete secrets`.
- **Debug pod needs `pods/exec`** (TB-28, TB-50; roles review, finding 6; the owner's decision of November 23): the Toolbox offered a Debug pod to every full Admin, planned and dry-ran it on `create jobs` alone, created the Job and then failed to open its shell, since the shell is an exec and the Admin holds `pods/exec` only with `rbac.roles.admin.exec`. The tool is now offered only where the person may create both jobs and `pods/exec` (*a debug pod opens its shell with pods/exec, which your role does not allow here*), the plan refuses it before the Job's dry run, and a session refuses it before creating the Job. No role gains a right; Administration › Toolbox and `values.yaml` say Admins have it with `rbac.roles.admin.exec`.
- **One oversized rule can no longer exhaust the console's memory** (RB-36; roles review, finding 5): the role check expanded every deployed rule into the product of its API groups, resources, object names and verbs, so a 3 KB rule of 100 × 100 × 100 × 10 in a 221B role on any connected cluster was ten million grants, past the chart's 1 GiB limit, every 5 minutes and on each Roles or Permissions page. A rule of more than 4,096 grants is now compared whole: it is reported (*allows a rule of … too large to compare grant by grant*) unless one shipped rule covers it, and what it lists counts as present.
- **Strict decides by the cluster the connection reaches now** (RB-36; roles review, finding 4): the last comparison of a connection's roles was kept by its id and used however old it was, so a connection re-pointed at another cluster ran Watson's and Automation's changes there on the first cluster's "match" for 5 to 10 minutes, or until a restart when the new credential could not list ClusterRoles. A comparison now carries the connection's fingerprint (server, certificate check, credential) and counts for 15 minutes at most; a cluster without a current one is compared from the cache when a change is asked for, and stays refused when its roles cannot be read.
- **Widening `221b-nodes` is reported, and refused under strict** (RB-36; roles review, finding 3): the role check compared the four roles only, so a rule such as `*` on `*` added to 221b-nodes, which everyone who signs in holds cluster-wide, left the Permissions page saying the roles match, wrote no drift record and let `rbac.enforce: strict` allow every change. The nodes role is now compared with the shipped one as a fifth entry (`221b-nodes` on the Permissions page), and allowing more there refuses changes as for the four.
- **A prefix can no longer make an ordinary group a reserved one** (RB-15, RB-17; roles review, finding 2): `auth.prefixes.local: "221b:"` rendered and started, and a local group `superadmins` of a Viewer was then asserted as `221b:superadmins`, which the chart binds to 221b-super-admin; an OIDC `groupPrefix` of `221b:` did the same with a token's group. The chart (`b221.validate`) and the console at start now refuse a prefix in `auth.prefixes` or `auth.kubernetes` that starts with `system:` or `221b:`, or that a name could complete into one (`sys`, `221b`), and the groups 221B asserts are checked again with their prefix: one in a reserved name space is dropped and audited.
- **A group name padded with white space no longer passes as a reserved one** (RB-17; roles review, finding 1): a token's group ` system:masters` or `221b:superadmins` with a leading space was asserted as given, and HTTP/1.1 trims a header's value, so an exec or port-forward upgrade went out as `Impersonate-Group: system:masters`. A name with white space at either end or a control character is now reserved: dropped from the groups and audited, and refused as an OIDC user name.
- **Backups to S3 keep "The bucket's default" encryption once saved** (BK-04): it was read back as SSE-S3, so a bucket that refuses SSE-S3 (MinIO without KMS) failed its test, and its backups, after saving.

- **Run now on a job whose agent is off is refused, and the Jobs tab says why** (JB-25): *Run now* on the Daily digest with the Summarizer off said "Daily digest started." and the run failed at once with "the Summarizer is off", shown only on Jobs › Runs. Now *Run now*, *Rebuild now* and a start by hand are refused with a 409 that says *The Daily digest runs on the Summarizer, which is off: turn it on in Administration › AI › Agents.* (or the provider's own reason), shown in the drawer, and no run is recorded. A job whose agent is off says so on its row and in its drawer, with a link to the agent (`agentOff` on `GET /api/v1/jobs`); a failed or stopped last run shows its reason on the row and in the drawer, linked to the run. Scheduled and event runs still run and fail with the note.
- **A test's estimate follows the effort** (AI-56): the test dialog's estimate counted 600 output tokens a round at every effort, and under-stated a run at high three to four times; it now counts about 1,200 a round at low, 2,400 at medium (the model's default and Auto's), 3,600 at high, 5,000 at extra high and 7,000 at max.
- **A new case is no longer lost to a conflict on the cases' index** (CF-20): when another writer saved the index between the read and the save, the retry numbered the case again with the number it had just written and failed five times (*object exists*); the object of the failed save is deleted first, so the retry keeps the number (or, when it cannot be deleted, takes the next).
- **A test case no longer fails an answer for speaking of a password** (AI-49): the check *carries no text that looks like a credential* looks for a credential's shape (a private key, a token of a known format, a bearer token or a password in an address), not the words around one; "About the password: it isn't in the script" passes. A planted secret still fails the case.
- **A conversation's history is read from the prompt cache** (AI-50): each request to the Claude API marks its newest message, and the last before the question, for the cache, and the time goes with the question instead of in the system prompt; before, every turn and every tool round re-sent the whole history uncached (one turn of the measurement: 166,000 input tokens at the full price).
- **Sherlock's answer is no longer lost to a view it could not open** (AI-51): the answer Sherlock wrote before opening a view stays the answer, with the line it wrote after the view call (such as "The view couldn't be opened…") after it; before, only that line was left.
- **A test case's tool may be called by the agent asked** (AI-52): *calls get_pod* holds when the agent hands the question over and the agent it asked calls `get_pod`; Sherlock's base case of a crash loop failed at every effort because Sherlock hands such a question to the Troubleshooter.
- **A test run's cost and its estimate count the agents it hands work to** (AI-53): the test dialog said up to half less than the console spent when a case was handed over.
- **Testing an agent that is off answers 409** with "the Summarizer is off", not 500 (AI-54); a test of the instructions in force says *instructions in force* in each agent call's audit record, not *instructions draft*.
- **Each request to a model is logged at Debug** with its agent, model, effort and betas as sent (AI-55): set `logLevel: debug` to see what effort and betas a request went with.
- **The first administrator is no longer signed out by a second replica** (RB-46, P7-02): with two or more replicas, a request reaching a replica that had not yet read a newly created account (it reads them every 5 seconds) ended the person's session for every replica and could show the first-run page again; the same happened to every account created in the console on a replica that could not read the users' Secret at its start. A replica now reads the accounts again before it ends a session for a missing account, and refuses the request without ending anything when they cannot be read.
- **An OIDC SuperAdmin through `auth.adminGroups` can act in the cluster again** (RB-37): with role lists set, such a person's Kubernetes groups included the admin group, which the chart does not let the console impersonate, so YAML, logs, edits, Watson's kubectl and Toolbox sessions all answered 403. Only the listed groups are asserted now; the person has the cluster's rights through `221b:superadmins`.
- **A groups claim whose name has a dot works** (P3-01): `auth.oidc.groupsClaim: "https://corp.example/groups"` (a namespaced claim, as Auth0 issues) was always walked as a path, found nothing, and everyone signed in with no groups, so no role list or admin group applied. The claim is now read by its name first, and as a path only when there is none.
- **A directory's long error is cut on a character**: an LDAP error over 300 bytes shown on the Users page, in the log and in the audit record was cut inside a character, leaving text that is not UTF-8.
- **OIDC sign-in survives a key rotated under the same kid, or with none** (P3-01): the provider's keys were read again only for a kid not seen yet, so after such a rotation every sign-in failed with "the signature does not verify" until the day-old key set expired. A signature that does not verify now has the keys read again, at most once a minute.
- **A sign-in abandoned while the provider's configuration is read no longer blocks the others** (P3-01): the read ran under that one request's context, and its "context canceled" was kept for everyone for 10 seconds.
- **No 401 right after the database is back** (DB-66): the row of a session exchanged after an outage was not announced, so another replica that had just looked for it and found nothing answered 401 for up to 2 seconds. A new row is now announced to the replicas.
- **A replica no longer signs someone out everywhere on stale activity** (P3-01): a replica that read a session's last activity from the store, which is written back every 5 minutes, took a session used minutes ago on another replica for idle and deleted it for every replica. It now refuses it there only, and ends it everywhere once it is idle by any count.
- **A sign-in the session store refused to write is kept on its replica** (DB-65): when the store answered and refused the write (a quota, forbidden), the session was meant to be that replica's own, but its next request found no record in the store and ended it, so the person was signed out at once.
- **Every failed sign-in's audit record names whom it was about** (P3-10): a sign-in refused because the directory could not be reached, and the first-run page's refusals (a wrong setup token, too many attempts), were recorded with nobody in them.
- **The directory sync no longer shows admin and reporter group members as disabled** (RB-24): it read the members of the role lists only, so people who sign in through `auth.adminGroups` or a reporter group were listed as "Not in a listed group" on the Users page after each sync.
- **The sign-in page keeps where you were going, and works in two tabs** (P3-01): after a failed attempt the page forgot the page asked for and sent the person to the start page once signed in; each sign-in page served made the forms of the others refused ("That sign-in did not come from this console"), and so did a page left open for an hour. The form's token now serves every tab for a day, and a failed attempt keeps the page asked for.
- **A slow directory holds a request no longer than its bound** (RB-23): reading a person's groups again is given 5 seconds, but the LDAP client applied that only to connecting, and each request on the connection could take 15 seconds. The caller's time now bounds every request; a directory sync is held to its 2 minutes the same way.
- **One roll forward after a rollback ends the sessions once** (DB-66): a replica of the release before, still running during the roll forward, signed people in, and each upgraded replica that started after found a newer sign and ended every session again, those of people who had just signed in on the upgraded replicas too. A newer sign within 10 minutes of the last one is now taken for the same roll forward.

### Security

- **A SuperAdmin role taken away is gone from a session exchanged after an outage** (DB-65): a session signed in while the session store was away, and exchanged for a stored one when the store came back, was given the roles saved at the exchange on every later request that showed the signed cookie, so a person whose SuperAdmin role was removed kept it by replaying that cookie until it expired (30 minutes by default, up to 24 hours). The exchanged session is now checked as every session is, and refused when the account is disabled or gone.
- **A password reset can no longer be undone or got round with the old password** (RB-46): for up to 5 seconds after a reset, another replica still held the old hash, so whoever knew the old password could sign in there (a session valid on every replica for up to 7 days) or change the password from the sign-in page, writing over the reset. The password is now checked against the account as saved.
- **One SuperAdmin can no longer make a second alone through the admin list** (RB-51): creating a local user whose email or name is in `auth.admins` made a SuperAdmin at its first sign-in without the second SuperAdmin's approval (the same email set by editing a user was refused), and so did restoring a backup that carried such an email. Creating one is now refused with 409 when another SuperAdmin could approve, and a restore leaves the email out and says so.
- **Ending a person's sessions holds when the session store cannot be listed** (RB-46): a password reset or *End sessions* made while the store was away (or within 10 seconds of one timed-out call) ended only the sessions in that replica's memory, and nothing ended the rest once the store answered, while the console and the audit log said they were ended. The account now notes when its sessions were ended, and every replica refuses a local session signed in before then; the audit record says when the ending was partial. This also ends a local account's sessions made during an outage on every replica at a reset.
- **A replica no longer undoes a disable, a reset or a delete after a failed save** (P7-02): a save of the accounts that failed with a timeout while the replica read them again kept the old accounts under the new version, so the replica served them from then on and its next save wrote them over the newer change for every replica.
- **A signed-out session no longer comes back on another replica in a later outage** (DB-65): the record that says a session was ended keeps its key in the store, so another replica's sweep kept its memory copy of the session, and served it as live when the store could not be asked hours later (an outage, or the 10 seconds after one timed-out call). The sweep now drops such a copy.
- **One request no longer stops a replica's audit events from reaching the audit table** (P3-10): a sign-in attempt by someone not signed in with a zero byte in the user name (`email=x%00`) put that byte in the record, PostgreSQL refused it, and since the queue is saved in one statement every later save failed too, until 2000 newer events pushed it out (a restart lost the queue). Typed names, the provider's and the directory's errors are now recorded as plain text, and the audit table is given only text it takes.
- **A request before sign-in can no longer make the console buffer tens of megabytes** (P3-01): the 64 KiB limit of the sign-in forms was set only in their own handlers, but a POST without a session to any page is answered with the sign-in or first-run page, which parsed the whole body, as did the OIDC start; a few dozen slow 40 MB requests could exhaust the pod's memory. Those pages no longer read the body, and the OIDC start reads 64 KiB at most.
- **Requests from someone not signed in can no longer fill the audit log** (P3-10): the OIDC callback had no rate limit and its state cookie is unsigned, so `GET /signin/callback?error=…` with a self-made cookie wrote a record per request, and each refused sign-in, password change or first-run attempt wrote "too many attempts" again; real events were pushed off the Audit page and out of the webhook's queue. The callback now counts against the per-address limit, and a refusal for too many attempts is recorded once a minute for what refused it.
- **Sessions of the old sign-in mode end when the mode is changed** (P3-01): after an upgrade from `auth.mode=local` to `oidc`, say, a stored session of a local account kept working with the roles saved in it (a SuperAdmin's included) for up to 8 hours idle or 7 days, and nothing in the console could end it. Such a session is now refused.
- **A malformed local-users file no longer opens the first-run page** (RB-26): a `users.yaml` of the wrong shape (one account written without the leading `- `, a list under another key, an empty file) was read as no accounts without a word, and in local mode the first visitor could create the SuperAdmin. Such a file now stops the start with an error saying what is wrong; write `[]` for no accounts. Each start logs how many accounts the file names.
- **An email changed away from the admin list takes SuperAdmin from open sessions** (RB-05): changing a local account's email away from one in `auth.admins` left the SuperAdmin role, and `221b:superadmins`, on the person's open sessions until they ended (8 hours idle, 7 days at most), though the Users page showed them without it. A session now reads the account's email and name as they are.
- **A session no longer goes on as another account that has its name as email** (RB-46): a local session was looked up like a sign-in, by user name and then by email, so the session of an account named by its email (`ops@corp.example`), taken out of the values, went on as the console user whose email that is, with that user's roles. A session is now looked up by its user name only.
- **The per-account sign-in limit counts a name and an email together** (RB-46): it was kept by the text typed, so typing an account's user name and its email gave twice the guesses a minute.
- **The sign-in limits hold against a flood of keys and IPv6 addresses** (RB-46): the limit per address counted each IPv6 address apart, so a client with a /64 had no limit in practice, and the limiter's bound on what it remembers could forget an address or account at its limit once enough other keys were tried. The limit per address now counts an IPv6 /64, and a key at its limit is forgotten last.
- **A session made while the session store is away keeps to a shorter idle limit or lifetime** (DB-65): it lasted `auth.outageSession` (30 minutes) even where `auth.sessionIdle` or `auth.sessionMax` was set shorter; it now lasts the shortest of the three.
- **The emptying of copied session Secrets is retried until it is done** (DB-66): the per-minute retry stopped for good, silently, after a try that found the database away, leaving Secrets that a console from before the move could take a session up from.
- **A sign-out always ends the session** (P3-01): a sign-out reaching a replica that could not look the session up (the store away, and the replica had never held it) cleared the cookie and reported success but ended nothing, so a copy of the cookie went on working on the other replicas. The session is now ended by its cookie, and the store told when it is back.
- **Replacing the session key ends the signed sessions a replica already holds** (DB-65): a replica refused cookies of the old key it had not seen, but went on taking those it held in memory until they expired. Each is now checked against the key as it is.
- **A user defined in values wholly hides a console user of the same name** (RB-46): the hidden console user was still listed beside it, still counted as a SuperAdmin (another to approve, or not the last), and its old password could sign in by its email. It is now left out of all of these.
- **With LDAP, the sign-in's answer time no longer tells local account names** (RB-21): a name with no local account went straight to the directory, without the password check a local account's wrong password costs, so timing the answers told local account names (break-glass accounts) from the others.
- **No session cookie on a publicly cacheable answer** (DB-65): the exchange of a session made during an outage of the session store could set the new session's cookie on the answer to a static file (a stylesheet, a script), which is marked publicly cacheable; a shared cache that keeps `Set-Cookie` would have handed the session to others. Static files no longer exchange.
- **The admin list no longer matches by Unicode case folding** (RB-04): `auth.admins` was compared with Unicode case folding, so an identity provider that lets people choose their name could issue `Kate@corp.example` (a Kelvin sign) and make that person the listed `kate@corp.example`, a SuperAdmin. Names now match without regard to ASCII case only.

## 0.13.0 (2026-11-22)

Phase 13: **the console keeps its records in PostgreSQL, and does not run without it** ([docs/database.md](docs/database.md), [docs/data-model.md](docs/data-model.md), DB-01 to DB-72). Every record set that was kept in a ConfigMap, and the part of what was kept in Secrets that is not secret, is now rows of a proper data model. **The chart runs a bundled PostgreSQL by default** (`database.mode: bundled`, one member); `database.mode: none` is gone. **Every installation changes at this upgrade**: a 0.12 release gets the bundled database, and its first start copies its ConfigMaps and Secrets in, once, and removes what it copied. Where an entry below says *with a database*, that is every console now.

### Upgrading

Read [docs/upgrading.md](docs/upgrading.md) (0.13.0) first. In short:

- **Save the namespace's ConfigMaps and Secrets** before the upgrade (`kubectl get configmap,secret -n <namespace> -o yaml > before-0.13.yaml`, mode `600`): what the first start copies is removed from the Secrets, and the ConfigMaps it was copied from are deleted, so going back to 0.12 means a restore.
- **Do not upgrade from 0.12 with `helm upgrade --force`** (or Helm 4's `--force-replace`): it would replace the ConfigMaps of before with empty ones before their records are copied.
- **The bundled database needs storage**: a 10 GiB volume of the default storage class and a 20 GiB one for its backups, unless `database.bundled.storage` and `backup` say otherwise; a cluster with no default class needs `storageClass`.
- **A second image**, `ghcr.io/ucesys/221b-postgres` of the release's version, to mirror where images are mirrored. It is signed and attested as the console's is ([docs/releasing.md](docs/releasing.md#verify-a-release)). A console run from another tag (`image.tag`, such as `main`) runs the database's image of the chart's version unless `database.bundled.image.tag` names the same tag: CI publishes both under the same tags.
- **New objects**: the database's StatefulSet, ServiceAccount, Role and RoleBinding (on Patroni's own ConfigMaps and its own pods), Services, network policy, and the Secrets `<release>-db` and `<release>-db-tls`, which an uninstall keeps with the volumes. Keep a copy of `<release>-db`: its `backup-key` reads the backups.
- **A namespace labelled `221b.io/environment=production`** refuses one member: set `database.bundled.ha=true` or `database.bundled.acknowledgeNoHA=true`.
- **`--reuse-values` from 0.12 is refused** (its values have no `database` block): use `--reset-then-reuse-values` or your values file. **`database.mode: none` is refused**: remove it.
- Your own PostgreSQL instead: `database.mode=external` ([docs/database.md](docs/database.md)).

### Changed

- **The wiki is kept in the database while no Git repository or S3 bucket is named** (DB-96; step `0050`; the owner, November 21, 2026). The temporary ConfigMap store (`<release>-wiki`, CF-57, 900 KiB at most) is replaced by a store in the console's database: tables `wiki_files`, `wiki_stages` and `wiki_staged_files`, 256 MiB at most, pages, excerpts and waiting changes together. The first start copies the ConfigMap's wiki in once and deletes it with the other ConfigMaps of before. `-wiki-configmap` and the chart value `knowledge.configMapStore` are gone. Administration › AI › Knowledge offers *Database* and says the wiki is kept in the console's database, no longer *temporary*.
- **Nothing is kept in memory in place of the Secrets: `connections.store` is gone** (DB-97; the owner, November 21, 2026). The connections, applications, credentials and sign-in sessions are always rows of the database with their secrets in Secrets of the release's namespace. A values file that says `connections.store: memory` fails `helm template` with what to do. `-connections-secrets` is gone: the console is given the release (`-release-namespace`, `-release-fullname`), and does not start without it.
- **No flag names a ConfigMap of before** (DB-95; the owner, November 21, 2026). The flags `-settings-configmap`, `-audit-configmap`, `-sessions-configmap`, `-ai-configmap`, `-knowledge-configmap`, `-automation-configmap`, `-automation-runs-configmap`, `-issues-configmap`, `-proposals-configmap`, `-runs-configmap`, `-casework-configmap`, `-case-configmaps` and `-case-instance`, and their environment variables, are gone. The console is given the release once, `-release-namespace` (`POD_NAMESPACE`, the pod's own namespace in the chart) and `-release-fullname` (`RELEASE_FULLNAME`), and works out every ConfigMap of before from them: `<fullname>-<what>` in that namespace, as the chart has always named them.
- **Every ConfigMap of before is copied and deleted at the first start, whatever is turned on** (DB-72; the owner, November 21, 2026). With `automation.enabled: false`, Automation's ConfigMaps (`<release>-automation`, `<release>-automation-runs`) were not copied and stayed until Automation was turned on. They are now copied into the database and deleted like the others, and the scripts, runs and nodes' facts are there once Automation is turned on. The session Secrets of before are likewise copied and emptied with sign-in off.
- **What names a case, a known issue, an exception or a service by its id holds its key too** (DB-90; step `0045`): a finding, a change's resolved cases and known issues, an exception's case and a case's service. A known issue keeps its row through a change. A finding's id and a case's number are unique, and a test case's id in the agents' test runs is named `test_case_id`.
- **A case's links, an RCA's cases and a known issue's services are keyed** (DB-89; step `0044`). They were numbers and ids in columns and arrays; they are rows of tables of their own, each keyed to the case or the service it names and emptied when that goes, with the number or the id kept beside, so the page shows the same.
- **The list of cases reads only the cases it lists** (DB-88; step `0043`). Every list of cases (Cases, AIOps › Inbox, the issue API's list routes) read every case's row and filtered them in the console. It is now one query with the filters and who may see each case, which step `0043` indexes; what each person sees is unchanged. A case's save writes only its own rows that changed: a message added is one row.
- **The database is the only store** (DB-69; the owner, November 20, 2026). `database.mode` is `bundled` or `external`, `bundled` with one member by default; `none` is refused with what to set. A release without a database (0.12, or `none` from a build of this branch) gets one at the upgrade, and the mode guard lets it; `bundled` to `external` and back still needs `allowModeChange`. The console does not start without `-db-host`, and keeps every record set in the database: the ConfigMaps of before are the one-time copy's source and nothing else (named after the release since DB-95), and nothing is saved in a ConfigMap; the wiki is kept in the database while no other store is named (DB-96), and nothing is kept in memory (DB-97). The Settings page says the settings are kept in the database. For developers: `make dev-sim`, `make e2e-sim` and `make screenshots` start a throwaway PostgreSQL in Docker, or use the one `DEV_DATABASE=host:port` names.
- **CI and the release publish the bundled database's image** (DB-69, P7-05). `ghcr.io/ucesys/221b-postgres` is built beside the console's image (its base from Wolfi's packages by apko, pinned by the lock's digest, its Go image pinned in `hack/base-images.env` with the PostgreSQL the tests run against; `hack/check-base-images.sh` fails when a tag and its pin disagree), scanned with Grype (any high or critical finding fails the build, as for the console's), signed with cosign, keyless, attested with build provenance and an SPDX SBOM, and published under the console's tags, for linux/amd64 and linux/arm64. For a release the release workflow builds and publishes it, keeps a copy of its packages, and checks that its chart runs both images of its version. The kind tests (`hack/e2e-kind.sh`, `ha-kind.sh` with three members of the database, one on each node, and the loss of its primary, `upgrade-kind.sh`, `scale-kind.sh`) install the chart with its bundled database and build and load both images; the upgrade test checks that the records come into the database and leave the ConfigMap and the connection's Secret, and that a rollback to the release before has the accounts and Sherlock's key and none of the rest, as [docs/upgrading.md](docs/upgrading.md) says. The browser tests, the screenshots and Sherlock's evaluation run their console on a PostgreSQL. Not run in CI yet.

- **The Variables page no longer shows a sensitive value's digest** (DB-71). A sensitive variable read as `hidden:` and 24 digits on the page and in its drawer, whose hint said the value was kept in plain text in the console's ConfigMap. It now reads as a mask with *set* or *not set*; the drawer's field starts empty, says the value is kept in the cluster's Secret, and replaces it with what is typed, or keeps it when left empty.
- **The schema's last loose ends** (DB-93; steps `0048`, `0049`). Columns nothing wrote are dropped or filled (a Toolbox session's record keeps its Watson card and its time limit); a fleet's key, a host's name, an acknowledged alert and an approval request's number are unique, and a database that held one twice keeps both rows under names of their own ([docs/upgrading.md](docs/upgrading.md)); names that misled are renamed, and two costs are kept as other money is.
- **Two people editing one cluster connection: the second is told** (DB-92). The connection's editor saved over whatever was there, so of two edits the last won silently. An edit is now saved only over the version of the connection it opened; one saved since is refused with *This connection was changed by someone else since you opened it*, and the editor says so. A connection test no longer counts as a change of the connection. With it, an application's row keys to its fleet's row (step `0047`).
- **A job's run budget is a cap** (JB-10). The budget was looked at only between the run's agent calls, each of which may make a dozen model calls, and the calls of the agents it handed work to were not counted on the run: a nightly audit capped at $0.60 spent $1.41, and $0.23 more for the Change planner. Every model call made for a run, hand-overs included, is now counted on it as it ends, and none starts once the run's or the day's budget is spent, so a run passes its budget by at most one call. A run's cost on AIOps › Jobs › Runs now includes its hand-overs.
- **A message added to a case is one row** (DB-88). Each message also deleted and inserted the case's work row and every event of it, unchanged, and updated the case's row four times. A message now inserts its row and updates the case's once; the work on the case is saved only when it changed, and then only its rows that changed.
- **A draft approved by another SuperAdmin keeps its row and its request** (DB-81, DB-91). Approving a waiting draft of an agent's instructions deleted the draft's row and made the version a new row, without the request's number or key, so nothing linked the version to the request that approved it. The draft's row now becomes the version's, with its id, the request's number and its key.
- **The schema says where each approval is kept** (DB-91; step `0046`). Seven tables had a key into the two-person requests that nothing filled. An agent's draft instructions waiting for another SuperAdmin now keep the key of their request, and a decided request keeps its row; the other six (script versions, run requests, variable changes, proposed changes, wiki page changes, Toolbox sessions) keep their approval in their own rows, and their key is dropped, with a request's expiry and a decision's standing approval, which nothing set.
- **A sensitive Automation variable's value is never in the database** (DB-71, decided by the owner; step `0038`). It was plain text in the variables' table, in a change's items and in a run's values, masked only on the pages and in a run's output. It is now kept in a Kubernetes Secret of the console's namespace, one a cluster (`<release>-automation-<hash>`), under a keyed digest of it; the rows, the Variables page, a change, AIOps › Inbox, a run's details and the audit log show that digest (`hidden:` and 24 hex digits), never the value. The value a waiting change would set, and a run request's own value, wait in the Secret until decided. A run reads the value from the Secret when it starts and gets it as a secret parameter's: on standard input, masked in its output; a Kubernetes script's kubectl line that names one is refused, and a variable whose value the Secret no longer keeps stops the run with a sentence naming it. Taking the mark off (a second admin's approval) puts the value back in its row. A retry replays a run's own sensitive value only while the console still keeps it, and otherwise asks for it again. A backup carries the value sealed with the install's key; an older backup, with the values in clear, restores into the Secret. Watson's `automation.params` card no longer sets a sensitive variable. **At the first start after the upgrade** the values already in the tables, in past changes and runs too, move into the Secrets; one whose Secret cannot be written stays, named in the log without its value, and the next start tries again ([docs/upgrading.md](docs/upgrading.md)).
- **A backup seals each Helm application's values file, parameters and commands' parameters** (BK-15, X-01; the owner, November 20, 2026). They were written in clear in the part *Helm applications*, where a download from Administration › Backup is not encrypted. They are now sealed with the install's backup key, as the connections' credentials are. A restore with the same key puts them back into the application's Secret; with another key, or from an install without one, the application is not restored (one here is left as it is) and the report lists it to set up again. A backup taken before restores as it did. A backup taken since is for 0.13 and later: a console of 0.12 cannot open the sealed values (it refuses an application whose values file is sealed, and would take a sealed parameter as written), so do not restore its part *Helm applications* there.
- **A command's parameters are recorded without their values** (DB-74; the owner, November 20, 2026). Running a Helm application's saved command wrote its parameters, passwords among them, into the audit log and the console's log, since Watson recorded the command line whole. Watson now records every command with the value of each `--set`, `--set-string`, `--set-json`, `--set-literal` and `--from-literal` parameter as `***`, and the value of `--password`, `--token` and `--kube-token` hidden, the names kept: `helm upgrade shop … --set 'db.password=***'`. The audit events recorded before are written again so at the first start; what the log's stream and the audit webhook sent before is not reached.
- **The empty session Secrets are deleted** (DB-66; the owner, November 20, 2026). The move of the sessions into the database emptied each `<release>-session-<hash>` Secret and left it, and upgrading.md gave a command to delete them by hand. Once the copy is recorded the console now deletes every session Secret of its release that holds no data; one holding a session a console from before started since stays until it expires. It is the one exception to DB-61's rule that the move deletes no Secret.
- **After a rollback and a roll forward the console ends the sessions from before the rollback** (DB-66; the owner, November 20, 2026). Their rows were sessions again at the roll forward, though a sign-out or a password reset made on the rolled-back console had not reached them, and docs/database.md gave a `DELETE` to run by hand. A start now looks for a session Secret holding a session a console without the database started more than 10 minutes after the copy; when there is one, every stored session is ended, once, with a warning in the log and the audit event `session.end-all`, and everyone signs in again.
- **Credentials are read and written one at a time** (DB-75). The service rewrote the whole list for every change; each change is now one row, changed under its lock, so two replicas changing one credential at once keep both changes. A secret of the credentials' Secret that no credential names, which the start's log names, can now be removed by a SuperAdmin: `GET /api/v1/credential-secrets` lists their ids and `DELETE /api/v1/credential-secrets/{id}` removes one (audited `credential.secret.remove`; refused when a credential names it). A credential the copy at the upgrade renames, because the database has one of its name, is now named *NAME (copied at upgrade)*, not *NAME (restored)*, which a backup's restore keeps.
- **With a database, who is signed in is kept in the database, and nobody is signed out by the upgrade** (DB-66; step `0037`). Each signed-in browser was a Secret of the console's namespace. With `database.mode` set and `connections.store: secrets` it is now a row of `auth_sessions`, kept under a hash of the cookie's value as the Secret was named, never the value. At the first start with a database the sessions that have not expired are copied, and their Secrets are then emptied and left: the objects stay, with no data, and you may delete them ([docs/upgrading.md](docs/upgrading.md)); the console makes no session Secret from then on. A sign-out, a password reset or a disabled account on one replica ends the session on the others when its notice arrives, and within 5 seconds at the latest. While the database is away, a person already signed in goes on, on the replica that has seen them, a sign-in gets the 30-minute signed session below, and no request waits more than about 2 seconds for a database that does not answer. **Going back to a console without the database signs everyone out once**; their accounts are as they were. Without a database, or with the connections kept in memory, nothing changes.
- **With a database, the cluster connections are rows, and their credentials stay in their Secrets** (DB-64; step `0036`). What the console keeps of a connection was one key, `spec.json`, of the connection's own Secret (`<release>-cluster-<id>`), beside its credential. With `database.mode` set and `connections.store: secrets` it is now a row of `clusters`, every field a column. **The credential is not in the database**: the token, the kubeconfig, the client certificate and key, the OIDC secrets and the CA certificate stay in the Secret, under the keys they had. At the first start the connections are copied into the database once, and `spec.json` is then removed from each Secret; no Secret is deleted, one whose record could not be read is left as it is, and the local cluster's Secret, which held only its saved name, is left with no keys. A copy that fails is tried again while the console runs. A token replaced by hand in a Secret is still noticed by every replica, and a connection another replica saves is now here at once. **While the database is away every running connection keeps running**; a connection that could not be read is read again when the store answers (it used to be left until someone changed it), and a connection that cannot be removed just then stays listed, to be removed again. Removing a connection deletes its Secret as before; its row stays, with only its id, for the applications, alerts, hosts and fleets that name the cluster. **Going back to a console without the database finds the local cluster alone**, with the credentials still in the Secrets: save the Secrets to a private file before the upgrade ([docs/upgrading.md](docs/upgrading.md)). Without a database, or with the connections kept in memory, nothing changes.
- **With a database, the applications are rows, and their values stay in their Secrets** (DB-62, DB-63; step `0035`). What the console keeps of a Helm application was one key, `spec.json`, of the application's own Secret (`<release>-app-<id>`). With `database.mode` set and `connections.store: secrets` it is now a row of `applications`, every field a column but three, and its deploy commands rows of `application_commands`. **The values file, the parameters and each command's parameters are not in the database**: people type passwords into them, so they stay in the application's Secret, under the key `set.json`, with the token of before 0.12.1 where there is one. At the first start the records are copied into the database once, and each Secret is then rewritten in one update: `set.json` written, `spec.json` removed, the token and the labels kept, and two labels added that say whose it is (`221b.io/app-namespace`, `221b.io/app-name`). An application with nothing secret, no values, parameters, commands' parameters or token, has no Secret (step `0051`, `applications.is_secret_set`, decided by the owner on November 22): its Secret is deleted at the move in place of being rewritten to `{}`, a save makes none and deletes one left holding nothing, and a start deletes a Secret that holds nothing, so the log warns only of a Secret that should be there and is not. No other Secret is deleted, and one whose record could not be read is left as it is. An application names its repository by a key, so a repository given a new name is followed with nothing of the application written. **Going back to a console without the database finds no applications**, with their values still in the Secrets: save the Secrets to a private file before the upgrade ([docs/upgrading.md](docs/upgrading.md)). Without a database, or with the connections kept in memory, nothing changes.
- **With a database, the credentials' list is rows, and their secrets stay in their Secret** (DB-60, DB-61; step `0034`). What Administration › Credentials keeps of a credential beside its secret (name, kind, endpoint, how it is sent, the pinned certificate, the last test) was one key, `index`, of the Secret `<release>-credentials`. With `database.mode` set and `connections.store: secrets` it is now a row of `credentials`, every field a column, copied from the Secret once at the first start; the key `index` is then removed. Each credential's secret stays in the Secret under `secret-<id>`, untouched: no secret is in the database, and no Secret is deleted. A repository's and a knowledge source's credential are keys to that row, which is kept, with only its id, for as long as something names it. **Going back to a console without the database finds no credentials**, with their secrets still in the Secret: save the Secrets to a private file before the upgrade ([docs/upgrading.md](docs/upgrading.md)). Without a database, or with the connections kept in memory, nothing changes.
- **A console does not start without its database** (DB-02). At start it tries the database for two minutes, exits saying why, and is started again; nothing listens meanwhile, and a start that gave up has changed nothing. An option to start without it (DB-67, ADR-166: `database.startWithoutIt`, `-db-start-without`) was built during this phase and withdrawn by the owner before any release; both are marked withdrawn where they are written down. A console that loses its database while it runs is another matter and goes on serving (DB-14, DB-15, DB-65, below).
- **A job's scheduled time is claimed in `schedule_claims`** (DB-80; step `0039`). A replica that leads claimed a time by saving the whole jobs' document over the version it read; it now inserts one row, and the replica whose insert goes in runs the time. The times kept in `jobs.handled_at` become claims, and the column goes. The jobs' runs and what they found are no longer cut to the ConfigMap's bytes: the runs are kept by count (400) and what was found by its count of checks (160).
- **An agent's instructions keep their rows' ids** (DB-81; step `0040`). An agent whose instructions changed had every row of them written again with new ids, its test runs too, at each case of a test run. A row is now updated in place, and a test run adds a result a case. `ai_providers.secret_ref`, which nothing filled, is dropped.
- **A decision on a proposed change writes that change alone** (DB-79). Every approval, rejection, check, logged command and linked case read every change's rows and saved them as one document, and two decisions on two changes took turns. The proposed changes now have a repository of their own: an operation reads and writes one change's rows, and of those only what changed. Two people approving one change from two replicas still get one approval and one *Already approved by …*. The record's byte bound is gone: the newest 500 decided changes are kept. A waiting change's conversation with Sherlock is bounded on its own (48 KiB) and no longer gives way to another change's.
- **A Mycroft run keeps its row's id** (DB-78; the eighth cluster test's O3). With a database, a run of page changes was written again whole, under a new `wiki_run_id`, at every approval or decision. Its row is now updated in place and keeps its id while the run is kept, and a page approved writes that page's rows and the run's, and no other.
- **The database is opened before the console's stores are made** (DB-59): a start's order only, so the stores made after it can be given the database.
- **A kept conversation keeps its hand-overs** (DB-58). The conversation Sherlock keeps for a case or for a waiting proposed change lost what an answer had handed to other agents when the console restarted or another replica took over. The hand-overs, with the ones inside them, are now kept with the answer, in a ConfigMap and in the database: scrubbed of what looks like a secret as the answer's text is, each text clipped, and bounded together so that a conversation still fits where it is kept.
- **The ConfigMaps of before are deleted once copied, and Helm never deletes one first** (DB-72, ADR-167; the owner, November 20, 2026). Once every record set a ConfigMap of 0.12 held is recorded as copied, the console deletes the ConfigMap: `<release>`, `-audit`, `-sessions`, `-ai`, `-knowledge`, `-automation`, `-automation-runs`, `-issues`, `-proposals`, `-cases`, `-runs` and `-casework`, as it deleted each case's own. A copy that fails keeps its ConfigMap whole for the next start. The chart renders each only while it is in the cluster, empty and with `helm.sh/resource-policy: keep`, so the upgrade from 0.12 keeps it for the copy and no later upgrade deletes it or makes it again; `helm template` renders all of them so. The Role no longer grants `create`, `patch` or `update` on ConfigMaps but the temporary wiki store's: `get`, `list` and `delete` remain, for the copy and the deletion. The ConfigMap flags stay, as the copy's source, and the chart passes them all. The configuration ConfigMaps (`-agents`, `-auth-config`, `-toolbox`) and `-wiki` stay. The proposed changes of before CF-104 (`<release>-cases`) are read in place by the copy into the database instead of copied into `<release>-proposals` first.
- **With a database, a record set is removed from its ConfigMap once it is copied** (DB-55; since DB-72 the ConfigMap is deleted whole, above). The ConfigMaps were kept as they were at the copy, as a way back; a console from before the move then showed changes approved and run since as waiting again, and could run them a second time. Now the copied keys are deleted (the ConfigMaps the chart makes stay) and each case's ConfigMap is deleted, also what an earlier build of this release copied and left. **Going back to a console without the database means a restore**: save the ConfigMaps before the upgrade (`kubectl get configmap -n <namespace> -o yaml > before-0.13.yaml`), or take a backup. Without a database nothing changes.
- **Approving a variable change sets what it alters** (DB-34), not the fleet's variables whole as they were when it was asked for. A value of the fleet that the change does not name, and that someone set meanwhile, no longer holds the approval and is no longer overwritten; a value it does name, changed meanwhile, still holds it.
- **A node's own variables are the node's** (AU-23). The Variables page has always kept a node's own values and reboot time under All nodes. A card or an API request could also put one under another fleet, so a node in two fleets could have two different values, which was a conflict that stopped its runs. Now a node has one, whichever fleet's request sets it, kept and shown under All nodes. What was kept under other fleets is read as the node's own; where two fleets kept different values for one node, the first by fleet id is used. The API's shape is the same and the app is unchanged.
- **Hosts outside Kubernetes carry no labels.** A host is in a fleet by being listed. The hosts API no longer takes or returns `labels`, an agent can no longer propose `host.label`, and labels kept from before are ignored. The app's label fields for a host have no effect and go in a later change.

### Added

- **The bundled database's image is built from Wolfi's packages** (the owner, November 21; ADR-169). `deploy/postgres` builds `221b-postgres` with apko straight from `packages.wolfi.dev` (no registry image underneath, no Chainguard branding): PostgreSQL 18 and Patroni pinned by major, their exact versions in the committed `apko.lock.json`, for linux/amd64 and linux/arm64 without emulation; WAL-G is WAL-G's own release, checked by SHA-256, since Wolfi's is built without the libsodium the backups are encrypted with. The Debian image of the development builds is gone, not kept as a fallback: at the time of the switch it had 22 critical and 200 high findings without a fix, this one none (12 medium or lower). It is larger, about 535 MB (175 MB compressed). `make image-postgres` builds it (`hack/wolfi-postgres.sh`, its tools pinned to releases at least two weeks old with their SHA-256); `make postgres-lock` moves to Wolfi's newer packages. **Each release keeps a copy of its packages**, `ghcr.io/ucesys/221b-postgres-packages:<version>`: the locked packages with an index signed by an RSA key pair made in the release job for that release alone (its public key in the copy, its private key never stored), the copy signed keylessly by the release workflow; `make postgres-rebuild WOLFI_PACKAGES=<version>` builds the release's image again from that copy alone once Wolfi has deleted the packages, checking the workflow's signature and then trusting only the key inside ([docs/database.md](docs/database.md#building-an-old-release-again)). A database made by the Debian image moves over in place at the upgrade: same collation order, nothing to do ([docs/upgrading.md](docs/upgrading.md)). The image has no `contrib` modules. The entrypoint names PostgreSQL's socket directory, `/var/run/postgresql`, where Wolfi's PostgreSQL would not put it.
- **A connection's last test is kept over a restart** (DB-64; step `0041`). The cluster page's *Connection test* was kept in the memory of the replica that ran it: a restart lost it, and another replica never showed it. It is now kept with the connection, its steps among it, with when it ran and who ran it (`lastTestedBy` in `GET /api/v1/clusters`), and every replica shows it.
- **A run's whole output is kept** (DB-87; step `0042`). Run History's page of a run showed each node's whole output only while the console that ran it kept it in memory, or from the Toolbox's transcript volume when there was one; otherwise the last 2 KiB. Each node's output is now kept in the database, its newest 64 KiB, masked as the tail is (a secret parameter's or a sensitive variable's value never in it), and the page reads it from any replica. Automation's runs and run requests are one repository whose operations read and write one run's rows, in place of two documents read whole at every save; a variable's row now names who set it.
- **Run History shows the run requests with the runs** (AU-24, DB-37). The requests for a run whose own values wait for approval on production are rows of the same list: waiting (with a link to its approval in AIOps › Inbox), rejected (with who rejected it and why), withdrawn or expired; an approved one is the run it started, which names it. A filter by state sits beside the search. The API is `GET /api/v1/automation/history`.
- **The bundled database's base backup takes a cron schedule** (DB-84): `database.bundled.backup.schedule`, five fields in UTC such as `"0 */6 * * *"` or `@weekly`. `dailyAt` is still taken when the schedule is empty, as the same time every day. The backup container runs a small Go program in place of its shell script, with the same rules for which member takes it.
- **An external database can be signed in to with the cloud's IAM, with no password** (DB-83): `database.external.iamAuth: aws` for RDS and Aurora PostgreSQL (an RDS IAM authentication token, signed with the ServiceAccount's IAM role through IRSA or EKS Pod Identity; give `database.external.aws.region`) or `gcp` for Cloud SQL (an access token of the ServiceAccount's Google identity through Workload Identity). A token is made for each new connection and sent over TLS only; `iamAuth` with a password Secret, or without TLS, is refused. The role, the annotation and the database user are the operator's to make: [docs/database.md](docs/database.md).
- **A page that needs the database answers 503 when the database is away**, whatever its handler made of the failure (500, 502 or 400 before), with the same sentence (DB-15), and with the header `X-221b-Database: unavailable`, which tells it from a part that is off.
- **A banner while the database is away** (DB-15). On every page, under the top bar: *The database is unavailable*, that sign-in and the pages read live from the clusters still work, and that what is kept in the database (the Inbox, cases and reports, jobs and their runs, Mycroft, Automation, applications, credentials, the audit log and the settings) cannot be read or changed until it is back, with since when and, for a SuperAdmin, why. It appears by itself, at the first refused call or within half a minute, and goes within 10 seconds of the database's return.
- **You can sign in while the session store is away** (DB-65, ADR-165). A sign-in whose session cannot be written, because the database, where the sessions are kept when there is one (DB-66), or without one the Kubernetes API server, does not answer, is now kept in its cookie, signed by the console, and every replica takes it: before, the session was known only to the replica that served the sign-in, so with two replicas the sign-in page came back on every other request. The sign-in page says what happened: such a session lasts 30 minutes from sign-in (`auth.outageSession`), is not extended by use, and at the first request after the store is back becomes a stored session that ends at the same time, without signing in again; when the 30 minutes are over you sign in again. It works for local accounts, a directory and OIDC. While the store is away it cannot be ended everywhere at once: signing out ends it on the replica that served the sign-out, a password reset on the replicas that hold it; a local account disabled or deleted loses it at once everywhere. Once the store answers, the ending is kept there until the 30 minutes are over, and every replica refuses the cookie. A person in so many groups that the session does not fit a cookie is told that a local account can sign in. The key is in a new Secret the console makes at its first start, `<release>-session-key`: anyone who can read it can sign in as anyone, as with the accounts' Secret, and deleting it ends those sessions. Server flag `-session-outage` (`SESSION_OUTAGE`).
- **What you submitted waits in your own Inbox** (IN-11). A script's version in review that you wrote or submitted, a variable change you asked for and a Watson command of yours that takes a second person are rows of your AIOps › Inbox while they wait, marked *Waiting for another SuperAdmin* (a Watson command under the two-person rule: *Waiting for a second person*). Until now they were left out, so nothing said that they waited, or for whom. The row opens the same drawer, with Open in place of Review and nothing to approve or reject, and is counted on the Inbox tab and by the bell, like your own run requests and console changes: the count is everything pending in your Inbox. `GET /api/v1/admin/approvals` marks such a row with `own` and `waitingFor`.
- **`database.mode`** in the chart: `bundled` (the default) or `external`. `bundled` runs PostgreSQL beside the console from a second image of the release, `221b-postgres` (PostgreSQL 18, Patroni, WAL-G): one member, or three with `database.bundled.ha`, a commit waiting for one of the two standbys; passwords and a certificate made once; the write-ahead log archived and a base backup a day, to S3 or a second volume. `external` connects to a PostgreSQL 16 or later that you run (`database.external.host`, `port`, `database`, `user`, `passwordSecret`, `sslMode`, `caSecret`, `clientCertSecret`, `maxConnections`, `listenerHost` for a pooler in transaction mode). One member has been run in a cluster (upgrade, copy, restart, base backup, rollback); **three members, a failover and a restore have not been run yet.** To a volume, the primary takes the base backup and a new primary takes one at once; with three members a bucket is the better place.
- **The audit log in the database**: with a database, Administration › Audit log reads `audit_events`, where each event is a row added and never changed; it is no longer bounded by a ConfigMap, and is kept a year. What the ConfigMap held is copied once, and after a rollback to a release without a database and an upgrade again, the events written meanwhile are copied too.
- **The Toolbox's session records in the database**: with a database, each ended session is a row of `toolbox_sessions`, no longer bounded by a ConfigMap's size; the newest `toolbox.history.keep` are kept, and the ConfigMap's are copied once, with those a rolled-back console added copied at the next start with the database.
- **Automation's scripts in the database**: with a database, a script is a row of `scripts` and each version a row of `script_versions`, with its parameters, Kubernetes actions, findings and approvals as rows of their own tables; copied once from the ConfigMap. The script groups and execution profiles are rows of `script_groups`, `run_profiles` and `run_profile_fleets`. The variables are rows of `variables`, each on one fleet or on one host, with the ceiling and the reboot time as columns of `fleets` and `hosts`. Their changes are rows of `variable_changes`, each with what it alters in `variable_change_items`. The runs are rows of `script_runs`, each node of a run a row of `script_run_hosts`, with the values it got in `script_run_values`; the runs that wait for approval, were rejected or expired are rows of the same table.
- **The AI agents' configuration in the database**: with a database, the providers, the agents' settings, their instructions with every version, draft and test run, their test cases and the pilots' answers are rows of `ai_providers`, `agents`, `prompt_versions`, `test_runs`, `test_cases`, `pilot_entries` and the tables that hang from them, no longer bounded by a ConfigMap's size; copied once from the AI ConfigMap.
- **What the agents spend as a ledger**: with a database, each cost is a row of `ai_spend`, only ever added, and the day's and month's sums are read from the rows; replicas no longer take turns to save. This month's and last month's rows are kept. The sums the settings ConfigMap held are carried over once.
- **The jobs, their runs and the validation rules in the database**: with a database, a job's settings, each run with its findings, facts and proposals, the checks seen on each cluster, the rules with their suggestions and what the runs found under each check are rows of `jobs`, `job_runs`, `findings`, `validation_rules`, `check_found` and the tables that hang from them, no longer bounded by a ConfigMap's size; copied once from the runs' and the cases' ConfigMaps.
- **The proposed changes in the database**: with a database, a change the agents propose is a row of `changes`, with its evidence, actions, plans, results, approvals, history, commands and the cases it resolves as rows of their own tables, no longer bounded by a ConfigMap's size; a waiting change's conversation with Sherlock is a row of `chats` with a row of `chat_messages` a message. Copied once from the proposed changes' ConfigMap, the changes before their conversations.
- **A conversation with Sherlock is joined to its change or its case by a key** (DB-56, DB-57): with a database, a proposed change keeps its row through every change to it, and the conversation kept for a waiting change or a case is a row keyed to that change's or case's row, which it goes with when the change or the case is deleted. The session's name is no longer stored. A database that already holds conversations has them keyed by schema step `0033`; one whose change or case is gone is deleted.
- **The fixes and the accepted exceptions in the database**: with a database, a fix is a row of `fixes` with the cases it was seen in as rows of `fix_cases`, and an accepted exception a row of `exceptions`, no longer bounded by a ConfigMap's size; copied once from the case work's ConfigMap.
- **Mycroft's sources, syncs and page changes in the database**: with a database, a source is a row of `knowledge_sources` with its live addresses and exclusions, each source's last read and the last syncs are rows of `knowledge_source_reads` and `knowledge_syncs`, and a run of page changes that waits for review is a row of `wiki_runs` with its page changes, their approvals and its decisions, no longer bounded by a ConfigMap's size; copied once from the knowledge ConfigMap. The wiki's pages stay where they are kept.
- **The cases, the known issues and the services in the database**: with a database, a case is a row of `cases` with its messages, the work on it (the analysis, the RCA, the history, the proposals, the drafts, the commands) and its conversation with Sherlock as rows of their own tables, no longer one ConfigMap a case; the known issues and the service catalogue are rows of `known_issues` and `services`. Copied once from the cases' ConfigMaps and the issue service's. The list of cases is read from the cases' rows.

- For developers: `make test-go-store` runs the tests of the eight packages whose records have moved (the agents, the jobs, the case work, the cards, the fixes, the lessons, Mycroft and the issue service) with their records in the database.
- **Inventory in the database**: with a database, hosts outside Kubernetes, paired nodes, fleets with the members of listed fleets, and each node's facts are rows of `hosts`, `host_logins`, `host_pairings`, `fleets`, `fleet_hosts` and `host_facts`.

- **Approvals in the database**: with a database, the requests that wait for a second person, their decisions, the standing approvals and the notification channels are rows of `approval_requests`, `approval_decisions`, `approval_policies` and `notification_channels`; copied once from their ConfigMaps.

### Fixed

- **Run requests expire** (FU-05a): an Automation run whose own values wait for approval could be approved at any later time and then started as the person who asked. While another SuperAdmin could approve, the change is now refused with a message (make the person a SuperAdmin on their roles, which waits for approval, then change the email); the only SuperAdmin still makes one at once, and the audit log says so.

The upgrade notes now say correctly that, without the setting, requests through a proxy share the proxy's per-address sign-in limit.
- **Helm: adopting a release keeps its values.** Setting the source of a running release now starts the application's values from the release's current values (`helm get values`); values given on that first save are merged over them instead of replacing them, so a Redeploy no longer resets the release to the chart's defaults. Application values show credentials masked; a masked value saved as it is keeps the stored value.
- **Watson: upgrade cards list what they remove.** Every Helm upgrade card lists, by key, the values the release has now that the deploy would remove or change (20 at most); a card that removes values is shown as a warning.

- **Charts render in a separate process.** A chart's templates render in a child process of the console with limits on memory and CPU time; it is stopped after 60 seconds, a few render at once, and a chart past the limits is refused in plain words while the console carries on.
- **The diff against the source** renders without reading the cluster (`lookup` finds nothing) and masks credentials in every object, not only in Secrets. Comparing with the source and listing its branches and tags need the right to manage the application in the namespace (the role, plus list and create Secrets).
- **A proposed change kept from a chat** shows its targets and impact as read by the person who asked, with their own rights; its fingerprint is still checked with the console's account. A command handed to Watson as Sherlock's becomes a proposed change only when it is in one of Sherlock's answers in the person's own conversation; otherwise it is a typed command.
- **Watson: Helm from git or a repository** — `helm install` and `helm upgrade` with `--git` or a repository chart, dry runs included, need the rights of managing applications in the namespace. When a repository cannot be reached the message is always "the repository could not be fetched"; the cause is in the console's log. Token and not-found messages are unchanged.
- **Local accounts sign in with LDAP on** (RB-28a): with `auth.mode: ldap` the accounts created in the console (the Secret `<release>-users`) were not read, so they could no longer sign in; now they are, also while the directory cannot be reached. - **Helm: Values next to Setup**: a release's Values tab is second, right after Setup, instead of after Other.
- **A fix is verified only by a read** (PM-J1c): an agent that answered `"still": null` for a fix it could not re-check was read as saying the problem is gone, which verified the fix. Null is now no answer, and the case keeps waiting.
- **A job's answer without a readable block is said** (PM-C6): a nightly audit, an alert diagnosis or a daily digest whose answer was cut or had no JSON block ended *ok* with no findings. The run now notes it and asks the agent once for the block alone.
- **A run that used every round** of reads ended with no answer (PM-C5): on its last round an agent is now told to answer from what it read.
- **Run in Watson on a case says what it does** (CF-48): its tooltip promised "Nothing runs until you approve it there", but a read (such as a suggested fix's `kubectl get …`) runs at once while Watson's *Auto-run reads* is on, as Send to Watson does in the dock. No path ran a change without an approval.

An item excluded while a sync runs stays excluded when the sync ends, and a Confluence page excluded with its children now covers a grandchild whose parent was never read (Data Center).

- **Instructions in layers, from draft to live** (AI-08 to AI-14, AS-01 to AS-03): each agent's built-in text, shown in full and editable with *Reset to built-in* and *Compare with built-in*; house instructions (the chart's `agents.<agent>.instructions`, or edited in the console: *In sync*, *Edited in app*, *Baseline changed*); notes for every cluster and per cluster. An edit goes *Draft* → *Test* (recorded test cases and replays of real answers, cost shown first) → *Pilot* (chosen people or clusters) → *Live* (a second SuperAdmin's approval), each step a button that says why it waits; every live version restores in one click; any answer can be saved as a test case.
- **Sherlock's compact form** (AS-07) for a model whose context its whole form does not fit: about 2,500 tokens of instructions and tools instead of about 10,000; the agent's drawer says how much of the context it takes.
- **Show costs** (CF-40): a SuperAdmin switch in Settings › AI › Agents; off, no dollar amount shows anywhere but the budget fields.
- **Prompt sources** (GS-13): [docs/prompt-sources.md](docs/prompt-sources.md) records what the agents' instructions drew on; `hack/check-prompt-sources.sh` fails on a source it does not record.

#### The AIOps area

- **AIOps, a third area** beside Kubernetes and Automation (CF-91, CF-104, ADR-88, ADR-152), at `#/aiops/…`, across clusters, shown to whoever has something in it: **Inbox**; **Jobs** (Schedule, Runs, Validation rules); **Mycroft** (Wiki, Known issues, Exceptions, Fixes). Sherlock and Watson are in the dock on every page, and Sherlock knows the area's pages, buttons and who may use them, and the item open (its AIOps skill, IB-10 to IB-13, IN-10). Settings has an *AIOps* group: Issues, SLA, Cases and Jobs.
- **The Inbox, one table** (IN-01 to IN-06, CF-17, CF-35 to CF-38, CF-66, CF-81, ADR-116): every case, proposed change, approval, known issue draft and knowledge draft (and, for a SuperAdmin, suggested validation rules, CF-87), pending first, then P0 first, then the longest waiting, each with its priority, type, incident number, cluster, object (linked, with its age), status, waiting time, assignee and *Last change* ("Auditor (agent) · 2h ago"). Filters in the address: Pending or All, People or Agents, Mine or Unassigned, priority, type, status, cluster and a search that finds past RCAs by their cause; *late* names the SLA target passed. Pick many cases and assign, prioritize, analyze or close them at once. A row opens its drawer at `#/aiops/inbox/<kind>/<id>`; *N alerts now* links the cluster's Alerts tab.
- **The bell** (CF-80, IN-07), right of *Live* in every area: red while a P0 or P1 case waits for you, yellow while anything else does; it opens the Inbox. The Inbox tab counts what waits.
- **Every problem is a case** (CF-01 to CF-05, CF-07, CF-14 to CF-16, CF-45, CF-67, CF-90, ADR-126 to ADR-133): a person's report, *New case*, an alert or an agent's finding, numbered `C-<n>`. A case is *New*, *In progress* (only a person puts it there; asking the reporter shows *Waiting for the reporter*) or *Closed* with one outcome: *Fixed* (an RCA, required at P0 and P1), *Duplicate* (of an open original), *No action needed*, *Known issue* or *Exception* (agent-found cases). A finding that repeats an open case joins it (*seen ×N*), is recorded on its known issue (*still present*), is dropped by an exception, reopens a fix that did not hold, or opens a regression. Priorities run P0 (outage), P1 (blocking), P2 (service degradation), P3 (preemptive) to P4 (question); agent-found cases have an SLA only at P0 and P1. The states are drawn in [docs/states.md](docs/states.md).
- **New case** (CF-12, CU-02, CU-03, CF-36, CF-37): a title, what you know, a cluster or none, what it is about in any words, a priority, a type and an incident number; as you type it shows the open cases, known issues, exceptions and recent closes like it, with their RCAs. An alert's *New case* opens a case about its object.
- **The case drawer** (CF-18, CF-46 to CF-49, CF-58 to CF-60, CF-70): near full screen, the case on the left and Sherlock and Watson on the right (tabs on a phone). One Sherlock conversation per case, shared by the people who work it and naming who asked, deleted when the case closes. Watson's commands from the case are logged on it, and the changes that worked start *What was done* when it is fixed. Priority, type and assignee in the header, the other fields edited in place (a pencil on each), the cluster by name, and one shared draft with *Save*, which asks before overwriting someone's newer edit.
- **Case analysis** (CW-04, CW-06, CF-32, CF-43, CF-49, CF-52, CF-82, CF-83): the Troubleshooter, read only, gives the cause, the evidence, a suggested fix with *Run in Watson* on each command, and proposed changes. It starts from the earlier cases like it with their RCAs, the open ones, the known issues it matches and the active fixes. New agent-found cases at P0 to P2 are analyzed by themselves, one at a time within the job's budget; *Analyze* and *Analyze again* run it at once. When it finds no problem it says why, and a case an agent or the console opened at P0 to P2 goes down to P3 unless a person set its priority.
- **Proposed changes** (WC-01 to WC-19, CF-25 to CF-31, CF-34, CF-39, CF-56, CF-61, CF-62, CF-92, IB-08, ADR-99 to ADR-102): every change an agent wants, in a chat or on its own, is a proposed change `PC-<n>` that waits in the Inbox and the cluster's Watson panel and outlives a restart: what started it, the agent and model, why, the evidence, one line per step (*What Watson will run*, *What it changes in the console*) with impact and risk, the cases and known issues it resolves, and its expiry (24 hours, or when its alert resolves). Its drawer opens like a case's, with a Sherlock conversation of its own. *Run in Watson* brings it to Watson, where the one approval is given after a re-check, by those in `cases.approverRoles` (two different people on production); *Reject…* asks why. Applied, it records the fix on each case it resolves; closing a case rejects the changes waiting only for it.
- **A fix is verified only on what a run re-checked** (CF-29, CF-30, CF-06, CF-94 to CF-96, ADR-145): the nightly audit and the alert diagnosis are given their job's waiting fixes inside what they read and say of each whether the problem is still there; only *gone* verifies it, and then a case below P1 closes as *Fixed* by itself, while at P0 and P1 it waits for its RCA. The case says which run verified it and what it read, or how long it has waited and how many runs passed. A fix re-checked and still there did not hold.
- **Fixes** (CF-50 to CF-55): closing a case as *Fixed* with *Save fix* (on by default) saves its fix in AIOps › Mycroft › Fixes, one per problem with the cases it fixed, which people edit and which outlive their cases; the agents are given the active ones.
- **Exceptions** (CF-13, CF-68, CF-69, CF-76): AIOps › Mycroft › Exceptions lists them, each covering one cluster, object and validation rule, with its justification, matches and last match; *New exception* suggests the cluster's objects as you type; Active, Stale, Expired, Inactive and All, with *Make active again*. Exceptions are the console's records, given to the agents in their task.
- **Known issues** (CS-13, CS-14, CF-14, CF-63, JR-10): AIOps › Mycroft › Known issues, with the editor (symptoms in users' words, services, status, workaround, expected fix, owner), dated updates, *Accept the proposal* on an agent's draft, Follow, and how often each is still present.
- **Validation rules** (CF-08, CF-71 to CF-75, CF-85 to CF-87, CF-89, CF-93, ADR-138): the ids the agents key their findings by, each with its meaning, in AIOps › Jobs › Validation rules, a SuperAdmin's: one table of the rules, the ids agents made up (*Unlisted*, with the agents' description) and suggestions, to add, edit, retire, replace by another and promote. The daily Housekeeping suggests rules and promotes only exact repeats; a suggestion waits in a SuperAdmin's Inbox.
- **Housekeeping** (CF-53, CF-54, CF-75, CF-100): a daily job with no agent that makes duplicate fixes, known issues and exceptions inactive, marks contradicting fixes pending, suggests validation rules, offers proven fixes to Mycroft, and puts right a case whose work was not saved with it; it reports what it did. The fixes of cases closed as Fixed before were imported once.
- **Settings › Cases and Settings › SLA** (CF-19, CU-06, CF-78): how long closed agent-found cases are kept (90 days), New case's look-back, when an exception is stale, the caps per run, and after how many minutes a critical alert nobody handled opens a case; the first-response and resolution targets per priority.
- **Alerts and cases** (CF-77 to CF-79, CF-82, CF-84): an alert's row links the open case that covers it, in place of *New case*; an alert diagnosis that concluded acknowledges its alert in the job's name, with a link to its run and case; a critical alert still going after 15 minutes that no case covers and no run concluded on opens a P0 case by itself; a case from an alert is named by its reason (*CrashLoopBackOff: back-off restarting failed container: shop/Pod/web-1*).

#### Jobs

- **Agents on their own** (JB-01 to JB-22, JR-05 to JR-07, CF-103, ADR-90 to ADR-93): AIOps › Jobs › Schedule lists the jobs, each with its agent (*Nightly audit · Auditor*): the *Nightly audit*, the *Alert diagnosis* of each new alert (a repeat updates its run), the *Daily digest*, the *Case analysis*, the *Case triage* of each reported case, *Housekeeping*, the *Drift check*, a *Wiki sync* per knowledge source and *Backup to S3*. Each is off until a SuperAdmin turns it on, with its clusters, a schedule (read back in words, in a time zone) or an event, a budget per run and per day, its lowest priority (P3 by default, CF-33), and a name and instructions of its own (*Reset to built-in*); *Run now*, *Pause* and *Add another <kind> job* are in its drawer. Schedules run once, on the leading replica; every change and run is audited.
- **Agents on their own read as `221b:agents`** (JB-08), never as a person, with the role Settings › Jobs chooses: Viewer (the default) or SuperViewer. Settings › Jobs also says who may edit jobs besides SuperAdmins. Nothing a job does changes anything: a change it wants waits as a proposed change.
- **Runs** (JB-14, JB-16, JR-01 to JR-04, CF-11, CF-95, CF-97 to CF-99, CF-101, FX-12): AIOps › Jobs › Runs lists every run with when it started and ended, its health in the tone of its worst finding (*Done · 2 critical*), what each finding did (opened, seen, known, excepted, reopened, regression, ignored, expected) with a link, the fixes it verified, its proposals, tokens and cost; a run under way can be cancelled. A run says what it could not be used for: a cluster that did not answer (*Done, with errors*), the findings left out past its 40, the fixes it did not re-check, and findings not routed while the exceptions could not be read, which the console routes later. An agent files nothing for a cluster it was not asked about, a proposed change is filed whole or not at all, and the same change for the same cases replaces the one waiting whatever its title.
- **A finding the system expects opens no case** (CF-82, CF-86): an agent marks a finding expected with its evidence, and it is shown on the run with its reason; an agent that makes up a validation rule says what it means.

#### Watson

- **Watson's console actions** (WC-12, ADR-101): adding, labelling and removing hosts outside Kubernetes (a host waits until a person pairs it), creating and changing fleets, and Automation variables and per-node values, each a SuperAdmin's to approve; a card never carries a host key or a credential.

#### Mycroft's knowledge

- **`ask_knowledge` knows the console's records** (KN-32, KN-33, CF-52, ADR-144): after the pages, the open known issues, the active fixes and, to who may read them, the active exceptions a question matches. Mycroft's drafts are given the fixes on their subject and flag a page that contradicts one (*Contradicts F-3, used in 4 cases*).

- **Inventory and drift** (GS-11, KN-19, KN-30, KN-31, ADR-98, ADR-143): the hosts a document lists that the console lacks, and the groups of hosts it names as fleets that would select nodes now, are proposed as changes (*3 nodes now: rke2cp1, rke2cp2, rke2cp3*); the drift check proposes each difference no known issue or exception covers, and the report lists what it left out and why.
- **Known issues in Confluence** (KN-13 to KN-18, ADR-97, Settings › Issues › Confluence): a Status page by service, a page per known issue and a resolved archive, kept current through an outbox; a Notes part people edit, and a person's edit of the rest waits for its owner. ### Fixed

- **A console change waiting for a second SuperAdmin is applied once** when two approve at once; the second is told who approved it and when, as is a second approval of a Watson command (IB-09, ADR-111).
- **A change proposed again no longer loses its approvals** (CF-110, ADR-153): the same change an agent proposed again replaced the card that waited, and the card's approvals went with it. On a production cluster, where a change needs two people, the first approval was gone each time the nightly audit proposed the change again. The card that waits is now kept, with its approvals, and its history says *proposed again*; it is replaced only when what it acts on changed since.
- **A re-check is about the cluster the agent was asked about** (CF-108): in a run over several clusters, an answer about one could verify, or reopen, a fix on another by naming it; such an entry is now left out and the run says so. A re-check that names the cluster by its name, not its id, now counts.
- **A verified fix that is found again no longer reads as verified** (CF-108): at P0–P1 a case whose fix a run verified waits for its RCA; when a later run found the problem again it went on saying *Verified: add the RCA to close*. It now says the fix did not hold.
- **A case a re-check reopens is analyzed again** (CF-108): closed as Fixed and found still there by a run that re-checked it, it is queued for its analysis as one reopened by a finding is.
- **A page that fails to draw** shows an error screen with Reload and *Report this problem* instead of going blank (CS-19).
- **A run whose cases cannot be read says so** (CF-111): when the cases or the known issues could not be read, the agent was given the keys in use without them, as if no case were open and no fix waited, and the run said nothing. Now the run notes that its agent was not given the keys, as it does when the exceptions cannot be read.
- **A case names its job** (CF-112): a case's drawer showed the job's id ("found by Auditor (nightly-audit)"); it now shows its name, "Nightly audit", as the rest of the console does.
- **A case's drawer keeps its full height with the dock open** (CF-114): with Sherlock and Watson open in the dock, a case's drawer ended above the dock, a third shorter, with a second Sherlock and Watson under its own. The dock now steps aside while a drawer shows a Sherlock you can ask in, and comes back when it closes.
- **A waiting fix says why a run left it** (CF-115): when a run found a waiting fix's problem again but an exception, the agent's *expected* or the job's lowest priority kept it from opening a case, the case waited with nothing said and the run did not count it. It now counts as not re-checked, and the case says why ("run-12 found it again and opened no case: the agent marked it expected"); use *Skip validation* or reopen it.
- **A run routed twice no longer counts twice** (CF-116): a run whose findings were routed but which could not be saved was routed again on the next look, and every case it joined counted it twice (*seen ×N*), as did a known issue's *still present* and an exception's matches. Routing it again now changes nothing. A case is also seen once per run, however many of the run's findings name it.

New parameter and a pencil on each row open a drawer: name, value, the nodes that overwrite it, the scripts that read it, and Delete.
- Pending approvals no longer approves anything: Review opens each item to be read first, and a waiting parameter change shows its values before and after. Every version of a script has the no-diff icon, and the diff icon compares with the latest version.
- A privilege is nobody (read-only) or elevated (the ssh-paired account's rights) for a script, a fleet's ceiling and a run profile; a header may say `privilege nobody` or `privilege elevated`, and none and full still work. The script drawer's group and New group sit on the tabs' line. The API paths follow the page names: `/automation/run-profiles`, `/automation/fleets/{fleet}/variables`, `/automation/variable-changes`.
- Scripts show their kind, Shell or K8S, in the table and the drawer. A fleet's ceiling reads nobody (read-only) or inherited (scripts run as the ssh-paired account). The script drawer's group sits above the script, with a New group button. The pages' addresses follow their names: `#/variables`, `#/run-profiles`, `#/run-history`; the old ones still open them.
- **Renamed:** Parameters is Variables, Configurations is Run Profiles, and a run's Configuration is Run as. The built-in profiles are nobody (read-only), ssh-paired account, and login-user (Kubernetes, as the signed-in person); their ids are unchanged, so earlier runs still name them. Run Profiles shows each profile's kind (ssh or k8s) and the fleets' ceilings above the table, without the Connects as column. A real run asks for confirmation; approval on production is unchanged. Variables lists only changes waiting for approval: decided ones are in the audit log. Scripts filter by state with a row of buttons (All, Review, Draft, Approved). The script drawer has its group at the top right with New group, and lists the header, then Sherlock and what it said (ten lines, scrolling), then the checks.
- Parameters has the same Fleets pane as Nodes: colour, requirements, New and a pencil to edit each. In the script editor Sherlock says what it wrote or changed, beside the code, with how many lines changed. Scripts and Run History, which was Executions, sort by any column.
- **Picked nodes** on the Nodes page: a box beside each name, and a bar with *New fleet…* (a fleet of those names), *Add to fleet…* (a fleet of names they join) and *Pair for SSH…* (one card to approve, then one pairing session per node). - One pop-up menu at a time: opening a Tools menu, a release's or a revision's menu closes the one open before it, on every page.
- **Administration.** Pending approvals is Approvals: what waits for you on top, then what was approved, rejected or revoked, newest first, in one table with who asked, when, who decided and when. Sessions and Audit log are one Logs page (old links open it). Sherlock and Watson stay docked on these pages. A role's *See every permission* opens Permissions on that role alone. A role definition reads Elevated or Read-only (still `full` or `readOnly` in the chart's values). Opening Administration keeps the Kubernetes or Automation area.
- Run as shows the profile a run takes, the one that fits the script unless another is picked, and offers only those that fit the script and the fleet. Closing a script with unsaved changes asks first.
- Approve asks for confirmation, on a script version and on a variable change. A version in review can be rejected, and a change too, with a reason (required, at most 500 characters) that the version, the audit log and Approvals show; a rejected version never runs or comes back, and the fix is the next version (`POST /api/v1/automation/scripts/{name}/versions/{n}/reject` with `{comment}`).
- **Changed:** a fleet with no ceiling set is nobody, as the page always showed: an elevated script no longer runs there until someone raises its ceiling under Variables.
- Off production, Run runs the version chosen, approved or not, and starts on the newest, as a dry run does; production still runs approved versions only. A rejected version never runs. The gear also flags a new review you can approve.
- The gear in the top bar carries a flag when someone approved, rejected or revoked what you asked for; it then opens Approvals, which marks your rows *yours*, and the flag clears there (kept in this browser). A decided script version opens over Approvals instead of leaving for Scripts. The privilege ceiling sits above the variables table. A Secret or namespace made in the console shows as soon as the cluster reports it, not at the next refresh. A parameter name in lower case says what to write instead (`MYNAME`, not `myname`).
- *Node shell* is *K8S node shell* wherever the page names it, beside *SSH*.
- The node drawer's *Actions* section (cordon, uncordon and drain as commands to copy or send to Watson) is gone: the node's Tools menu runs them.
- **Reboot timeout.** Variables sets how long a fleet's nodes, or one node, have to come back after a script reboots them (1 to 240 minutes; 10 when unset). A node in several fleets gets the longest; a node's own time wins over all of them. Each run records each node's time.
- **A reboot is checked.** A node is back from a reboot only when it answers from a new boot (its boot ID changed) and Kubernetes reports it Ready; a reboot command that fails, or a node that never went down, fails the node. A script that runs as nobody cannot have its node rebooted.
- **Each node answers to all its fleets.** A run refuses nodes under a fleet whose ceiling is below the script's privilege, and, on production, nodes in any fleet where a waiting variable change suspends the version, whichever fleet the run was started on. On production a run takes its values from the fleets alone: the Run dialog's values are for dry runs and other clusters, and the API refuses them (409).
- **Only the newest variable change on a fleet can be approved**: an older one says which newer change overtook it and can only be rejected; one whose fleet's values changed since it was asked for says what differs. Approving applies the change only over the values it was asked against.
- **A node is in one run at a time**: a run on nodes another running run has is refused with that run's number, and the control-plane nodes of a cluster are worked on one at a time across runs. A start sent twice starts one run.
- **Runs stop with their console.** A console that loses the lead stops its runs (interrupted, with the reason); a cancel reaches a run through its record too. A production run stops before each batch when its version lost its approval or its text since it started. A run keeps who had approved its version; a node drained and not uncordoned is marked *left cordoned* in the run, with an Uncordon button, cancelled runs included.
- **Storage.** Runs and nodes' facts have a ConfigMap of their own, `<release>-automation-runs` (the chart creates it; they move there on the first save); the newest run always fits its record. Revoking keeps who had approved; versions a kept run used are kept. Saving the same text as a rejected version starts a new version that says so. The audit log drops runs' per-node commands first when full.
- The page shows what the server says each person may do with a version (approve, reject, run on production or elsewhere, dry run), rather than working it out again. The gear's mark is per person on a shared browser, and orders the server's times correctly within a second.
- **Two people for production and SuperAdmins.** Taking a cluster off production, and making a local user a SuperAdmin (by role, or by a group that gives it; on create, on the Users page and in a restore), waits for another SuperAdmin on Administration › Approvals as a *Console change*; the rest of the change applies at once (202). Whoever asked may withdraw it with a reason, never approve it. When the one asking is the only SuperAdmin, it applies at once and the audit log says nobody else could approve it. Helm values stay the way around it.
- **Sign-in off is Viewer.** With `auth.mode: none` everyone is a Viewer (`auth.anonymousRole`: viewer or admin, never a SuperAdmin role, which the chart and the server refuse); SSH, Automation and showing Secret values are off, and the top bar's *Sign-in off · Viewer* says why.
- **One sign-in limit.** `X-Forwarded-For` counts only from a trusted proxy, and every address has the same 30 attempts a minute; the wider budget for shared addresses is gone.
- **Run profiles and impersonation.** A run profile limited to some fleets is refused on All nodes and for a script on the whole cluster; impersonating a profile's or hook's service account is checked for that account by name.
- **Backup and restore.** A backup includes Automation: scripts with their versions, fleet variables (secret references only), run profiles and groups. A restore brings each script back as a draft of its newest version, checks applications and SSH pairings as creating them does (adding pairings, and listing what it skipped), applies variables at once off production and as a waiting change on production, and marks restored audit events *Restored from the backup of …*.
- The release panel's *Source* tab and card are *Setup*: they hold the whole deployment setup, not only where the chart comes from. *Deploy to the fleet* has a row of its own there and is always shown; with no fleet labelled for deploys it says so instead of vanishing (M2-08).
- *Upgrade…* in a release's Tools menu is *Redeploy…*, and its dialog *Redeploy from the source* (M2-03). Every drop-down in a field shows a chevron (M2-02).
- Only the leader reads the clusters: it lists and watches them, polls metrics-server and the kubelets, checks connection health and role drift, and serves every data request; the other replicas sign people in and forward the rest, so Kubernetes sees one reader however many replicas there are. The chart's `replicas.warmStandby` (default `true`) keeps the others' watches open for an instant takeover; `false` has them hold nothing until they lead, for very large clusters. The cap on open event streams (200) is the console's rather than each replica's, and a replica's `/metrics` says `b221_leader 1` or `0` (P7-09, ADR-70).

### Fixed

- The round Sherlock button no longer covers what a drawer has at the bottom right, Delete among them.
- Drawers stop above the Sherlock and Watson dock, so it no longer hides their buttons.
- Admins and Viewers also see a Helm application created by an admin with the same namespace access, such as one whose namespace does not exist yet.

- A node's *In use* is a share of the whole machine: metrics-server reads all of it, so with resources reserved for other software, a share of allocatable could pass 100% and look like an alert. Bars and the home page follow.
- Typing a new script's name keeps focus in the box; no drawer takes focus from a field inside it.
- Escape and Tab keep working in a drawer after its Save button disables itself, or after a click on its text.
- A script's header reads the same with or without spaces after `221b:` and a colon after the key, as the new-script template writes it.

- A test written as `[ "$X" = y ]`, `[[ … ]]` or after `&&`/`||` counts as a condition that reads `X`, so changing it needs approval on production.
- A run's last save can no longer be overwritten by its heartbeat, so a finished run never shows as running and then interrupted; progress is saved at most every two seconds.
- **No ConfigMap can fill up (#46).** The audit log and the toolbox's session records have ConfigMaps of their own, `<release>-audit` and `<release>-sessions`, beside `<release>-automation-runs`; each record moves on its first save. Every key has a limit, and the limits of each ConfigMap's keys add up to less than its 1 MiB (a test checks). A save past a limit is refused with what is full and what to remove; the audit log keeps less instead of stopping; the session records and two-person requests drop their oldest. A replica that cannot read a ConfigMap the chart names does not start, so replicas never keep records in different places. Sherlock's settings say when its spend could not be saved. New metrics: `b221_configmap_bytes{configmap,key}` and `b221_sherlock_spend_unsaved`; a key past four fifths of its limit is logged.
- Opening a pop-up menu closes any other, as before, now by the menus' own outside-click rule heard before a button can stop it (#78).
- **Signed releases (#79, P7-05).** Every image CI publishes is signed with cosign, keyless, and carries SLSA build provenance and an SPDX SBOM as GitHub attestations; a release's chart is signed and has its provenance attested, and the `221b` command comes with signed checksums, provenance and an SBOM. A release's image and chart are never replaced by a rerun. [docs/releasing.md](docs/releasing.md#verify-a-release) says how to check them.
- **Delete a Secret.** A Secret's page has *Delete…* for those who may edit it: it asks first, then hands `kubectl delete secret NAME -n NAMESPACE` to Watson, whose card says what goes (its keys), which pods read it, which Ingress serves TLS from it, and when it is a Helm release record or a service account token, with a server dry run before anyone approves. The card never holds a value.
- **Console.** A log line longer than 1 MiB is split into pieces and no longer ends a followed log. A pod failed as a whole (Evicted, OutOfcpu, NodeAffinity) shows red with its status message and raises an alert. Restarts and last restart count init containers and sidecars as `kubectl get pods` does. A Job that failed after some pods succeeded reads failed, and a Job between pods no longer flashes green. A volume claim no longer raises an alert because another volume's name contains its name. An Ingress using a generic Secret with `tls.crt` and `tls.key` shows its certificate. The rollout check matches ResourceQuotas scoped to a PriorityClass. A ServiceAccount whose name contains its namespace keeps its long-lived tokens on the Access tab. A CA certificate pasted while editing a connection is honoured on save and on Test.
- **Large clusters.** Volume usage is read in its own time and kept when the read runs long, pods' CPU and memory no longer blank when a read runs out of time, and the Policies and Networks tabs no longer stall the console on namespaces with many pods and budgets or clusters with many Ingress routes.
- **Audit.** Records for Secrets, namespaces and applications name the cluster, and refused or failed attempts are recorded as denied or failed, not ok. Stopping a queued command is recorded, and a stop is credited to the person who pressed it. The Audit log page's "kept in memory" notice shows again where there is no settings ConfigMap.
- **Applications.** A save made during a long upgrade is no longer overwritten when it ends, and two saves that collide give a conflict message. `helm install` or `helm upgrade` with `--git` but no `--app` keeps the record's values, parameters, commands and fleet; moving to another repository removes the saved token. `--set` on a Watson line, a saved command's parameters included, applies to that deploy only and no longer joins the saved parameters. A chart with an enabled dependency not vendored under `charts/` is refused with a message.
- **Watson and Sherlock.** A comma list of types shows its targets and guards on the card. *Approve all for…* no longer grants on selection: choose a length, then press *Approve all*. With one custom price set, the other counts at the highest listed price, so caps no longer under-count. Sherlock's Undo no longer mixes up answers from different clusters, and its view changes report back from a hidden window.
- **Sessions.** A pod or Job created while its session is being ended is removed. Extend now really extends a node shell or debug pod. A forward whose connection to the pod died dials again. Terminals no longer freeze while a check waits on a slow directory, and a terminal no longer takes the keyboard from a field or dialog. A session's transcript can be downloaded for as long as the file is kept, not only while the session is in memory. With the CLI, the end of a response is no longer lost when the program reads slowly, and a client that half-closes still gets the answer.
- **Secrets.** A key left on *Replace* with nothing typed can no longer be saved empty. Saving a Secret someone changed after you opened it is refused with a plain message instead of overwriting them. The Namespaces tab's Secret controls follow the cluster you are on.
- **Page.** A tool's dialog stays on the cluster it was opened on. A link in the assistants' window opens only in the main window it follows, and a minimised assistants' window no longer sends Sherlock and Watson back into the main one. A followed pod log that reconnects no longer shows lines twice. Long tables keep drawing rows after crossing the small-screen width. Closing a drawer returns focus to what opened it. The Helm tab no longer shows another cluster's applications. The repository look-over no longer overwrites what you typed. Walking Watson's history no longer jumps. The same backup file can be chosen twice.
- **Replicas and restore.** A replica that stops being leader ends its open streams, so browsers reconnect to the new leader. After a start or failover, the role comparison retries within seconds if nothing could be read yet. A restore keeps a user's name and email when the backup has none, and its settings go through the same checks as the settings pages.
- **Shutdown.** The console waits for Sherlock's answers and Watson's running commands within the pod's termination grace period (20 s by default); what is still running then is stopped and audited. Raise `terminationGracePeriodSeconds` for longer helm upgrades.
- **Chart.** With sign-in off and `localCluster.mode: write`, `localCluster.writeClusterRole` defaults to `minimal`, a role of the chart's own that reads Secrets only with `secrets.read` and holds no impersonation, instead of the built-in `edit`. New `rbac.shared` installs the roles two consoles share on their own, so neither takes them away on uninstall; the install notes say when another release holds them.
- **Release.** A release's chart waits for CI to publish its image. Its linux/amd64 image is the one the checks tested, and linux/arm64 is scanned before it is published. CI builds from pinned base images, and a pull request's `sha-` tag names the merge commit it was built from; builds on a laptop are unchanged.
- **Chart.** An empty `networkPolicy.outboundPorts` is refused rather than opening every port. `networkPolicy.outboundCIDRs` opens the way to a git host with `sherlock.egress` off. New `networkPolicy.ldapCIDRs` narrows the directory's egress, which `outboundCIDRs` no longer does. `service.externalIPs` are let in by the policy. An all-digit `image.tag` renders. With transcripts on a volume of one node, an upgrade replaces the pod rather than stalling. The PodDisruptionBudget lets unhealthy pods be evicted, so a broken console cannot hold up a drain. The read-only install notes say what `kubeletStats` still allows. CI publishes an image only when the two-replica and scale jobs pass too.
- **Access.** Changing a Helm application, its commands or `--app`, and looking over its repository with the saved token, now need rights in that application's namespace, asked of Kubernetes as the person. Revealing a Secret needs Admin in its namespace, or SuperAdmin, and a read-only Admin can no longer reveal. Each person receives only the settings they need, and Sherlock's and Watson's configuration goes to SuperAdmins only, which can no longer be changed through `PUT /api/v1/settings`. Rows for cluster-scoped objects no longer name objects in namespaces the person may not list. The chart refuses Admin and Viewer groups bound in the console's own namespace or the toolbox's.
- **Cards.** Watson's cards are read as the person who asked: what they may not read is left out, and the card says so. A card whose objects cannot be read for any other reason cannot be approved. An install or upgrade card pins its commit and values: the run deploys those or refuses. An empty selector counts as no selector.
- **Applications, limits.** Changing an application's repository removes its saved token unless a new one is given, and the page says so. Repository fetches are limited in size and file count. Chart renders have a timeout, an output limit and a limit on loops. Chart paths are limited to plain path characters, and repository hosts on loopback, link-local and cloud metadata addresses are refused, at save and at every connection. A Helm dry run renders without reading the cluster and masks credentials.
- **Secrets and Sherlock.** More credential forms are masked in release values, rendered release notes are masked, `get_yaml` redacts environment variables as `get_pod` does, `get_helm_release` no longer sends notes, and the scrubbers cover more forms. The rule that cluster text is data applies with view control off and with custom instructions.
- **Sign-in and audit.** New `auth.trustedProxies` says whose X-Forwarded-For the console believes. An address that may stand for many people has a wider limit of its own, and password checks run a few at a time behind a short queue. Fleet and acknowledgement changes made through the settings name their cluster in the audit log. Sign-in, password and first-run forms bound their input, sign-in limits use bounded memory, and the audit store keeps older records when one is too large. A token without the configured username claim is refused, and nested claims work. An access verdict past its age stops applying when reviews fail. The LDAP cleartext check parses the URL's scheme. Secrets from the environment no longer appear in usage messages. A terminal closes when the sign-in that opened it ends. Reading another person's live session output counts as watching, and transcript downloads are audited. A restore records changes to Sherlock's and Watson's settings. A link with `?ask=`, and a home card's Audit and Troubleshoot buttons, put the question in the box for the person to send.
- **Sign-in.** A tab left open no longer keeps a session alive: background refreshes do not count as activity, so a wall display is signed out after `auth.sessionIdle`, and a port forward or shell tied to that sign-in ends with it. Pointer, keys and terminal typing still count.
- **Sherlock's spend.** Answers that were stopped or cut off, and providers that report no usage, now count, from an estimate marked in the audit log, so caps are reached in these cases too. Sherlock's settings say when a provider reports no token use.
- **Several consoles on one node.** Each keeps its own line in `/etc/ssh/221b/ca.pub` and the principals files, and has its own principal, `221b-superadmins-<namespace>.<release>`; unpairing removes only that console's lines. Existing pairings keep the old principal until paired again, and a record with only the old single host key says to pair the node again. Consoles sharing a node trust each other's authority there: sshd does not tie a key to a principal. Two replicas making the authority at once now end up with one key. A pairing's host keys no longer appear in its session's output.
- **Picked nodes.** The Nodes page's picking is the Fleets tab's: the same boxes and bar, *Remove from a fleet…*, and fleets of labels through Watson, plus *Pair for SSH…*. Picks are shared with the Fleets tab and kept across a tab switch, and only SuperAdmins see them. A fleet made from the bar is selected.
- **Audit log page.** It reads the log once and on *Refresh*, and searches in the browser across every kept event. A node's Tools menu reads the server once a minute and still updates at once when a pairing ends. A multi-node card says which node's session could not start, and every session's audit records name its card. A restore keeps as many session records as `toolbox.history.keep`.
- **SSH, pairing.** A failed pairing puts the node's SSH configuration back as it was, an earlier pairing included. Pairing checks with `sshd -T` that sshd really uses the drop-in and listens on the port given, refuses a node that already trusts another SSH authority, and leaves only the new login user's principals file. `Include` goes at the top of `sshd_config`, never under a `Match` block, and no `sshd_config` is written where a system keeps only the vendor's. Socket-activated sshd (Ubuntu 22.10 and later, Flatcar) pairs and unpairs at the first try, and a node with no sshd left can be unpaired.
- **SSH, sessions.** The handshake has a deadline and follows *End*, so a node that takes the connection and says nothing no longer holds a session in *starting* for good; a connection that comes up after the session ended is dropped; a lost connection ends the session as failed, not as a clean exit.
- **SSH, rules.** A read-only SuperAdmin definition turns SSH off with the node shell, in the chart. With `toolbox.nodeShell.approval: always`, an SSH session waits for a second person; pairing respects `toolbox.nodeShell.profiles`. Only pairing takes several nodes: any other tool refuses a request that names more. Upgrading with `--reuse-values` from an earlier release renders, with SSH off.
- **SSH, cards.** The cards of *SSH*, *Pair for SSH* and *Unpair from SSH* say what they do; pairing shows its pod, and refuses a node that is not Ready before anyone approves. With several nodes the first is among the targets.
- **SSH, storage.** The authority is made by the first pairing, not by opening a Tools menu. An unreadable `ssh-pairings.json` is reported and never overwritten. A card of many nodes outlasts the other writers of the settings ConfigMap. A backup now holds the pairings, and a restore can put them back; the authority's private key stays out, and the backup says so.
- **SSH, page.** Viewers and Admins see the SSH items greyed with the reason, like the node shell's. The pairing dialog's fields can be emptied and typed into, and it says which port the network policy opens. The picked-nodes bar goes with the last picked node that leaves the cluster and greys *Pair for SSH…* when SSH is off. An open Tools menu on the Nodes page no longer fetches on every refresh or takes the keyboard back to its first item. Administration › Toolbox says who may use the SSH tools. A pairing session's pane starts with its summary, and the Dock closes with the last session listed.
- **Sherlock.** Closing a block of another language no longer opens a false shell block, which moved lines out of manifests and left an empty box. Commands joined by a backslash are read whole, and tilde fences and unclosed blocks are read as the page reads them. A report with no later text stays as the answer after Stop or a failure. Interim text offers no *Send to Watson*.
- A Sherlock report that the model wrote before reading the cluster once more vanished from the pane while the next round ran; it now stays, dimmed, until the next text replaces it, and is never part of the answer. A line Watson would refuse (a pipe, grep, an unsupported verb) is moved out of an answer's shell block into a text block with the reason, so Send to Watson only ever offers what Watson runs. Sherlock is told how to narrow logs and objects with kubectl's own flags.
- **Security.** `kubectl events -o` took any format, so `-o go-template-file=PATH` printed a file from the server's own disk, the console's token included, to anyone signed in; it now takes the same list as `kubectl get`, which never reads a file.
- **Security.** `--app` with `--git` sent an application's saved token and values to the repository on the line. `--app` now refuses another repository, and only an Admin or SuperAdmin may use it, in a dry run too.
- **Security.** A standing approval outlived its holder: signed out, disabled or out of the directory group, their grant went on approving other people's changes in their name. It is now read again before each approval, runs as the person is then, and ends with their session.
- With two replicas, CPU and memory in use flickered to — on the Helm release page and in the pod and object drawers: a fetch answered by the replica without the page's stream had no usage. Every data request now goes to the leader (P7-09).

### Added

- **Automation** (Phase 11 part 2, ADR-73, docs/automation.md). A new *Automation* tab for SuperAdmins: scripts with a `# 221b:` header, static checks, versions approved once (twice on a two-person cluster), fleet and node parameters, and runs on a fleet's paired nodes over SSH with dry run, batches, a failure limit, reboot and wait, cancel and per-node output. Scripts declaring `privilege none`, and every dry run, run as `nobody`. Needs `toolbox.ssh.enabled`; chart value `automation.enabled` (true) adds the ConfigMap `<release>-automation` (AU-01 to AU-14).
- **SSH to nodes** (Phase 11, ADR-72). A node's Tools menu gains *Pair for SSH…*, *SSH…* and *Unpair from SSH…* for SuperAdmins. Pairing is a node command that installs the console's certificate authority and a principals file for an existing login user on the node and pins the node's host key; a session is a terminal over SSH with a certificate the console signs for that session alone, checked against the pinned host key, and works when the kubelet does not. SSH is off until `toolbox.ssh.enabled` is set, and only then does the chart add an egress rule from the console to the nodes. Chart values `toolbox.ssh.enabled`, `toolbox.ssh.port` and `toolbox.ssh.loginUser`; the authority lives in the Secret `<release>-ssh-ca` (SSH-01 to SSH-07).
- **Administration › Audit log**: the newest 2,000 events the console recorded, who did what and when, searched by words and narrowed by action and outcome, with a JSON download. They are kept beside the settings (`audit-log.json` in the settings ConfigMap), so every replica and a restarted console show them; standard output and the audit webhook stay the full record (M2-01, ADR-71).
- **Administration › Backup**: one JSON file with everything the console keeps of its own (settings, local users, connections, Helm applications, Toolbox session records, Sherlock's spend, the audit log) and never a credential; and a restore of the parts picked from such a file, with a report of what is left to do by hand (M2-06, ADR-71).
- **Commands of a Helm application**: *New command…* in a release's Tools menu saves a named redeploy with its own `--set` parameters; the command is then an item of the menu, with Run, Edit and Delete (M2-07).
- The diff dialog compares any two of: a revision, the source at its deployed branch or tag, the source at any branch or tag (M2-05).
- Sherlock's question box recalls earlier questions with ↑ and ↓, as a shell does (M2-04). Watson's history, which ↑ walks, now holds every command the person ran there, a Redeploy or an application's command included, not only the typed ones.

Each change runs through Watson as you, with a card where the two-person rule applies. A release's panel shows its source and commit, its drift (each object compared with what Helm applied), its values file beside the values as deployed, its history with a diff of any two revisions or of the deployed one against the source and a notice when a newer tag or commit exists, and the images every revision runs. An upgrade moves node shells from `221b-toolbox` to the new namespace; set the value to keep the old name.
- Watson runs `helm install`, `helm upgrade` and `helm uninstall` with a git source (`--git`, `--path`, `--ref`, `--tag`) and an application's saved values (`--app`).


## 0.9.1 (2026-10-27)

The first release since 0.7.1, with Phase 8 (Storage), Phase 9 (Toolbox) and the Phase 9.1 review; there is no 0.8.x or 0.9.0. [docs/upgrading.md](https://github.com/ucesys/221b/blob/v0.9.1/docs/upgrading.md#091) says what an upgrade from 0.7.1 changes.

### Added

- **Toolbox.** A Tools button beside each pod and node opens a shell, forwards a port to your computer, adds a debug container, starts a debug pod, or opens a shell on a node, and cordons, drains or deletes. Each tool asks through a dialog, and its button opens the session as a tab in the dock, at once: it runs as the person who asked, and ends after 10 minutes without activity, at its limit (Extend adds 10 minutes, up to the console's maximum), or when its pod is gone. Cordon runs at once; Drain and Delete ask first; Watson shows them running. On production where the two-person rule is on, another SuperAdmin approves through Watson, since the session opens as the person who asked, with their rights; node shells follow the same rule (`toolbox.nodeShell.approval: always` brings back a second SuperAdmin everywhere). Pods on a node that stopped reporting show Unknown, in a status segment of their own; the Pods segments show only when they have pods. A pod raises a Pending alert only after a grace period, 2 minutes by default, set on the Settings page. Port forwards reach your computer through the new `221b` command, attached to each release; it asks for the forward's token, so the token stays out of your shell's history. Administration gains Sessions (open and ended) and Toolbox (what the chart allows). Sherlock can open a tool's dialog filled in. A debug pod carries no ServiceAccount token unless a SuperAdmin names the account. Chart: a `toolbox` block, `rbac.roles.admin.exec`, and the `221b-toolbox` namespace for node shells; the full Admin role gains port forwards and Jobs, which the Permissions page flags `runs pods`, since a Job may run as any ServiceAccount of its namespace.
- **Storage tab.** Storage classes, persistent volumes and claims, and the pods that mount them, in one table beside a filter sidebar by namespace, node and storage class, as on the Pods tab, with how full each volume is (from the kubelets), a Needs attention filter, and a drawer that traces a claim from its class to its node and says where it breaks. A class has a drawer of its own. Expand a claim, delete a claim, and set or remove the default class through Watson, each after an approval. People bound to namespaces see their claims only. Alerts, the pod drawer and the banner link to it. Full Admin gains `delete` on claims, and the chart's ClusterRole reads VolumeAttachments.
- **Fleets by name.** A fleet can now be a list of nodes kept in 221B, as well as a set of labels and taints. A list changes nothing in the cluster, a node may be on any number of lists, and a new node joins one only when someone adds it; the editor offers both kinds.
- **Fleets: pick nodes and put them in a fleet.** Administrators tick nodes in the matrix, then make a new fleet of them (a list, by default), add them to a fleet or remove them from one, choosing the fleet in the dialog; Cancel drops the picks. For a fleet of labels and taints the dialog lists the `kubectl label` and `kubectl taint` commands, and what else they change (fleets the nodes leave, pods a taint keeps off or evicts), and sends them to Watson, where each waits for approval.
- Watson runs `kubectl taint` on nodes. Its card says what changes and, for NoExecute, which pods are evicted.
- **Alerts by node.** Each pod's alert sits under the node it runs on, below the node's own alert when it has one, and a node whose pods fail comes near the top even when the node itself is fine. Pods that no node took and volumes keep their own sections; By kind shows the alerts as before.

### Changed

- **Tabs open as they were left.** A tab in the bar opens with the filters, selection and sort it had, per cluster, for the rest of the session; a details pane over it is not kept.

- **Sherlock knows the cluster it is asked about.** Its prompt now names the cluster's Kubernetes distribution (RKE2, K3s, kubeadm, kind, EKS, GKE, AKS, OpenShift, Talos), the operating system and kernel of each node, and its network plugin, load balancer, storage and GPU plugin, and gives the guidance for those alone: the distribution's own services, log files and commands, and each operating system's. It troubleshoots down to the node's operating system and hardware, and gives the checks to run on a node in a block of their own. A console with several clusters gives each its own prompt. Node details are included only for people who may list nodes.
- **Namespaces: a tab per kind.** A namespace's kinds are tabs with their counts, as on the Helm tab, Pods first and Helm releases last, in place of a table per kind one under another and the kinds funnel.
- **Alert banners can be hidden.** Settings › General › Alert banners: Hide takes the alert banners off the top of every tab, for everyone; the Alerts tab's name still turns red or amber.
- **Home: figures only, and Storage.** A cluster card's tiles show only their figure: nodes ready, pods ready of those not finished (94/104; completed pods are left out), alerts, and a new Storage tile, claims bound, in place of Namespaces. The health lines no longer say that a node not ready also has errors, and call the pods on a node that stopped reporting Unknown rather than failing to start.
- **Home: Troubleshoot or Audit.** A cluster card's Sherlock button reads Troubleshoot while the cluster has errors or warnings, and asks Sherlock why and how to fix each, most severe first; while it is healthy it reads Audit and asks for the review of its setup, as before.
- Sherlock's prompt is cached for longer: the time comes last, so asking again a minute later costs less.
- Chart: `antiAffinity` (`soft` or `hard`, off by default) keeps several replicas on different nodes: soft prefers it more strongly than the spread the chart already asks for, hard requires it.

- **Nodes and Fleets: All, With problems, With errors.** The Nodes with errors checkbox is now a switch of three: every node, the nodes with an error or a warning (cordoned, under pressure, pods not ready), or only those with an error. Links with err=1 still show the nodes with errors.

### Fixed

- **The Tools menu and its confirmations had no background.** They are drawn outside the table, and took the theme's colours with them only on the page itself.
- **A bound volume's drawer said its claim was none.** It now shows the claim's chain, with the claim as a link back to its drawer; the Volume link in the Storage table opens the volume's drawer and the Claim link the claim's, where both used to open the claim's.
- The filter sidebars of the Pods and Storage tabs no longer show an "only" button on hover; the checkboxes and Select all do the same.
- **The home page counted a cordoned node as not ready.**
- **An acknowledgement took a second or two to show.** It is saved with the settings, and the replica serving the page, when it is not the one that saved it, reads them every 3 seconds. The Alerts tab, its badge and its colour now show it at once, and the server's rows take over when they come.
- **The home page's pod counts did not add up**, and differed from the Pods tab's: "109 pods · 106 running · 10 not ready" counted the not-ready pods among the running ones. The tile now reads "96 running · 10 not ready · 3 completed", and the Pods and Helm tabs have a Not ready status beside Running: pods running but failing a readiness check, or on a node that stopped reporting. The Nodes, Pods and Alerts boxes stay plain when nothing is wrong.
- **Copy buttons copied nothing** when the console is reached over plain HTTP, as at http://<address>: browsers offer their clipboard API only to HTTPS and localhost. Copying now falls back to the older way, which works there too.
- The refresh ring kept the old pace after the refresh rate changed, until the next refresh. It now starts again at the new rate at once, as the server does.
- **"Show me the nodes with problems" showed every node.** Sherlock could not set the Nodes and Fleets tabs' filter or the Alerts tab's Hide acknowledged, so it guessed at taints and search words and then cleared the filters; and with only an errors filter, a node with warnings alone left it no filter that fit. It now shows the nodes with problems, or with errors, as asked, leaves a filtered view empty when nothing matches, and cannot take off a filter it set while the filter shows something.

## 0.6.6 (2026-10-18)
