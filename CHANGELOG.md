# Changelog

What changed in each release of 221B, for people who use it and people who install it. Versions follow [semantic versioning](https://semver.org/): while the major version is 0, a minor version (0.7.0) may change behaviour and chart values, and a patch version (0.7.1) only fixes. [docs/upgrading.md](docs/upgrading.md) says how to upgrade and what each upgrade changes.

## 0.12.0 (unreleased)

Phase 12: AI.

### Added

- **One flow for findings and cases** (CF-01 to CF-87, ADR-126 to ADR-138). Every problem is a case, whether an agent found it or a person reported it: *New* → *In progress* → closed as *Fix* (with an RCA, required at P0 and P1), *Duplicate* (only of an open original; a closed one offers what fits), *Not a problem* (people's cases), *No fix needed*, *Known issue* or *Exception* (agents' cases). A finding of a run becomes a case or joins the one it repeats: an open case counts it *seen ×N*, a known issue records it *still present*, an exception drops it, a fix that did not hold reopens, a later return is a regression. Agents pick their checks from a list per job and see the keys in use, so a problem keeps its name. *New Case* shows similar cases, known issues and recent closes as you type. Priorities run P0 (outage) to P4 (question); agents' cases have an SLA only at P0 and P1. Settings › Cases sets the retention, look-back and caps. Each case is kept in a ConfigMap of its own. Each proposed change names the cases and known issues it resolves; applying it marks their fix, and the next run that no longer finds the problem closes the case as *Fix* (at P0 and P1, once the RCA is added). New agent-found cases at P0–P2 are analysed by themselves, one at a time within the job's budget; a job's lowest priority (P3 by default) keeps lower findings out; closing a case rejects the changes waiting only for it; every case and change names who did each step; cases have a type and an incident number; the Inbox drops its Kind column and acts on many cases at once; a SuperAdmin can hide every cost. Any case may close as a duplicate of an open one; the drawer has one *Close…* with every outcome the case allows; many cases fixed at once share one RCA. An RCA is part of its case only (no Mycroft › RCAs): its fix is what was done, and the Inbox search finds past RCAs by their cause. A case's analysis starts from the earlier cases like it with their RCAs, the open ones like it and the known issues it matches; `ask_knowledge` gives matching known issues too. Only a person puts a case in progress; an agent's analysis leaves it New. A case's drawer opens near full screen with Sherlock and Watson beside the case (tabs on a phone): one Sherlock conversation per case, shared by the people who work it and naming who asked, deleted when the case closes; Watson's commands from the case are logged on it, and it keeps the changes that worked, which start *What was done* when it is fixed and tell a later case like it what fixed this one. **Fixes** (CF-50 to CF-55): closing a case as *Fixed* with *Save fix* (on by default) saves its fix in AIOps › Mycroft › Fixes, one per problem with the cases it fixed, which people edit and which outlive their cases; the agents are given the active ones. A daily *Housekeeping* job makes duplicate fixes, known issues and exceptions inactive and marks contradicting fixes pending, and reports it; the cases closed as Fixed before are imported once. Fixes, Known issues and Exceptions are tables sortable by *Updated*. Proposed changes are numbered **PC-<n>** (old c<n> ids and addresses still work; CF-56). The case drawer has Priority, Type and Assignee at the top, its fields edited in place, the cluster by name from a list, and one shared draft with **Save**, which asks to discard or overwrite when someone saved in between (CF-58 to CF-60). A temporary **ConfigMap wiki store** is the default until Git or S3 is set up (CF-57; chart `knowledge.configMapStore.enabled`). A proposed change opens like a case, with Sherlock and Watson; its Approve became *Run in Watson*, whose card in Watson is the one approval, and Refuse became *Reject* (CF-61, CF-62). The report page lets the reporter pick a priority and a cluster and no longer lists known issues made inactive (CF-63, CF-64). Watson keeps only the newest request active, earlier ones folded away, never discarded (CF-65); the Inbox is wider with Columns and Export above its table (CF-66); a reply moves a case: asking the reporter shows *Waiting for the reporter*, any reply puts a New case In progress (CF-67). The states of every record are drawn in docs/states.md. Mycroft › Exceptions has *New exception*, a separate Cluster line by name, *Justification* and *Created*, *Inactive* in place of Removed with *Make active again*, and filters for Expired and Inactive (CF-68 to CF-70); a check is now called a *validation rule*, shown with its meaning, and AIOps › Jobs › Validation rules (in Mycroft before CF-89) lists them for SuperAdmins to edit, retire, replace and promote from what agents report, with suggestions and exact repeats promoted by the daily housekeeping (CF-71 to CF-75, ADR-138). Every field edited in place shows a pencil; Mycroft's tables share one width; a wiki draft's diff wraps and folds its front matter. Mycroft's sub-tabs share one column and one toolbar layout, their tables one size, an empty one keeping its header (CF-55); New exception suggests the cluster's objects as the person types, those the agents reported first, within what the person may see (CF-76).
- **Backups carry secrets sealed** (BK-15, ADR-137): each install keeps a key in the Secret `<release>-backup-key`, made on first start and kept on uninstall; a backup seals the console's secrets with it (AES-256-GCM) instead of placeholders. Restoring with the same key brings them back; with another key the console asks first, then restores the rest and lists every secret to set and where. A SuperAdmin reads the key from the Secret (Getting started › The backup key); a lost key means the backups' secrets cannot be recovered.
- **The Inbox is one table** (IN-01 to IN-06, ADR-116), as the Nodes and Namespaces pages are: every case, finding, proposed change, approval and draft as a row with its kind, priority, title, cluster, object (linked, with its age), status, how long it has waited and who has it, pending first, then P1 first, then the longest waiting; any column header sorts. Filters on top, kept in the address: *Pending* or *All* (what was closed, completed or decided too, newest first after what is pending), the kind with how many of each are pending, *Mine* or *Unassigned*, priority, cluster and a search. A row opens its drawer at `#/cases/inbox/<kind>/<id>`; *late* says which SLA target passed and links Settings › SLA. Every case is listed, one being analysed too.
- **An Inbox bell in the top bar** (IN-07, CF-80), right of *Live* in every area: red while a P0 or P1 case waits for you, yellow while anything else does, plain otherwise; it opens the Inbox. Alerts an agent's job dealt with are acknowledged by it, with a link to the case (CF-77 to CF-79).
- **This is outdated…** on a wiki page (KN-23, ADR-139): an Admin or a SuperAdmin says what is outdated and what is true now; it becomes a correction under *Added in Mycroft* tied to the page, and Mycroft redrafts that page with it (the correction wins over older sources and is named as one), for review as usual. The page says a correction waits until its redraft is decided; without a model the correction is kept and no page is written. Audited `knowledge.outdated`, never the text.
- **Retire page** on a wiki page (KN-24, ADR-139): a reviewer asks with a reason, and one other reviewer approves it in AIOps › Inbox. A retired page leaves what `ask_knowledge` and every agent read, is listed under the Wiki's *Retired* filter with why, who asked and who approved, and is never deleted or rewritten by Mycroft (its change is held); *Make active again* works the same way. Audited `knowledge.retire.request`, `knowledge.retire`, `knowledge.activate`, `knowledge.retire.reject`.

- **Hosts outside Kubernetes.** A SuperAdmin adds machines that are not nodes (*Add host…* on the Nodes tab), one or many at once, by spaces, tabs, commas or semicolons, each named after its address (and renamed after its hostname once paired, when no node or host has that name) or as `name=address`, with their SSH port and how to pair them: an account's password or private key, kept in the page until the keys are trusted, or a setup command run by hand. Then every host's key is read with no sign-in and listed by fingerprint for one approval, which pins them all and pairs each host with the account in turn (the console runs the nodes' pairing script through `sudo -S`, logs in with its certificate, and keeps the credential nowhere); comparing a key on its host with `ssh-keygen -lf` is optional, and a host that failed is tried again from its row with another account. The setup command is followed by *Check connection*. A paired host is a node for Automation: fleets, runs, facts, variables and its reboot timeout, reached by SSH from the console, back from a reboot once SSH answers from a new boot, never cordoned, drained or counted as control plane. It shows on the Nodes tab tagged *host*; a host that shows another key is refused until a SuperAdmin trusts its key again. Hosts are kept in the settings ConfigMap under `ssh-hosts.json`, and their addresses must be inside `networkPolicy.nodeCIDRs`; the new `networkPolicy.hostPorts` opens other SSH ports. See [docs/automation.md](docs/automation.md#hosts-outside-kubernetes-phase-12).

- **Scheduled backups to S3.** Administration › Backup gains a card, *Scheduled backups to S3*: the bucket, prefix, region and, for MinIO or another S3-compatible store, the endpoint, path-style addresses and a private CA; an access key kept in the Secret `<release>-backup` (never shown again; *Replace…*) or the pod's own AWS identity (IRSA, EKS Pod Identity); a schedule (every day at a time, weekdays, weekly on some days, every N hours, or a cron expression, in a time zone, read back in words with the next times); retention (the newest N, N days, or the bucket's lifecycle rules); SSE-S3 or SSE-KMS, and optionally each file encrypted on the console with AES-256-GCM under a passphrase you hold (`….json.gz.enc`). The leading replica runs it; a time missed while the console was down runs once within the hour, else waits; a time that comes while one runs is let go. The card shows the last runs and a failure, which also goes to the audit log (`backup.s3.run`); *Test connection* puts, reads back and deletes a small object; *Run now*; and the backups in the bucket can be listed and restored with the same choice of parts as a file. The S3 client is the console's own (SigV4, no AWS SDK). Chart: `backup.s3.egressCIDRs` and `backup.s3.egressPorts` open the network policy to the endpoint.
- **A backup holds every part the console's packages register** (ADR-80): each package exports its records with a placeholder for each secret and restores them without putting a placeholder over a secret here; the page lists the parts the server has, and a restore names a part it does not know. Optional parts, such as chat conversations, are taken only when asked (*Include …* on the page, `GET /api/v1/admin/backup?optional=1`). An encrypted backup chosen from the computer is opened by the console with its saved passphrase.

- **Report a problem** (the issue service, docs/issues.md). A page of its own at `/report`, outside the console's tabs: people say what is wrong in their own words, and anything that looks like a password or a token is taken out before it is kept. A report that matches a problem the operators already know about is linked to it at once and told its status, what to do meanwhile, the expected fix and the last update; "No, mine is something else" sends it to investigation instead. *Your reports* shows each with its status, *It works* and *Still broken* on a fixed one, and why a closed one was closed; *Known problems right now* lists the open ones to follow. The page says what changed every half minute. Reports are numbered, prioritized P1 to P4 with response targets, linked to known issues and services, closed with an outcome, reopened within 7 days, and closed by themselves 3 days after a fix nobody answered. Operators (`issues.operatorRoles`, SuperAdmin and Admin by default) triage through the API, `/api/issues/v1/` (docs/issues-api.yaml), which also takes reports from systems with API tokens. A fifth role, **Reporter**, for `issues.reporterGroups` and local groups of the role `reporter`, sees the report page and nothing else. Records live in a new ConfigMap, `<release>-issues`; every report, status change, reply, and token made or revoked is in the audit log. The screens for operators are in Cases (below); the AI investigation comes later.

- **Cases**, a third area beside Kubernetes and Automation for everything that waits for a person, across clusters, with a count on the switch of what waits for you (ADR-88). Not admin-only: it shows to whoever has something in it. **Inbox** puts reports to triage, approvals, agent proposals, findings and drafts of known issues and knowledge in one page, with a chip for each kind and *Mine* and *Unassigned*. **Reports** lists the problem reports with filters (status, open, service, owner, priority, known issue, words), and an operator triages one in a drawer: the reporter's words, the known issues it matches with their confidence, link and unlink, reports alike and duplicates, the service, what the investigation found, the conversation with internal notes and drafts to send, edit or discard, a reply, *Ask for info*, the owner, priority, status and outcome, and *Create known issue from this*, which links the report and its alike. **Known issues** lists them open, resolved or proposed, with an editor for the title, symptoms in users' words, services, status, workaround, expected fix, owner and full page, dated updates (resolving one fixes its reports), *Accept the proposal* and Follow. Someone who may only report sees their own reports and known issues there, read-only. Runs, Jobs and Knowledge are its other tabs.
- **Ways into the report page** from anywhere in 221B, each in a new tab, for whoever may report: *New report* and *On behalf of…* in Cases, *Report a problem* and *My reports* in the account menu, Sherlock's *Report this* when a conversation ends, and *Report this problem* on an error screen or error banner. Sherlock's and the error screens' text is filled in for the person to edit, handed over in the browser and never in the address, and nothing is sent until they press Send (ADR-89). A page that fails to draw now shows an error screen with Reload instead of going blank.
- **Alerts link to reports on the same service:** an alert on what a service runs on shows how many open reports that service has, for operators.
- **AI agents** (Administration › Settings › AI). Sherlock is now the front desk of nine agents, each with one purpose, its own model and only its purpose's tools: the Troubleshooter, the Change planner, the Auditor, the Host doctor, the Automation author, the Script reviewer, Mycroft and the Summarizer. Sherlock hands parts of a question to them (`hand_over`, at most three deep, never the same agent twice, each call charged to the one asked), and the answer shows each as *Sherlock asked the Troubleshooter: …*, opening to what came back, its model and cost. Only Sherlock changes your view. Every agent call is audited (`ai.agent`).
- **Providers.** Any number of providers (Anthropic, OpenAI-compatible, Amazon Bedrock, Google Vertex AI, or a gateway in front of one), each with its credential in a Secret of its own, a default model, prices and a Test. Each agent picks its provider and model, its daily and monthly caps, its clusters and its tools; its spend also counts toward the overall limits. The Script reviewer wants another provider than the Automation author's.
- **Instructions in layers, with a way to live.** Each agent's fixed core, then house instructions (from the chart's new `agents.<agent>.instructions`, or edited in the console, shown *In sync*, *Edited in app* or *Baseline changed*), then notes for every cluster and per cluster. An edit is a draft that is tested on recorded test cases and replays of real answers (its cost shown first), may be piloted for chosen people or clusters, and goes live with a second SuperAdmin's approval on Approvals; every live version is kept and restores in one click. Any answer can be saved as a test case (*Save as test case*, for SuperAdmins).
- **Mycroft's knowledge** (Administration › Settings › Knowledge, AIOps › Knowledge; KN-01 to KN-12, ADR-94 to ADR-96). A SuperAdmin connects Mycroft's sources: Confluence spaces (Cloud with an email and API token, or Data Center with a personal access token), git repositories of runbooks by HTTPS, uploaded documents (markdown, text, Word, HTML and PDF), and what the console itself knows; each credential is kept in the Secret `<release>-knowledge` and shown only as set. Mycroft reads only what changed (a manifest keeps each item's version and hash), with every secret scrubbed and any text that tries to give instructions reported, and writes or updates wiki pages, each claim naming its source with its version and date. The wiki is kept in a git repository (each run on a branch, merged on approval) or an S3 bucket (drafts under a prefix, copied with conditional writes, SSE-S3 or SSE-KMS), chosen in the settings, with *Move the wiki here*. Each run's changes wait in AIOps › Inbox with every page's diff; a critical page (best practices, runbooks) needs two people, and a page someone changed meanwhile waits for a person. Agents read only approved pages: every agent has `ask_knowledge`, which answers from each replica's own copy and keyword index, citing pages with their dates and marking stale ones, then excerpts of the sources. A webhook (`/api/v1/knowledge/hook/…`, with a token) reads the wiki again on a push.
- **An S3 bucket of documents as Mycroft's source** (KN-25, ADR-140): beside Confluence, git repositories and uploads, a SuperAdmin adds a bucket (prefix, region, endpoint and path-style for MinIO, a read-only access key in the knowledge Secret or the pod's identity, private CA); Mycroft reads the documents under the prefix (Markdown, text, Word, PDF, HTML, CSV, up to 20 MiB each, 1000 objects a read), each object's ETag its version, skips and counts the rest, and links each back as `s3://bucket/key`.
- **A Wiki sync job for each of Mycroft's sources** (KN-28, ADR-141): AIOps › Jobs lists *Wiki sync: <source>* for every source, with the usual schedule, pause, budget ($5 a run, $20 a day by default) and *Run now*. A Confluence space is read every 15 minutes for the pages edited since, and whole once a night; a git repository every hour and on each push; an S3 bucket and the console every night; what people add or upload when they do. A source added or changed is read at once as a run of its job; renaming a source renames its job, switching it off pauses it, removing it removes the job (its runs stay). Every sync is a run in Jobs › Runs whose drawer says the source, the items read, unchanged, gone and skipped, the drafts with a link to AIOps › Inbox, the proposals, the errors, tokens and cost. The jobs *Knowledge sync* and *Knowledge sync: pages edited since the last read* are gone; existing installs get the per-source jobs at start.
- **Mycroft knows the known issues, exceptions and fixes** (KN-32 to KN-34, ADR-144): `ask_knowledge` gives, after the wiki's pages, the open known issues a question matches (by the objects it names, then by their words) with status, workaround, expected fix and affected objects, and, to who may read them (never for a reporter), the active exceptions with their rule, justification and last day. Mycroft's page drafts are given the active fixes on the same subject: a page that agrees names the fix as a source, one that contradicts it is flagged on the review card (*Contradicts F-3, used in 4 cases*) and in the run's report.
- **A proven fix becomes a runbook draft** (KN-34): a new source *Fixes*, there from the start: the daily housekeeping offers Mycroft each active fix seen in 3 cases or more that no runbook draws on, once and again when it changes; Mycroft drafts a runbook for two approvers, and the fix's drawer links the page once approved.
- **Rebuild now** (KN-29): a Wiki sync job's drawer has *Rebuild now…* beside *Run now*: after you confirm, Mycroft gets every item of the source again, unchanged ones too, and redrafts the pages. Use it after a sync that failed, or after changing Mycroft's model or instructions.
- **Test in the source dialog** (KN-26): *Test* moved from a source's row into its *New source* / *Edit…* dialog and tests the values as typed, before they are saved (`POST /api/v1/knowledge/sources/test`); on Edit a credential left blank is the saved one, read on the server and never sent back. The result stays under the button until a field changes: what it reached and what it skips, or the error, plainly, naming host:port and what to check (connect within 10 s, the whole test within 30 s). No audit record, no credential in the answer.
- **Settings › Knowledge starts no sync** (KN-28): *Sync now*, each source's *Sync*, the sync status line and the last sync's history are gone; a line links AIOps › Jobs, each source links its Wiki sync job, and a source's error is shown whole. `POST /api/v1/knowledge/sync` is removed.
- **Add only in Settings › Knowledge** (MY-11): a note, a web address or documents are added in Settings › Knowledge's *Added in Mycroft* card, with what was added; AIOps › Mycroft › Wiki has no *Add* view, and its old address opens the card. An Admin, for whom the rest of Settings stays closed, finds the card alone there.
- **Inventory and drift proposals** (KN-19, ADR-98): the hosts a document lists that the console lacks, and each difference between the documents and what the console sees, are proposed as cards; none holds a credential or a host key.
- **Inventory proposals match the live cluster** (KN-30, ADR-143): a group of hosts a document names is proposed as a fleet only when its labels select nodes now and not the same nodes as a fleet you have; each group left out is listed under *Not proposed* in the sync's report, with why. A fleet proposal says its members now (*3 nodes now: rke2cp1, rke2cp2, rke2cp3*), and *Check again* warns when a proposed fleet would be empty.
- **Drift respects known issues and exceptions** (KN-31, ADR-143): each kind of inventory and drift difference is a validation rule (`inventory.host-unreachable`, `inventory.address-differs`, `inventory.host-unlisted`, `inventory.host-missing`, `inventory.fleet-missing`, under *Drift check* in Validation rules); a difference an active exception for its cluster, host and rule covers, or an open known issue about the host, is not proposed, and the run's report says which (*covered by KI-3*, *accepted as-is by EX-4*).
- **Known issues in Confluence** (Settings › Issues › Confluence; KN-13 to KN-18, ADR-97): a Status page grouped by service, one page per known issue and a resolved archive by month, kept current through an outbox that retries while Confluence is down; each page has a part the console rewrites and a Notes part people edit, and a person's edit inside the first is never overwritten but waits for the owner to keep or replace it. A nightly check repairs or reports differences, never deletes a page, and imports a page written by hand under the tree as a draft known issue. Approved wiki pages can be published read-only beside them. Reporters' names, report text, namespaces, hostnames and unapproved agent text never reach Confluence.
- **Jobs: agents on their own** (AIOps › Jobs and Runs, ADR-90 to ADR-93). Jobs start an agent with nobody at the screen, for read-only work: the Auditor's *Nightly audit* (new RBAC risks, volumes nearly full, practices not met), the Troubleshooter's *Alert diagnosis* of each new alert (warning and above, or errors only; a repeat of the same alert updates its run instead of running again) and *Report triage* of each new report, and the Summarizer's *Daily digest* of the last day's audit log and runs. Each is off until a SuperAdmin turns it on, with its clusters, a schedule (every day, weekdays, weekly, every N hours or cron, in a time zone, read back in words with its next times) or an event, and a budget per run and per day; it stops when either is spent and says so. A schedule runs once, on the leading replica; a time missed while the console was down runs once within the hour; a run still going makes the next skip. *Run now*, *Pause* and each job's runs are in its drawer; *Add job…* adds another of a kind. *Backup to S3* is listed too, with Run now and Pause. Every change is audited with its old and new values, and every run with the agent, who set the trigger, what it found and proposed and its cost.
- **Runs and findings.** AIOps › Jobs › Runs lists every run with its report, findings, proposals, tokens and cost, kept in the new ConfigMap `<release>-runs`. Findings stay in AIOps › Inbox until someone makes a case of them or ignores them. A change an agent proposes is a proposal that waits for a person; nothing a job does changes anything.
- **Findings have a priority, New Case and Ignore** (FX-01 to FX-07, ADR-108). A finding starts at its severity's priority (since wave 5 critical P2, warning P4, info P5), which an approver changes. *New Case* makes a case of it; *Ignore* asks why and, optionally, until when, and records an accepted exception in Knowledge: later runs leave out a finding of the same check on the same resource, their agents are told about it, and the run says how many it left out. The agents now give each finding a short `check` id. Findings acknowledged or dismissed before stay as they were.
- **Exceptions and RCAs in Mycroft** (FX-08 to FX-11, ADR-110, MY-09). AIOps › Mycroft lists the accepted exceptions (with why, where, who, the expiry, and *Remove* for approvers) and the RCAs cases are completed with. Both are kept with the cases and in backups; RCAs are written to Mycroft's wiki as approved pages when it has a store, where every agent reads them through `ask_knowledge`, while exceptions stay the console's records, told to the agents in their task.
- **AIOps › Mycroft** (MY-01 to MY-10, ADR-118, ADR-119): one tab for what the console knows, with the sub-tabs *Wiki*, *Known issues*, *Exceptions* and *RCAs*, each with its address (the old Knowledge and Known issues addresses lead there). The Wiki has *Pages*, *Drafts*, *Sources* (what Mycroft reads and what people added) and **Add**: an Admin or a SuperAdmin adds a note (up to 200 KiB), a web address, read with the pages of its site it links to (1 to 3 links deep, up to 50 pages, robots.txt obeyed, never another site or an address inside the pod), or documents (PDF, Word, Markdown, HTML, plain text and CSV, up to 20 MiB each). What is added is scrubbed of secrets, quoted by the agents once read, and written up by Mycroft as pages that wait for review. With no wiki store the Wiki says so and offers the setup, where it showed *Loading…* for good (the server answered no pages as `null`).
- **Cancel a run** (FX-12, ADR-109): a run under way has *Cancel run* for job editors and SuperAdmins; it ends *cancelled*, with who cancelled it, keeping what it found and counting what it spent.
- **Agents on their own read as `221b:agents`**, never as a person, with the role Settings › Jobs chooses: Viewer (the default, with the namespaces bound to that user or those of a chosen Viewer group) or SuperViewer. Settings › Jobs also says who may edit jobs besides SuperAdmins.
- **Reports are investigated** by the Troubleshooter when the *Report triage* job is on: the likely service and how sure, the cause, the evidence, a technical summary and a plain one for the reporter; a known issue it proposes waits as a draft, a fix as a proposal, and a fix marked done is checked again. The report's text reaches it as untrusted data. Report work has its own daily budget.

- **Agents' proposals wait as durable Watson cards** (ADR-99 to ADR-102). Every change an agent wants, asked in a chat or on its own, is a card in AIOps › Inbox and the cluster's Watson panel, kept in a new ConfigMap, `<release>-cases`, so it outlives a restart: what started it and who set the trigger, the agent and its model, why, the evidence with its dates, the exact commands or console changes with their impact and risk, and when it expires (24 hours, or when its alert resolves). A newer proposal for the same thing replaces the older. Approving needs the approval permission (`cases.approverRoles`, SuperAdmin and Admin by default), not admin rights; Watson checks again that the condition holds and the target has not changed since, and says why when it cannot be approved as it stands; on production, with the two-person rule, an agent's change needs two people. Approved cards run through Watson as the last approver, and the audit log names the agent, model, trigger and approvers. A change Sherlock proposed that you send to Watson is kept as a card too.
- **Watson's console actions**: adding, labelling and removing hosts outside Kubernetes (an added host waits as pending until a person pairs it in Add host; a card never carries a host key or a credential), creating and changing fleets of either kind, and Automation parameters and per-node values, each a SuperAdmin's to approve.
- **Getting started** (Administration › Settings › Getting started, and a card on the home page; GS-01 to GS-06, ADR-103). A checklist for SuperAdmins of setting the console up, in nine steps: sign-in, clusters, an AI provider and default model, agents with budgets, Mycroft's sources, jobs and notifications, fleets, SSH and hosts outside Kubernetes, and a first backup. Each step is checked against the console every time the list is read, never ticked by hand, says what is missing and why it comes where it does, and links to the screen where it is done. A step that does not apply can be dismissed and brought back, each audited (`setup.dismiss`); the card leaves the home page once every step is done or dismissed. See [docs/getting-started.md](docs/getting-started.md).
- **Sherlock's setup skill** (GS-07 to GS-10, ADR-104): while a step is open, a SuperAdmin's Sherlock shows a *setup* tag and can read the checklist with a new read-only tool, `setup_status`. It answers *What's next?* (what is left, in order, and why), links to the step's screen and names the field to use, explains choices (which model for the Auditor, what acting on its own costs, which role an agent on its own reads with) from the docs and Mycroft's best-practice pages, and never asks for a password, key or token: those are typed on the screen. The skill leaves Sherlock's instructions once every step is done or dismissed; three shipped test cases cover it.
- **Mycroft's first import** (GS-11): a source added in Settings › Knowledge is read at once, and the hosts its documents list, with the labels they give them, and the groups of hosts they name, as fleets of those labels, are proposed in one card per document in AIOps › Inbox. Fleets the console has are not proposed again.

A release's image and chart are never replaced by a rerun. [docs/releasing.md](docs/releasing.md#verify-a-release) says how to check them.
- **Delete a Secret.** A Secret's page has *Delete…* for those who may edit it: it asks first, then hands `kubectl delete secret NAME -n NAMESPACE` to Watson, whose card says what goes (its keys), which pods read it, which Ingress serves TLS from it, and when it is a Helm release record or a service account token, with a server dry run before anyone approves. The card never holds a value.
- **Console.** A log line longer than 1 MiB is split into pieces and no longer ends a followed log. A pod failed as a whole (Evicted, OutOfcpu, NodeAffinity) shows red with its status message and raises an alert. Restarts and last restart count init containers and sidecars as `kubectl get pods` does. A Job that failed after some pods succeeded reads failed, and a Job between pods no longer flashes green. A volume claim no longer raises an alert because another volume's name contains its name. An Ingress using a generic Secret with `tls.crt` and `tls.key` shows its certificate. The rollout check matches ResourceQuotas scoped to a PriorityClass. A ServiceAccount whose name contains its namespace keeps its long-lived tokens on the Access tab. A CA certificate pasted while editing a connection is honoured on save and on Test.
- **Large clusters.** Volume usage is read in its own time and kept when the read runs long, pods' CPU and memory no longer blank when a read runs out of time, and the Policies and Networks tabs no longer stall the console on namespaces with many pods and budgets or clusters with many Ingress routes.
- **Audit.** Records for Secrets, namespaces and applications name the cluster, and refused or failed attempts are recorded as denied or failed, not ok. Stopping a queued command is recorded, and a stop is credited to the person who pressed it. The Audit log page's "kept in memory" notice shows again where there is no settings ConfigMap.
- **Applications.** A save made during a long upgrade is no longer overwritten when it ends, and two saves that collide give a conflict message. `helm install` or `helm upgrade` with `--git` but no `--app` keeps the record's values, parameters, commands and fleet; moving to another repository removes the saved token. `--set` on a Watson line, a saved command's parameters included, applies to that deploy only and no longer joins the saved parameters. A chart with an enabled dependency not vendored under `charts/` is refused with a message.
- **Watson and Sherlock.** A comma list of types shows its targets and guards on the card. *Approve all for…* no longer grants on selection: choose a length, then press *Approve all*. With one custom price set, the other counts at the highest listed price, so caps no longer under-count. Sherlock's Undo no longer mixes up answers from different clusters, and its view changes report back from a hidden window.
- **Sessions.** A pod or Job created while its session is being ended is removed. Extend now really extends a node shell or debug pod. A forward whose connection to the pod died dials again. Terminals no longer freeze while a check waits on a slow directory, and a terminal no longer takes the keyboard from a field or dialog. A session's transcript can be downloaded for as long as the file is kept, not only while the session is in memory. With the CLI, the end of a response is no longer lost when the program reads slowly, and a client that half-closes still gets the answer.
- **Secrets.** A key left on *Replace* with nothing typed can no longer be saved empty. Saving a Secret someone changed after you opened it is refused with a plain message instead of overwriting them. The Namespaces tab's Secret controls follow the cluster you are on.
- **Page.** A tool's dialog stays on the cluster it was opened on. A link in the assistants' window opens only in the main window it follows, and a minimised assistants' window no longer sends Sherlock and Watson back into the main one. A followed pod log that reconnects no longer shows lines twice. Long tables keep drawing rows after crossing the small-screen width. Closing a drawer returns focus to what opened it. The Helm tab no longer shows another cluster's applications. The repository look-over no longer overwrites what you typed. Walking Watson's history no longer jumps. The same backup file can be chosen twice.
- **Replicas and restore.** A replica that stops being leader ends its open streams, so browsers reconnect to the new leader. After a start or failover, the role comparison retries within seconds if nothing could be read yet. A restore keeps a user's name and email when the backup has none, and its settings go through the same checks as the settings pages.
- **Shutdown.** The console waits for Sherlock's answers and Watson's running commands within the pod's termination grace period (20 s by default); what is still running then is stopped and audited. Raise `terminationGracePeriodSeconds` for longer helm upgrades.
- **Chart.** With sign-in off and `localCluster.mode: write`, `localCluster.writeClusterRole` defaults to `minimal`, a role of the chart's own that reads Secrets only with `secrets.read` and holds no impersonation, instead of the built-in `edit`. New `rbac.shared` installs the roles two consoles share on their own, so neither takes them away on uninstall; the install notes say when another release holds them.
- **Release.** A release's chart waits for CI to publish its image. Its linux/amd64 image is the one the checks tested, and linux/arm64 is scanned before it is published. CI builds from pinned base images, and a pull request's `sha-` tag names the merge commit it was built from; builds on a laptop are unchanged.
- **Chart.** An empty `networkPolicy.outboundPorts` is refused rather than opening every port. `networkPolicy.outboundCIDRs` opens the way to a git host with `sherlock.egress` off. New `networkPolicy.ldapCIDRs` narrows the directory's egress, which `outboundCIDRs` no longer does. `service.externalIPs` are let in by the policy. An all-digit `image.tag` renders. With transcripts on a volume of one node, an upgrade replaces the pod rather than stalling. The PodDisruptionBudget lets unhealthy pods be evicted, so a broken console cannot hold up a drain. The read-only install notes say what `kubeletStats` still allows. CI publishes an image only when the two-replica and scale jobs pass too.
- **Access.** Changing a Helm application, its commands or `--app`, and looking over its repository with the saved token, now need rights in that application's namespace, asked of Kubernetes as the person. Revealing a Secret needs Admin in its namespace, or SuperAdmin, and a read-only Admin can no longer reveal. Each person receives only the settings they need, and Sherlock's and Watson's configuration goes to SuperAdmins only, which can no longer be changed through `PUT /api/v1/settings`. Rows for cluster-scoped objects no longer name objects in namespaces the person may not list. The chart refuses Admin and Viewer groups bound in the console's own namespace or the toolbox's.
- **Cards.** Watson's cards are read as the person who asked: what they may not read is left out, and the card says so. A card whose objects cannot be read for any other reason cannot be approved. An install or upgrade card pins its commit and values: the run deploys those or refuses. An empty selector counts as no selector.
- **Applications, limits.** Changing an application's repository removes its saved token unless a new one is given, and the page says so. Repository fetches are limited in size and file count. Chart renders have a timeout, an output limit and a limit on loops. Chart paths are limited to plain path characters, and repository hosts on loopback, link-local and cloud metadata addresses are refused, at save and at every connection. A Helm dry run renders without reading the cluster and masks credentials.
- **Secrets and Sherlock.** More credential forms are masked in release values, rendered release notes are masked, `get_yaml` redacts environment variables as `get_pod` does, `get_helm_release` no longer sends notes, and the scrubbers cover more forms. The rule that cluster text is data applies with view control off and with custom instructions.
- **Sign-in and audit.** New `auth.trustedProxies` says whose X-Forwarded-For the console believes. An address that may stand for many people has a wider limit of its own, and password checks run a few at a time behind a short queue. Fleet and acknowledgement changes made through the settings name their cluster in the audit log. Sign-in, password and first-run forms bound their input, sign-in limits use bounded memory, and the audit store keeps older records when one is too large. A token without the configured username claim is refused, and nested claims work. An access verdict past its age stops applying when reviews fail. The LDAP cleartext check parses the URL's scheme. Secrets from the environment no longer appear in usage messages. A terminal closes when the sign-in that opened it ends. Reading another person's live session output counts as watching, and transcript downloads are audited. A restore records changes to Sherlock's and Watson's settings. A link with `?ask=`, and a home card's Audit and Troubleshoot buttons, put the question in the box for the person to send.
- **Sign-in.** A tab left open no longer keeps a session alive: background refreshes do not count as activity, so a wall display is signed out after `auth.sessionIdle`, and a port forward or shell tied to that sign-in ends with it. Pointer, keys and terminal typing still count.
- **Sherlock's spend.** Answers that were stopped or cut off, and providers that report no usage, now count, from an estimate marked in the audit log, so caps are reached in these cases too. Sherlock's settings say when a provider reports no token use.
- **Several consoles on one node.** Each keeps its own line in `/etc/ssh/221b/ca.pub` and the principals files, and has its own principal, `221b-superadmins-<namespace>.<release>`; unpairing removes only that console's lines. Existing pairings keep the old principal until paired again, and a record with only the old single host key says to pair the node again. Consoles sharing a node trust each other's authority there: sshd does not tie a key to a principal. Two replicas making the authority at once now end up with one key. A pairing's host keys no longer appear in its session's output.
- **Picked nodes.** The Nodes page's picking is the Fleets tab's: the same boxes and bar, *Remove from a fleet…*, and fleets of labels through Watson, plus *Pair for SSH…*. Picks are shared with the Fleets tab and kept across a tab switch, and only SuperAdmins see them. A fleet made from the bar is selected.
- **Audit log page.** It reads the log once and on *Refresh*, and searches in the browser across every kept event. A node's Tools menu reads the server once a minute and still updates at once when a pairing ends. A multi-node card says which node's session could not start, and every session's audit records name its card. A restore keeps as many session records as `toolbox.history.keep`.
- **SSH, pairing.** A failed pairing puts the node's SSH configuration back as it was, an earlier pairing included. Pairing checks with `sshd -T` that sshd really uses the drop-in and listens on the port given, refuses a node that already trusts another SSH authority, and leaves only the new login user's principals file. `Include` goes at the top of `sshd_config`, never under a `Match` block, and no `sshd_config` is written where a system keeps only the vendor's. Socket-activated sshd (Ubuntu 22.10 and later, Flatcar) pairs and unpairs at the first try, and a node with no sshd left can be unpaired.
- **SSH, sessions.** The handshake has a deadline and follows *End*, so a node that takes the connection and says nothing no longer holds a session in *starting* for good; a connection that comes up after the session ended is dropped; a lost connection ends the session as failed, not as a clean exit.
- **SSH, rules.** A read-only SuperAdmin definition turns SSH off with the node shell, in the chart. With `toolbox.nodeShell.approval: always`, an SSH session waits for a second person; pairing respects `toolbox.nodeShell.profiles`. Only pairing takes several nodes: any other tool refuses a request that names more. Upgrading with `--reuse-values` from an earlier release renders, with SSH off.
- **SSH, cards.** The cards of *SSH*, *Pair for SSH* and *Unpair from SSH* say what they do; pairing shows its pod, and refuses a node that is not Ready before anyone approves. With several nodes the first is among the targets.
- **SSH, storage.** The authority is made by the first pairing, not by opening a Tools menu. An unreadable `ssh-pairings.json` is reported and never overwritten. A card of many nodes outlasts the other writers of the settings ConfigMap. A backup now holds the pairings, and a restore can put them back; the authority's private key stays out, and the backup says so.
- **SSH, page.** Viewers and Admins see the SSH items greyed with the reason, like the node shell's. The pairing dialog's fields can be emptied and typed into, and it says which port the network policy opens. The picked-nodes bar goes with the last picked node that leaves the cluster and greys *Pair for SSH…* when SSH is off. An open Tools menu on the Nodes page no longer fetches on every refresh or takes the keyboard back to its first item. Administration › Toolbox says who may use the SSH tools. A pairing session's pane starts with its summary, and the Dock closes with the last session listed.
- **Sherlock.** Closing a block of another language no longer opens a false shell block, which moved lines out of manifests and left an empty box. Commands joined by a backslash are read whole, and tilde fences and unclosed blocks are read as the page reads them. A report with no later text stays as the answer after Stop or a failure. Interim text offers no *Send to Watson*.
- A Sherlock report that the model wrote before reading the cluster once more vanished from the pane while the next round ran; it now stays, dimmed, until the next text replaces it, and is never part of the answer. A line Watson would refuse (a pipe, grep, an unsupported verb) is moved out of an answer's shell block into a text block with the reason, so Send to Watson only ever offers what Watson runs. Sherlock is told how to narrow logs and objects with kubectl's own flags.
- **Security.** `kubectl events -o` took any format, so `-o go-template-file=PATH` printed a file from the server's own disk, the console's token included, to anyone signed in; it now takes the same list as `kubectl get`, which never reads a file.
- **Security.** `--app` with `--git` sent an application's saved token and values to the repository on the line. `--app` now refuses another repository, and only an Admin or SuperAdmin may use it, in a dry run too.
- **Security.** A standing approval outlived its holder: signed out, disabled or out of the directory group, their grant went on approving other people's changes in their name. It is now read again before each approval, runs as the person is then, and ends with their session.
- With two replicas, CPU and memory in use flickered to — on the Helm release page and in the pod and object drawers: a fetch answered by the replica without the page's stream had no usage. Every data request now goes to the leader (P7-09).

### Added

- **Automation** (Phase 11 part 2, ADR-73, docs/automation.md). A new *Automation* tab for SuperAdmins: scripts with a `# 221b:` header, static checks, versions approved once (twice on a two-person cluster), fleet and node parameters, and runs on a fleet's paired nodes over SSH with dry run, batches, a failure limit, reboot and wait, cancel and per-node output. Scripts declaring `privilege none`, and every dry run, run as `nobody`. Needs `toolbox.ssh.enabled`; chart value `automation.enabled` (true) adds the ConfigMap `<release>-automation` (AU-01 to AU-14).
- **SSH to nodes** (Phase 11, ADR-72). A node's Tools menu gains *Pair for SSH…*, *SSH…* and *Unpair from SSH…* for SuperAdmins. Pairing is a node command that installs the console's certificate authority and a principals file for an existing login user on the node and pins the node's host key; a session is a terminal over SSH with a certificate the console signs for that session alone, checked against the pinned host key, and works when the kubelet does not. SSH is off until `toolbox.ssh.enabled` is set, and only then does the chart add an egress rule from the console to the nodes. Chart values `toolbox.ssh.enabled`, `toolbox.ssh.port` and `toolbox.ssh.loginUser`; the authority lives in the Secret `<release>-ssh-ca` (SSH-01 to SSH-07).
- **Administration › Audit log**: the newest 2,000 events the console recorded, who did what and when, searched by words and narrowed by action and outcome, with a JSON download. They are kept beside the settings (`audit-log.json` in the settings ConfigMap), so every replica and a restarted console show them; standard output and the audit webhook stay the full record (M2-01, ADR-71).
- **Administration › Backup**: one JSON file with everything the console keeps of its own (settings, local users, connections, Helm applications, Toolbox session records, Sherlock's spend, the audit log) and never a credential; and a restore of the parts picked from such a file, with a report of what is left to do by hand (M2-06, ADR-71).
- **Commands of a Helm application**: *New command…* in a release's Tools menu saves a named redeploy with its own `--set` parameters; the command is then an item of the menu, with Run, Edit and Delete (M2-07).
- The diff dialog compares any two of: a revision, the source at its deployed branch or tag, the source at any branch or tag (M2-05).
- Sherlock's question box recalls earlier questions with ↑ and ↓, as a shell does (M2-04). Watson's history, which ↑ walks, now holds every command the person ran there, a Redeploy or an application's command included, not only the typed ones.

## 0.9.1 (2026-10-27)

The first release since 0.7.1, with Phase 8 (Storage), Phase 9 (Toolbox) and the Phase 9.1 review; there is no 0.8.x or 0.9.0. [docs/upgrading.md](https://github.com/ucesys/221b/blob/v0.9.1/docs/upgrading.md#091) says what an upgrade from 0.7.1 changes.

### Added

- **Toolbox.** A Tools button beside each pod and node opens a shell, forwards a port to your computer, adds a debug container, starts a debug pod, or opens a shell on a node, and cordons, drains or deletes. Each tool asks through a dialog, and its button opens the session as a tab in the dock, at once: it runs as the person who asked, and ends after 10 minutes without activity, at its limit (Extend adds 10 minutes, up to the console's maximum), or when its pod is gone. Cordon runs at once; Drain and Delete ask first; Watson shows them running. On production where the two-person rule is on, another SuperAdmin approves through Watson, since the session opens as the person who asked, with their rights; node shells follow the same rule (`toolbox.nodeShell.approval: always` brings back a second SuperAdmin everywhere). Pods on a node that stopped reporting show Unknown, in a status segment of their own; the Pods segments show only when they have pods. A pod raises a Pending alert only after a grace period, 2 minutes by default, set on the Settings page. Port forwards reach your computer through the new `221b` command, attached to each release; it asks for the forward's token, so the token stays out of your shell's history. Administration gains Sessions (open and ended) and Toolbox (what the chart allows). Sherlock can open a tool's dialog filled in. A debug pod carries no ServiceAccount token unless a SuperAdmin names the account. Chart: a `toolbox` block, `rbac.roles.admin.exec`, and the `221b-toolbox` namespace for node shells; the full Admin role gains port forwards and Jobs, which the Permissions page flags `runs pods`, since a Job may run as any ServiceAccount of its namespace.
- **Storage tab.** Storage classes, persistent volumes and claims, and the pods that mount them, in one table beside a filter sidebar by namespace, node and storage class, as on the Pods tab, with how full each volume is (from the kubelets), a Needs attention filter, and a drawer that traces a claim from its class to its node and says where it breaks. A class has a drawer of its own. Expand a claim, delete a claim, and set or remove the default class through Watson, each after an approval. People bound to namespaces see their claims only. Alerts, the pod drawer and the banner link to it. Full Admin gains `delete` on claims, and the chart's ClusterRole reads VolumeAttachments.
- **Fleets by name.** A fleet can now be a list of nodes kept in 221B, as well as a set of labels and taints. A list changes nothing in the cluster, a node may be on any number of lists, and a new node joins one only when someone adds it; the editor offers both kinds.
- **Fleets: pick nodes and put them in a fleet.** Administrators tick nodes in the matrix, then make a new fleet of them (a list, by default), add them to a fleet or remove them from one, choosing the fleet in the dialog; Cancel drops the picks. For a fleet of labels and taints the dialog lists the `kubectl label` and `kubectl taint` commands, and what else they change (fleets the nodes leave, pods a taint keeps off or evicts), and sends them to Watson, where each waits for approval.
- Watson runs `kubectl taint` on nodes. Its card says what changes and, for NoExecute, which pods are evicted.
- **Alerts by node.** Each pod's alert sits under the node it runs on, below the node's own alert when it has one, and a node whose pods fail comes near the top even when the node itself is fine. Pods that no node took and volumes keep their own sections; By kind shows the alerts as before.

### Changed

- **Tabs open as they were left.** A tab in the bar opens with the filters, selection and sort it had, per cluster, for the rest of the session; a details pane over it is not kept.

- **Sherlock knows the cluster it is asked about.** Its prompt now names the cluster's Kubernetes distribution (RKE2, K3s, kubeadm, kind, EKS, GKE, AKS, OpenShift, Talos), the operating system and kernel of each node, and its network plugin, load balancer, storage and GPU plugin, and gives the guidance for those alone: the distribution's own services, log files and commands, and each operating system's. It troubleshoots down to the node's operating system and hardware, and gives the checks to run on a node in a block of their own. A console with several clusters gives each its own prompt. Node details are included only for people who may list nodes.
- **Namespaces: a tab per kind.** A namespace's kinds are tabs with their counts, as on the Helm tab, Pods first and Helm releases last, in place of a table per kind one under another and the kinds funnel.
- **Alert banners can be hidden.** Settings › General › Alert banners: Hide takes the alert banners off the top of every tab, for everyone; the Alerts tab's name still turns red or amber.
- **Home: figures only, and Storage.** A cluster card's tiles show only their figure: nodes ready, pods ready of those not finished (94/104; completed pods are left out), alerts, and a new Storage tile, claims bound, in place of Namespaces. The health lines no longer say that a node not ready also has errors, and call the pods on a node that stopped reporting Unknown rather than failing to start.
- **Home: Troubleshoot or Audit.** A cluster card's Sherlock button reads Troubleshoot while the cluster has errors or warnings, and asks Sherlock why and how to fix each, most severe first; while it is healthy it reads Audit and asks for the review of its setup, as before.
- Sherlock's prompt is cached for longer: the time comes last, so asking again a minute later costs less.
- Chart: `antiAffinity` (`soft` or `hard`, off by default) keeps several replicas on different nodes: soft prefers it more strongly than the spread the chart already asks for, hard requires it.

- **Nodes and Fleets: All, With problems, With errors.** The Nodes with errors checkbox is now a switch of three: every node, the nodes with an error or a warning (cordoned, under pressure, pods not ready), or only those with an error. Links with err=1 still show the nodes with errors.

### Fixed

- **The Tools menu and its confirmations had no background.** They are drawn outside the table, and took the theme's colours with them only on the page itself.
- **A bound volume's drawer said its claim was none.** It now shows the claim's chain, with the claim as a link back to its drawer; the Volume link in the Storage table opens the volume's drawer and the Claim link the claim's, where both used to open the claim's.
- The filter sidebars of the Pods and Storage tabs no longer show an "only" button on hover; the checkboxes and Select all do the same.
- **The home page counted a cordoned node as not ready.**
- **An acknowledgement took a second or two to show.** It is saved with the settings, and the replica serving the page, when it is not the one that saved it, reads them every 3 seconds. The Alerts tab, its badge and its colour now show it at once, and the server's rows take over when they come.
- **The home page's pod counts did not add up**, and differed from the Pods tab's: "109 pods · 106 running · 10 not ready" counted the not-ready pods among the running ones. The tile now reads "96 running · 10 not ready · 3 completed", and the Pods and Helm tabs have a Not ready status beside Running: pods running but failing a readiness check, or on a node that stopped reporting. The Nodes, Pods and Alerts boxes stay plain when nothing is wrong.
- **Copy buttons copied nothing** when the console is reached over plain HTTP, as at http://<address>: browsers offer their clipboard API only to HTTPS and localhost. Copying now falls back to the older way, which works there too.
- The refresh ring kept the old pace after the refresh rate changed, until the next refresh. It now starts again at the new rate at once, as the server does.
- **"Show me the nodes with problems" showed every node.** Sherlock could not set the Nodes and Fleets tabs' filter or the Alerts tab's Hide acknowledged, so it guessed at taints and search words and then cleared the filters; and with only an errors filter, a node with warnings alone left it no filter that fit. It now shows the nodes with problems, or with errors, as asked, leaves a filtered view empty when nothing matches, and cannot take off a filter it set while the filter shows something.

## 0.7.0 (2026-10-20)

### Added

- **Several replicas** (P7-02): `replicaCount: 2` or more, with a PodDisruptionBudget. One replica, chosen through a Kubernetes Lease, runs Sherlock and Watson, and the others pass those requests to it; sign-ins, settings and accounts are shared, so losing a replica costs a viewer a reconnect.
- **Upgrades from the two previous releases** (P7-03) are tested in CI: upgrade, roll back and upgrade again, keeping settings, users, connections and Sherlock's key. Stored settings and local accounts carry a format version; a console migrates older formats, keeps fields it does not know when it saves, and refuses to overwrite a format newer than it knows.
- **Releases** (P7-08): semantic versions, this changelog, the chart published to `oci://ghcr.io/ucesys/charts/221b`, and a GitHub release for every version tag ([docs/releasing.md](docs/releasing.md)). A contributing guide, a code of conduct, a security policy, issue and pull request templates, and a Developer Certificate of Origin check for pull requests from forks.

### Changed

- Everyone signs in once more after upgrading to 0.7.0: sign-ins used to live in the console's memory and are now kept in the cluster, where they survive restarts and upgrades.

### Fixed

- Sherlock on the home page and on a connection's page: *Send to Watson* shows under a command, and a cited object (*Open deployment … →*) opens on the cluster's tabs.

## 0.6.6 (2026-10-18)

### Security

- The YAML view refuses names with `/`, `..` or `%`, which could reach any API path, and hides anything that comes back as a Secret.
- A kubeconfig that names a token, certificate or key file is refused, so the console never sends its own token to another server.
- Watson refuses to print Secrets in any type spelling (`secrets.`, `secret.v1.`), shows prefixed label removals on its card, acts only on the cluster a card was made for, and checks a selector's matched set and a queued change's objects again before it runs.
- The read-only SuperAdmin no longer gets `nodes/proxy`, `pods/exec`, `pods/attach`, `pods/portforward` or the proxy subresources; the README's read-only recipe sets `kubeletStats: false`.
- Sign-in no longer redirects off the site through `\`; OIDC refuses reserved user names and ignores an unverified email; event streams end with the session or a change of the person's groups.

### Changed

- One date and time format everywhere, in the browser's time zone with its short name (`2026-05-03 1:34pm PDT`); Settings sets the date style and the clock for everyone.
- Copy icons beside names in the tables and side lists. The top bar no longer shows the refresh time; acknowledged alerts say who and when; the home card's review button is *Audit*.
- A pod that runs but is not ready stays an alert (*Not ready*).
- Permissions and Roles open for every signed-in person.

### Fixed

- One unreadable connection Secret no longer hides the others; a kubeconfig without `current-context` starts.
- The assistants' event stream reconnects after a proxy error; a modal drawer keeps and returns focus; CSV cells that would run as formulas stay text.
- The image builds again after the README screenshots were added.
