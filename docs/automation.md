# Automation: requirements

Automation runs AI-written, human-approved scripts on the cluster's nodes over SSH, with the same safety model as the rest of 221B. Approval happens once, on the code: running or scheduling approved code needs permission, not approval. Designed on October 31, 2026, as the second part of Phase 11 (branch `phase-11-auto`), on top of Phase 11's SSH to nodes (ADR-72). The full design, with every phase, is the doc "221B Automation Design"; the screens are on the canvas "221B Automation design", copied to `docs/design/automation/`; the mapping from Ansible's functions is [automation-mapping.xlsx](automation-mapping.xlsx).

## Scope

In, for this first step (Auto-1 core):

- A top-level **Automation** area with **Nodes**, **Scripts**, **Variables**, **Run Profiles** and **Run History**.
- Scripts with a comment header the console reads, static checks, immutable versions and approval.
- Fleet and node parameters, read by scripts as environment variables.
- Runs on a fleet's paired nodes over Phase 11's SSH: dry run, privilege nobody or full, batches, a failure limit, a timeout per node, reboot and wait, cancel, per-node results and output.
- A ConfigMap of Automation's own for scripts, parameters and runs.

Built since (see *As built*): Auto-1's second step, Auto-2 and Auto-3, and hosts outside Kubernetes (Phase 12, see *Hosts outside Kubernetes*).

Later: Auto-4, a Schedules area shared with Kubernetes actions, notifications, a script library.

Out: Ansible or another tool as the executor; a module library, playbooks and handlers; a file store or templating in the console; app deployment through scripts (Apps does that); limited sudo (needs sudoers rules on the node).

## Approach

**A script is the unit of work.** One shell file does one job on one node. Running it on many nodes is the engine's job: order, batches, the failure limit, results. There are no steps, handlers or modules; logic lives in the script.

**Approve code, not runs.** On a production cluster, only an approved version runs. A script version is approved once, like a code review, by someone who did not write or submit it, so every approved version has had two people. On any other cluster a SuperAdmin may run the latest version without approval, and the audit log records its state. Running or scheduling approved code needs a SuperAdmin's permission and the checks below, not another approval. An SSH session on a cluster with Watson's two-person rule needs a second person every time, and that difference is deliberate (open question 10 in the design doc). A console needs two SuperAdmins for anything to be approved.

**Limits outside the AI.** Sherlock (Auto-2) reviews; the console enforces. A script that declares `privilege nobody`, and every dry run, runs as `nobody` through `runuser`, so it cannot change the node even if it ignores `DRY_RUN`. The fleet's ceiling caps what a run may get. Static checks refuse a `sudo` the header did not declare, a download that is not checked, and a few commands that destroy a node.

**Phase 11 is the transport.** Each node connection is Phase 11's: the pairing's login user and port, a certificate the console signs for that connection (key ID `<person> via 221B automation run <id>`, five minutes), the pinned host keys. A node that is not paired, or paired with another authority, fails with the reason. Automation never pairs a node.

**Its own ConfigMap.** The settings ConfigMap is shared and capped at 1 MiB (phase-9-review.md), so Automation keeps its records in `<release>-automation` (ADR-73).

## The script header

| Line | Declares | Example |
| --- | --- | --- |
| `# 221b:describe` | What the script does, one line or more | `# 221b:describe Report mounts above a threshold` |
| `# 221b:param` | A parameter: name, `required`, `optional` or `secret`, a description | `# 221b:param THRESHOLD optional percent full, default 85` |
| `# 221b:privilege` | `none` runs as `nobody` and cannot change the node; `full` runs with the login user's rights, root or sudo, up to the fleet's ceiling | `# 221b:privilege nobody` |
| `# 221b:dry-run` | `yes` when the script honours `DRY_RUN=1` | `# 221b:dry-run yes` |
| `# 221b:facts` | Facts it reads, fresh from the node, as `FACT_OS_FAMILY` | `# 221b:facts os.family` |
| `# 221b:target` | `nodes`, or `kubernetes` for kubectl lines on the cluster | `# 221b:target kubernetes` |
| `# 221b:k8s` | One Kubernetes action it may take; Watson refuses any other | `# 221b:k8s rollout restart deployments` |
| `# 221b:runs-as` | The service account of a Kubernetes script | `# 221b:runs-as ops/deployer` |

Spaces after `221b:` and a colon after the key are optional: `# 221b: privilege: none` is the same line as `# 221b:privilege nobody`.

A script receives its parameters as environment variables, `DRY_RUN=1` on a dry run, and `NODE`, `CLUSTER`, `FLEET` and `RUN_ID`. Exit code 0 is success. The last line of output may be JSON: `{"changed": true, "msg": "…", "reboot": true}`; `reboot` asks the console to reboot the node and wait for it.

## Design

## As built (Auto-1)

- **Server.** `server/internal/automation`: the header parser and checks (`header.go`, `checks.go`), scripts and versions (`store.go`), fleet parameters (`variables.go`), runs and the engine (`runs.go`, `engine.go`). `nodessh.Service.Exec` runs one command with no terminal on a paired node, behind a certificate signed for that run (key ID `<user> via 221B automation run <id>`); `NobodyCommand` wraps privilege `none` and every dry run. The API is `server/internal/api/automation.go`; every route is a SuperAdmin's and is recorded in the audit log (`automation.script`, `automation.approve`, `automation.params`, `automation.run`).
- **Web.** The Automation area, shown only to a SuperAdmin, has *Nodes*, *Scripts* (one table, filtered by groups on the left and by state, with Dry run… and Run…), *Run History* (every run, with a drawer of per-node results and output, polling while the run goes on, and Cancel), and *Variables* (values, a node's own values, and the privilege ceiling). The script drawer edits, checks as you type, saves the draft, submits, approves and deletes; its Versions tab lists each version's approvals and SHA-256.
- **Settings.** `-automation` / `AUTOMATION` (default true) and `-automation-configmap` / `AUTOMATION_CONFIGMAP`; the chart's `automation.enabled` adds the ConfigMap `<release>-automation` and lets the settings Role reach it. Without the ConfigMap, scripts and runs live in memory.
- **Fleets.** A run picks one of the cluster's fleets, or *All nodes* (id `_all`) for every node; only nodes paired for SSH can run, and the dialog shows why the others cannot.
- **Auto-1, second step.** *Facts*: `automation/facts.go`, one built-in read-only script run as `nobody`; only known keys are kept, per node, with the time and any error; a script that declares `# 221b:facts` gets them fresh, as `FACT_OS_FAMILY` and so on, and Facts are in the node's drawer, with Refresh. *Run Profiles*: `profiles.go` and the page now called Run Profiles; the built-in run profiles `nobody` (id `read-only`), `ssh-paired account` (id `login-user`) and `login-user` (id `as-the-person`, Kubernetes only) are built in; a run is refused one that gives less than the script declares or more than the fleet allows, and a dry run always uses `read-only`. SSH reaches a node only as the user it was paired with, so a configuration chooses between that user and `nobody`, not among SSH profiles. *Watson's wording*: every command of a run, script, facts, kubectl line and hook, is recorded as `automation.command`, "Watson via <script> v<N>, run #<id>", and each node's output opens with it.
- **Auto-2.** *Sherlock*: Write with Sherlock in the script drawer locks the script until it ends or is cancelled. It sees the console's checks, is sent back to fix what they find up to three times, and a person sees only what it could not fix and what it asks. Ask Sherlock on a version is kept with it as advice; it never approves, and script text is scrubbed first. *Parameter changes*: `changes.go`; a change lists the approved versions that read a changed value, the console's rule first (sensitive, or read by a condition), and Sherlock can only add to what needs approval. On production one that needs approval waits for someone other than the requester: the values stay, and those versions are suspended on that fleet. Off production it applies at once, with the same list. *Kubernetes targets*: `# 221b:target kubernetes` with `# 221b:k8s verb resource` lines; the body is kubectl lines with no shell, run by Watson's kubectl inside the console, each checked against the header at save and again at run; a dry run uses `--dry-run=server`. *Run identities*: the configuration's service account, else `# 221b:runs-as`, else the person; whoever starts the run needs `impersonate` on it, and the chart lists it under `automation.runIdentities`. *Secrets*: `# 221b:param NAME secret`, whose value is `secret:namespace/name/key`, read as the person who starts the run; it reaches the node on standard input, never on a command line, is masked in output, and only the reference is recorded. Kubernetes scripts cannot take one, as the line is audited. The Run dialog suggests references while one is typed (FU-03) from `GET /api/v1/automation/secret-refs` (also under `/clusters/{cluster}/`, SuperAdmins only): the namespaces, names and keys of the Secrets in namespaces where Kubernetes lets the person list Secrets, Helm's release records left out, never a value.
- **Auto-3.** *Hooks*: Around each node in the Run dialog: cordon and drain before, uncordon after a healthy result, and any approved Kubernetes script before or after. A failed drain skips the script; a failed script leaves the node cordoned and says so. *Retry*: Retry failed on a finished run starts a new run of the failed and unreachable nodes, through every check a run goes through.
- **Not yet.** Conditions and loops across scripts, pause between batches, schedules, notifications and a script library. Fleet roles (AT14) and `K8S-` role names were dropped on November 2, 2026: SuperAdmin covers the whole console, not Kubernetes alone, and Automation is a SuperAdmin's.

## Run safety (November 2026)

What a run checks and keeps, as built after the review of November 3, 2026:

- A node runs under the strictest ceiling of the fleets it is in (All nodes' when it is in none), and on production a variable change waiting on any of its fleets suspends the versions it touches there, whichever fleet the run picked. On production a run's own values are weighed as a variable change for that run, and wait for a second admin when they need it (FU-05, below).
- Only the newest change on a fleet can be approved; approving applies it over the values it was asked against, or refuses and says what differs.
- A node is in one live run at a time (dry runs and scripts on the cluster aside), and a cluster's control-plane nodes are worked on one at a time. A request id makes a start sent twice one run.
- A reboot runs with the script's privilege, so a nobody script cannot ask for one. The node is back when its boot ID changed and Kubernetes reports it Ready, within its reboot timeout: the node's own, else the longest of its fleets', else 10 minutes. A host outside Kubernetes is back when its boot ID changed, which SSH answering again tells.
- A console that loses the lead stops its runs; a cancel also goes through the run's record; a production run re-reads its version before each batch and stops when it changed or lost its approval. Runs and facts live in `<release>-automation-runs`.

## Run values: bindings and approval (FU-04 to FU-06)

As built on November 13, 2026 (ADR-156):

- **Bound to its own name first** (FU-06, replacing FU-04's filled box). A variable parameter whose name a fleet or a node sets for at least one node of the run (All nodes, for a script on the cluster) starts bound to that variable, as the dialog opens and whenever the nodes change: its field holds the chip *variable NAME · 3 values*, or *· its value* when every node has the same one (*value hidden* for a sensitive or secret-looking variable), with each node's value in its tooltip (a hidden one's places alone), and the nodes without it named below, as for a binding picked. That is what each node inherits anyway, so it is not sent: the run's own values leave it out, and on production it is not weighed. A binding picked to the parameter's own name is the same and is not sent either. A choice the person made, another variable or a constant, is never undone by a change of nodes. ✕ clears the chip and leaves an empty, focused box; a value typed there is a constant and carries a *constant* badge at the field's right (a secret parameter's *secret ref*). An empty box says what it sends (FU-07): once a chip or a value was cleared it holds the chip *empty string ""*, sent as `NAME=""` on every node over what nodes and fleets set (✕ goes back to the variable of its name, or to not set); untouched, with no value to inherit, it holds *not set*, and the script gets no `NAME` at all. Environment variables have no null; unset is the nearest. A required parameter refuses the empty string, in the dialog and on the server. Typing a variable's exact name binds only when it is picked from the list. The chip's text describes the field, ✕ is labelled *Clear variable NAME from PARAM*, and the badge is in the input's description. A run's details and a run request in AIOps › Inbox show a binding as the same chip (without values) and a constant with the same badge (`ValueTag.tsx`).
- **Searched by name and value.** Typing searches every variable a fleet or a node sets on the cluster, and this script's earlier runs' own values, case aside. A suggestion shows the variable's name, its values on the run's nodes and where it is set. A variable marked sensitive, named like a secret (PASSWORD, TOKEN, SECRET, CREDENTIAL, PRIVATE, API_KEY, …KEY) or holding a `secret:` reference or a PEM key shows its name alone, and its values are not searched.
- **Bound by name.** Picking a variable sends `var:NAME` as the run's value: when the run starts, each node gets its own value of NAME, inherited as any variable is (its own, then its fleets', then All nodes'), and a node without one gets none. A required parameter is refused for those nodes; a variable no node of the run has is refused whatever the parameter. The form follows `secret:namespace/name/key`: `var:` and a variable's name (capitals, digits and underscores), nothing around them. Only a run's own values bind; a fleet's or a node's value is always text, and a secret parameter's value never binds. The run keeps `var:NAME` in its own values, and each node's resolved value as before; a retry binds again.
- **Constants.** Anything typed is the same on every node. A text that starts with `var:` is sent with a backslash in front (`\var:x`), and the server drops one leading backslash before `var:` (`\\var:x` is `\var:x`). A run value that starts with `var:` and names no variable is refused, so a typo never runs as text.
- **On production.** A real run's own values are weighed as if the fleet's values changed for that run: per node of the run, what it inherits against what the run gives it (`ChangedVariables`), a binding to another variable counting as a change; then `Impact` for the version run, with the names any of the nodes' fleets marks sensitive, and Sherlock, as for a variable change. None needs approval: the run starts, and its basis says so. One does: the start answers 202 with a run request, kept beside the variable changes (`changes.json`, the newest 50 decided ones), listed in AIOps › Inbox (*Run with its own values*) with its values and what they touch. Another SuperAdmin approves it there, which starts the run at once as the person who asked (their name and Kubernetes identity), with what they asked for: the version, the nodes, the rollout, the run profile, the hooks and the values. Every check is made again (version approved, suspensions, ceilings, pairing, values resolved then); when one fails, it keeps waiting and the answer says why, so it can be rejected. Anyone may reject it with a reason; whoever asked may only do that. The run records who approved its values, and the audit log (`automation.run`) the request, the approval or rejection, and the start. The Run dialog weighs the values before Run is pressed (`POST …/automation/runs/weigh`, the console's rule alone, nothing recorded) and says which would wait and why.

## Hosts outside Kubernetes (Phase 12)

A **host** is a machine that is not a Kubernetes node, which the console reaches by SSH and Automation then treats as a node: a backup server, a load balancer, a database VM. It is added per cluster connection, by a SuperAdmin, on the Nodes tab (*Add host…*), and it shows in the table with a *host* tag, the columns only Kubernetes fills left empty.

**Adding hosts.** The dialog adds one host or many at once (asked November 5, 2026), in three steps:

1. **Details:** the hosts, by spaces, tabs, commas, semicolons or lines: each an address (IP or DNS name), named after it as a node name (lower-cased), or `name=address` to name it otherwise (an IPv6 address needs a name). A host named after its address takes its own name once paired: as the console first logs in with its certificate it reads `uname -n` and, lower-cased, renames the host to it when that is a node name no node or other host has; its pairing and the lists of nodes that named it follow, and the audit log has `host.rename`. Otherwise it keeps its address as its name, and the console stops trying. A name is a node name, not one a node of the cluster or another host has; it is the host's name in fleets, runs and the audit log. Then, for every host given, the SSH port (22); the login user the console logs in as is the chart's (`toolbox.ssh.loginUser`, root unless the chart says otherwise). And how to pair them (asked November 5, 2026): an account that may use sudo, or root, with its password or private key, kept in the page and sent nowhere until the keys are trusted; or the setup command, run by hand. Each host is *pending*; one the console refuses (a node's name, say) is named, and the others go on. A pending host given again at the same address is taken up again with what was given now, its trusted key kept; a name a paired host, or a host at another address, has is refused, saying which. A host whose SSH port does not answer is named with why (no answer in time, refused, no route) and where to look: sshd on it, a firewall, and `networkPolicy.nodeCIDRs`, outside which the console opens no SSH connection.
2. **Host keys:** the console connects to each host with no credential at all, reads the key sshd presents (ed25519 first) and lists every host with its SHA256 fingerprint, each ticked. **One approval** trusts them all (*Trust N keys and pair*): each is pinned, and a host that later shows another key is refused until a SuperAdmin trusts it again; with an account given, each host is then paired with it in turn. Comparing a key on its host is optional: the step shows the command, `ssh-keygen -lf /etc/ssh/ssh_host_ed25519_key.pub`, for a network where someone could stand between the console and the hosts. Unticking a host leaves it pending. The key itself is never shown or answered by the API, only its fingerprint.
3. **Pair**, one of two ways:
   - **Sign in once.** An account that may use sudo, or root, with its password or its private key (and passphrase), and sudo's password if it is another. The console opens one SSH session with it, the pinned key checked, and runs the pairing script nodes run (`PairScript`, with the login user made first when missing) as `sudo -S -k -p '' -- sh -c '…'`, sudo's password on standard input and never on a command line (root needs no sudo; an account with a key and no sudo password gets `sudo -n`). It then logs in as the login user with a certificate, as it does to a node, and the host is *paired*. The credential is wiped once the request ends: it is never stored, logged, audited, cached, answered or sent to Sherlock (X-01), and the session's output goes through the same per-stream mask as a run's secret parameters before anything reads it. When it fails the dialog says why and what to do: password sign-in off on the host (give a key, or run the command), sudo that needs a terminal or a second factor (run the command), sudo that refused the password or the account, or the step of the script that stopped it (another authority already trusted, sshd on another port, no sshd).
   - **Run this command yourself.** The dialog shows the same setup as a command to paste on the host as root (`sudo sh <<'221B-SETUP' … 221B-SETUP`): it makes the login user when missing, writes the console's public key to `/etc/ssh/221b/ca.pub`, sets `TrustedUserCAKeys` and `AuthorizedPrincipalsFile` in a drop-in and reloads sshd. *Check connection* then logs in with a certificate and marks the host paired, or says the host did not take the certificate.

There is no second-person approval: whoever holds sudo on the host can do anything there anyway (decided November 4, 2026).

**As a node.** A paired host can be in fleets (a fleet of labels takes it by its labels; a list of nodes takes it by name, and *Add to fleet…* on picked rows works for it), be a run's target, have its facts collected and a reboot timeout of its own, and has variables like any node. The differences: it is reached by direct SSH from the console at its own address, with no node-shell pod; a reboot is over when its boot ID changed and SSH answers again, with no Kubernetes Ready to wait for; hooks around each node (cordon, drain, uncordon, Kubernetes scripts) do not run on it, and the run's output says so; it is never counted as control plane. Kubernetes-only tools (node shell, kubectl, YAML, pods) are not offered for it.

**Removing one** forgets the host, its pinned key and its pairing. Its details show, before it goes, the cleanup command that takes this console's lines off it (`UnpairScript`, to run as root on the host).

**Audit.** `host.add`, `host.trust` (trusted, or trusted again, with the fingerprint), `host.pair` (with the bootstrap account's name, or by the setup command, and failures) and `host.remove`, each with who and when; never a credential.

**From an agent's proposal** (ADR-101). An approved Watson card may add, label or remove hosts (`host.add`, `host.label`, `host.remove`), create or change fleets, and set a fleet's parameters and per-node values; a SuperAdmin approves it, and each change is audited under its own action, naming the card. A card never carries a host key or a credential: a host it adds waits as pending until a person pairs it here, with one credential and one approval of every key.

**Storage.** Hosts are kept under `ssh-hosts.json` in the settings ConfigMap, beside `ssh-pairings.json` (128 KiB, at most 150 hosts); a paired host's pairing is an ordinary pairing under its name. The leader reads them again every 30 seconds, so a host added through another replica shows within that.

**Network.** The console reaches hosts through the same network policy rule as the nodes: their addresses must be inside `networkPolicy.nodeCIDRs` (when it lists any), and a host whose sshd listens on a port other than `toolbox.ssh.port` needs that port in `networkPolicy.hostPorts`. Hosts need `toolbox.ssh.enabled`, like Automation.

**API.** Under `/api/v1/hosts` and `/api/v1/clusters/{cluster}/hosts`, a SuperAdmin's: `GET` (the hosts, with the chart's login user and port), `POST` (add), `POST {name}/scan` (read the key: fingerprint, type, command), `POST {name}/trust` (`{fingerprint}`), `POST {name}/pair` (`{user, password | privateKey, passphrase, sudoPassword}`; a request that is not valid is refused without quoting it), `GET {name}/setup`, `POST {name}/check`, `GET {name}/cleanup`, `DELETE {name}`.

## Keeping resources for software beside Kubernetes

To run MinIO or anything else on the nodes Kubernetes runs on, tell the kubelet to keep part of the machine from pods. It is agent configuration, so it changes through a script and shows read-only in the console.

1. *Scripts › New script › Start from*: **Reserve resources from Kubernetes (RKE2, k3s)**. Have it reviewed and approved as usual.
2. *Variables*: set `SYSTEM_RESERVED_CPU` and `SYSTEM_RESERVED_MEMORY` on the fleet, and on a node where it differs; `KUBE_RESERVED_CPU` and `KUBE_RESERVED_MEMORY` are optional. Raise the fleet's ceiling to `full`.
3. *Run…*: a dry run says what would change on each node. Then run it **Canary first** with batches of 1, so one agent restarts at a time and control-plane nodes keep their quorum.
4. *Fleets* shows what each node keeps now. Nodes that differ are listed apart, which is how a run that stopped part way shows.

The script writes `/etc/rancher/rke2/config.yaml.d/50-221b-reserved.yaml` (`k3s` on k3s) with `kubelet-arg+:`, which adds to arguments already set, restarts `rke2-server`, `rke2-agent`, `k3s` or `k3s-agent`, and waits for the kubelet. If the agent does not come back, it puts the file back as it was and restarts it again. The same values twice change nothing and restart nothing.

Three things to know:

- **A shrinking node can lose pods.** On restart the kubelet admits its pods again; one that no longer fits what is allocatable fails with `OutOfmemory` or `OutOfcpu`, and its controller starts it elsewhere. Before you run it, compare *Free to schedule* on Nodes with what you are taking away, or cordon and drain the node first.
- **Memory is a limit on pods, CPU a share.** The kubelet caps all pods together at allocatable memory. For CPU it only lowers their share when the machine is busy, so software beside Kubernetes gets its CPU under contention, not a wall.
- **In use is the whole machine.** metrics-server reads the machine, your other software included, so *In use* is shown as a share of the machine; *Requested* and *Free to schedule* stay shares of what pods may have.

**Names (November 3, 2026).** A privilege is *nobody* (read-only) or *elevated* (all the rights of the ssh-paired account), for a script, a fleet's ceiling and a run profile alike. A header says `# 221b:privilege nobody|elevated`; `none` and `full`, the earlier words, still read, and are what is stored, so earlier versions keep their hashes and approvals. The API follows the pages: `/api/v1/automation/run-profiles`, `.../automation/fleets/{fleet}/variables` and `.../automation/variable-changes`; stored records keep their field names (`config` on a run, `params.json` and `configs.json` in the ConfigMap).

**Run as and Approvals (November 3, 2026).** The Run dialog names the run profile it will use: the built-in that fits the script (nobody for a nobody script and every dry run on nodes, the ssh-paired account for an elevated one, login-user on the cluster), or another the person picks among those that reach the fleet, give what the script declares and stay within the fleet's ceiling. Administration › Approvals (`GET /api/v1/admin/approvals`, `{items: [...]}`) lists what waits for this person, then the newest 200 decisions: script versions approved or revoked, variable changes approved or rejected, Watson commands approved, each with who asked and when and who decided and when. Watson's commands are kept in memory, so their history starts again on a restart.

**Approve and Reject (November 3, 2026).** Approve asks first, on a version and on a variable change. Reject, with a reason the author reads, is offered on a version in review to anyone who did not write or submit it, and on a waiting variable change; the reason is kept on the version (`rejected`) or the change (`comment`) and shown on Approvals. A rejected version is final: it is never approved or run, and saving the script starts the next version. A fleet whose ceiling is not set is nobody, on the server as on the page.
