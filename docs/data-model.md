# The data model

What 221B keeps in PostgreSQL (Phase 13): 121 tables in eleven domains and three tiers (the model's 73, 3 that hold what a script version kept in lists, the script versions a variable change touches, who had approved a run's version, what a run request's values mean for its script, a provider's headers, the notes, parts, planned cases, checks and recordings of the agents' instructions and tests, a job run's facts, proposals and the cases they resolve, the clusters the jobs looked at, the rule suggestions with their descriptions, what the runs found under each check with its titles, kinds, findings and descriptions, the suggestions dismissed and the runs counted, a proposed change's evidence, plans, results, decisions and commands, the conversations Sherlock keeps with their messages, in place of the model's `change_chats`, a live source's addresses, each source's last read, the syncs with their batches, and Mycroft's runs with their page changes' sources, approvals and contradictions, their decisions, the page requests and the corrections, and of Cases a case's people, the work on it, its proposals, drafts and commands, a service's places and a known issue's followers and keys, in place of the model's links between cases, cases of an RCA and services of a known issue, and of Platform an application's commands). The schema itself is the SQL in [`server/internal/db/migrations`](../server/internal/db/migrations), one file per domain; this page says what each table holds and the rules every table follows. [database.md](database.md) says how the database is run, and which domains have moved to it so far.

Each table's columns are listed with their marks: **PK** is the key, **FK** a key into another table, **FK?** one that may be empty, and ↗ a key into another domain.

## The rules

- **Keys point down the tiers or stay inside one.** The AIOps flow may key into the engines and the foundation, the engines into the foundation, and the four AIOps domains into each other along the flow. A foundation table never keys up: where it records something higher (an acknowledgement's case, a Toolbox session's change, a policy's agent), it keeps the id as a plain column. One engine's table keys up into the flow, by the owner's decision: `chats`, whose row is joined to the change or the case its conversation is of (step `0033`).
- **Every key is named for its table.** A primary key is `<entity>_id` (`fleet_id`, `script_run_id`); no table has a bare `id`. A foreign key has the name of the key it points to; a second key into the same table adds a role (`retry_of_script_run_id`, `linked_case_id`). A join table's key is its pair of keys.
- **Natural keys only where the code already has a stable id:** `settings.scope`, `clusters.cluster_id`, `agents.agent_id`, `validation_rules.validation_rule_id` and `wiki_pages.path`. Every other key is a UUIDv7 the console makes (`db.NewID`), never a sequence; a number people read, such as `case_number`, is a column of its own.
- **Names say what a column holds.** Flags start with `is_`, times end in `_at`, people in `_by`, money in `_usd`, lists of ids in `_ids`.
- **History outlives what it points to.** A run, result or record that outlives its target holds a key that is emptied when the target is deleted, beside the target's name as text (`host_name`, `fleet_name`, `case_number`).
- **A cluster is `cluster_id` everywhere.** Only Platform and Inventory hold a real key to `clusters`. Inventory's is emptied when a cluster's row is deleted, so list fleets and hosts outside Kubernetes outlive it (removing a connection does not delete its row yet: it keeps the row with only its id, DB-64); the other domains keep the id as a plain column, so history survives a removed connection.
- **Sign-in never depends on the database.** Local accounts stay in a Kubernetes Secret, and while the session store is away whoever signs in (a local account, a directory person, a person of the OIDC provider) gets a short-lived signed session (DB-65).
- **Kubernetes state is never stored.** A node's row holds its identity only (cluster, name, uid); labels, taints, status and topology are read live.
- **Observed host state is a fact, not a column.** What the facts run reports, network details included, is JSON in `host_facts`; the tables hold only what people set, such as a host's data center and rack.
- **A record is one row for its whole life.** Approval changes its state; there are no draft tables.
- **Versioned things keep their history in a versions table:** scripts and prompts.
- **JSON only for what is read whole:** facts, checks, rollout settings, evidence. Anything joined, filtered or pointed to has a table.
- **Ledgers are only added to.** `audit_events` and `ai_spend` are inserted and read, never updated (a trigger refuses it), so writers at once never collide. Retention deletes.
- **True singletons are JSON rows of `settings`,** read whole and written rarely, each over its version.
- **Secrets stay in Kubernetes.** A table holds only the name of a credential's, a token's, a provider key's or the SSH authority's Secret; a secret script parameter keeps only its Secret's name.
- **Bodies stay where they are.** Wiki pages and transcripts remain in git, S3 or a volume.

## Where the schema differs from the names above

- `check` and `window` are reserved words in SQL: the columns are `check_name` (in `findings`, `cluster_checks` and `exceptions`) and `time_window` (in `known_issues`).
- `audit_events` has `actor`, `actor_subject` and `actor_email` for who, `detail` as text (it is a sentence, searched by word), and `restored_at` for an event that came back from a backup.
- `toolbox_sessions.toolbox_session_id` is the Toolbox's own id, sixteen hex digits, not a UUID: the audit log and the transcripts' file names carry it. The table also has the session's `summary`, `node`, `owner_user`, `approved_by`, `reason`, `created_at`, `ended_by`, `end_note`, `is_recorded`, `byte_count`, `connection_count` and `watched_by`.
- `approval_policies.approval_policy_id` and `notification_channels.notification_channel_id` are the ids the console already gives them (`s…`, `n…`), not UUIDs: the audit log and the channels' Secret carry them. `approval_requests` has `request_number`, the number people read, and `requested_by_key`; a decision has `decided_by_key`; both lists keep a `position`. The next request's number and the notifications' link are scopes of `settings` (`approvals`, `notifications`).
- `hosts.is_kubernetes_node` is a plain flag, set by what made the row, since a node's uid is not known where its row is made; `hosts` also has `is_auto_named`. `host_pairings` has `fingerprint`, `trusted_at`, `offered_key` and `mismatch_key` for a host outside Kubernetes. `fleets` has `fleet_key`, the id a fleet has within its cluster, and `position`; `labels` and `taints` are text arrays of the requirements as written; `color` is the palette's number. `fleet_hosts` has `position`.
- `alert_acks.job_run_id`, `case_id` and `exception_id` are text: the ids those records carry today.
- `credentials.credential_id`, and the columns that point at it, are text: the id the console gives a credential. `repositories` has `position`, `username`, `is_secret_set`, `is_credential_migrated`, the pinned certificate's parts as `pinned_cert_*`, `pinned_by`, `pinned_at` and `test_result`.
- **Credentials** (step `0034`, DB-60): every field of a credential but its secret is a column of `credentials`: `ca_pem`; the pinned certificate as `pinned_cert_sha256`, `pinned_cert_subject`, `pinned_cert_issuer`, `pinned_cert_not_after`, `pinned_by` and `pinned_at`, in place of the model's one `pinned_cert`; how a token is sent as `send_method`, `send_username`, `send_header`, `send_prefix`, `send_param` and `send_cookie`; the kinds' own parts `host_key`, `app_id`, `installation_id`, `token_url`, `client_id`, `scope` and `cert_pem`; `secret_parts`, the names of the secret parts kept, never their values; the last test as `tested_at` (null for a credential never tested), `is_test_ok`, `test_target`, `test_method`, `test_status`, `test_text`, `test_suggest` and `tested_by`, with the certificate it saw as `test_cert_*` and `is_test_cert_*` (`test_cert_sha256` is empty when it kept none), in place of the model's `last_test` JSON; `created_at`, `updated_by` and `migrated_from`. There is no `secret_ref`: a credential's secret is the key `secret-<credential_id>` of the credentials' Secret, and no column holds any of it. `is_kept` is false for a row with only its id, which stands for a credential that a repository, an application or a source names and whose own record is not in the table (the list kept in memory, or a credential since removed): the list is the kept rows, and `lower(name)` is unique among them. A row something points at is updated in place and never deleted while it is pointed at. The note of the upgrade to 0.12.1 is the settings scope `credentials-migration`. `knowledge_sources.credential_id` is a key from this step, null for none and emptied if the credential's row is deleted.
- **Applications** (step `0035`, DB-62): the model's `values` column is gone, and never held anything: an application's values file, its parameters and its commands' parameters are its secret part, since people type passwords into them, and stay in the application's Secret under the key `set.json`. Every other field of the record is a column: `source_path`, `ref_kind`, `commit_at`, `commit_subject`, `chart_version`, `values_file` (a second values file's name, never its contents), `is_namespace_created`, `is_defaults_ignored`, `fleet_key` and `fleet_label` (the fleet by its id within the cluster, a plain column, as `run_profile_fleets.fleet_key` is), `matched_revision`, `source_diff`, `adopted_revision`, `is_credential_migrated`, `creator_namespaces`, `created_by`, `created_at`, `updated_at`, and `version`, which a save is held to. Whether a token of before 0.12.1 is kept is read from the Secret, where the token is, and has no column. `repository_id` is a real key, emptied when the repository's row is deleted, beside `repository_name`, the name as it was last saved: the name is read through the key while the repository is listed, so a repository given a new name is followed with no application written, and from `repository_name` once it is gone. For that a repository keeps its row through a new name. `(cluster_id, namespace, name)` is unique. The commands are `application_commands`, keyed by the application and the command's place in the menu, not by its name: a command's parameters are paired with it by name from the Secret, and two commands of one name each keep their own.
- **Cluster connections** (step `0036`, DB-64): every field of a connection but its credential is a column of `clusters`: `ca_mode` (how the API server's certificate is checked: `pem`, `system` or `skip`) and `ca_info` (the saved CA's subject and expiry, never the certificate); what the saved credential says about itself as `cred_who`, `cred_context`, `cred_cluster`, `cred_issuer`, `cred_client_id`, `cred_expires_at` and `cred_set_at`; and `version`, which counts the row's writes so a replica sees what another one changed. `created_at` is when the connection was added and `updated_at` when it was last saved. There is no `secret_ref`: a connection's credential is the Secret `<prefix>-cluster-<cluster_id>`, whole, and no column holds any of it, the parts that are not strictly secret included (the CA certificate, a kubeconfig's context, the OIDC issuer, client id and scopes), since they are read only together with the secret. `is_kept` is false for a row with only its id, which stands for a cluster that an acknowledged alert, an application, a fleet or a host names and whose connection is not in the table (kept in memory, not copied yet, or since removed): the connections are the kept rows. The table was altered where it stood, so the rows with only an id stayed. A removed connection's row is not deleted: it is set back to one with only its id, its columns emptied and its `version` raised, so its applications, acknowledged alerts, fleets and hosts stay as they were until what becomes of them is decided (the handover's to-do 3). No name is unique in the table: the console refuses a second connection of one name, and a copy from Secrets that held two must not fail.
- `run_profiles.run_profile_id` is the id the console gives a profile (the built-in ones are fixed), and `run_profile_fleets` holds `fleet_key`, not a key to `fleets`: a profile is not of one cluster and names a fleet as runs do.
- **Scripts** (step `0016`): `script_versions.header` and `review`, which were JSON, are columns and rows: every field of a version is a column, a scalar list (`facts`) an array, and a list of records a table. A script may be in no group; a group a script names gets its row then, and keeps it while scripts are in it.
- **Variables** (step `0017`): as the model has them, on one fleet or one host; the service was changed so that a node's own values are the node's (AU-23). `fleets.kind` has two more values, which the settings' list of fleets leaves out: `all`, the cluster's fleet of every node, which carries All nodes' variables, ceiling and reboot time; and `unlisted`, a fleet that variables name and the list does not have. A node's own reboot time is `hosts.reboot_minutes`.
- **Variable changes** (step `0018`): a change is on a fleet, named by `cluster_id` and `fleet_key` as a run names it, since a change outlives its fleet; the model's `scope`, `fleet_id` and `host_id` are gone, the items saying which nodes' own values it alters. `impact`, which was JSON, is the table `variable_change_impacts`. `approval_request_id` is optional: nothing joins a change to Approvals yet.
- **Runs** (step `0019`): `script_runs.rollout` and `hooks`, which were JSON, are columns. A run is kept after its script's version, its profile, its fleet, its nodes and the run it retries are gone, so it has each as its document named it (`script_name` and `version_number`, `run_profile_id` as plain text, `fleet_key`, `host_name`, `retry_of_number`) beside the key, which is filled while the row exists. `script_run_hosts` has `position`, `message` and `error`; one row a node of a run. `script_run_values` holds a run's own values (scope `run`) and what each host got (scope `host`); scope `fleet`, `script_run_fleets` and `script_run_host_fleets` wait for the engine to record a run's fleets.
- **Run requests** (step `0020`): a run that waits for approval is a row of `script_runs` with `request_number` and no `run_number`; approved, the run is written into the same row. The request's own columns are `request_number`, `request_state`, `request_client_key`, `requested_by`, `requested_by_user`, `requested_at`, `request_method`, `request_nodes`, `request_targets`, `person_user`, `person_groups`, `request_changed`, `request_note`, `decided_by`, `decided_by_user`, `decided_at`, `decision_comment` and `started_run_number`. `script_run_values` has scope `request`, and `script_run_impacts` holds what the request's values mean for the script. `approval_request_id` is still empty: Approvals has no operation yet to open one request.
- **A run's fleets** (step `0021`): `script_run_fleets` has `fleet_key` and `position`, `script_run_host_fleets` has `position`; `script_run_values` of scope `fleet` hold what each fleet had when the run started.
- **AI providers and agents** (step `0022`): a provider is known by the id the console gives it (`ai_provider_id` is text), which agents, Secrets and spend rows name; `agents.ai_provider_id` and `ai_spend.ai_provider_id` are not keys, since the default provider may have no row and a provider can go while what names it stays. Every field of a provider is a column (how it signs requests, the last connection test, its limits), its headers the table `ai_provider_headers`. The default provider, whose endpoint and model are Sherlock's settings, is the row `default` when anything is kept of it. `agents.is_enabled` may be empty (the catalog's default); `secret_ref` of the model is not used, the Secret's name following from the id.
- **Instructions, tests and the pilot log** (step `0023`): an agent's instructions are rows of `prompt_versions`, each in one `state`: `in_force` (one for an agent: what is in force, with the live version's number and the last draft revision given), `version`, `draft` and `revision`. `notes` and `pilot`, which were JSON, are the table `prompt_version_notes` and the `pilot_` columns; the edits of the built-in text are `prompt_version_parts`. A test run is of a draft's row, or of the row in force (the check made at start with a new baseline); its planned cases are `test_run_cases`, a result's `expect` and `checks` are columns and `test_case_result_checks`. A result names its case by `case_key` and not by a key, since a built-in case has no row and a result outlives its case. A test case is known by the console's id (`test_case_id` is text), its recorded tool results are `test_case_recordings` (`input` is what the agent gave the tool, kept as text as it was recorded). `pilot_entries` name their agent and the version that answered, not a row of `prompt_versions`: an entry outlives the draft.
- **Spend** (step `0024`): `ai_spend` is rows that are only ever added, one a cost (`usd` as a float, a sum of estimates; `question_count` 1 for a question's first call). The model's `provider_name`, `tokens_in` and `tokens_out` are gone: the engine counts cost, not tokens. `is_share_only` marks a share carried over from the sums a ConfigMap or a backup held: counted for its agent or provider and not in the total, which has rows of its own. No history is kept: rows from before the month before this one are removed, once a day.
- **Jobs and their runs** (step `0025`): a job is known by the console's id (`job_id` is text: its kind's, or one made when it is added), and has a row only when it was changed or added (`is_kept`), or has handled a scheduled time (`handled_at`) or spent (`spend_day`, `spend_usd`, `spend_stopped`). `schedule`, which was JSON, is the `schedule_` columns. `job_runs.job_id` and `schedule_claims.job_id` are not keys: a run outlives its job, and a job nobody changed has no row. A run is known by `run_key`, the newest has the greatest `position`; `trigger`, `routed` and `facts`, which were JSON, are columns and the table `job_run_facts`; the changes it proposed are `job_run_proposals` and `job_run_proposal_cases`. A finding names its check, case, known issue and exception by their own ids (`check_name`, `case_key`, `known_issue_key`, `exception_key`), not by keys: a check need not be a rule, and the three domains have not moved. The jobs' schedules do not use `schedule_claims` yet: a time is claimed by setting `handled_at` in the transaction that read it.
- **Checks, rules and what the runs found** (step `0026`): `cluster_checks` is the list of checks seen on a cluster (`position`); the model's `first_seen_at`, `last_seen_at`, `finding_count` and `sample_title` are gone, since the service counts by check and not by cluster: `check_found` with `check_found_titles`, `check_found_kinds`, `check_found_findings` and `check_found_descriptions`. `checked_clusters` holds each cluster's first run. `validation_rules` holds a built-in rule's changes or a rule added; `is_edited` is gone (every row of a built-in rule is an edit), `job_kinds` may be empty of a value (the built-in's own), and `replaced_by_validation_rule_id` is not a key, since the rule that replaces one may be built in and have no row. The suggestions are `rule_suggestions` and `rule_suggestion_descriptions`; the ids dismissed are rows of `dismissed_checks`, and the runs already counted rows of `counted_runs`, which names runs that may be gone from `job_runs` (step `0027`, which carries over what step `0026` kept of both as JSON in settings scopes).
- **Proposed changes** (step `0028`): a change is known by the id the console gives it (`change_key`, "PC-12"), which cases, runs, the audit log and Watson name; `change_id` is the row's own, and stays for as long as the change is kept: a change that changes has its row changed in place and what hangs from it written again (DB-56), so other tables can key to it, as `chats` does. `source` and `evidence`, which were JSON, are the `source_` columns and the table `change_evidence`. What must still hold is `condition_kind` and `condition_args`; an action's and a condition's arguments are one JSON value each, whatever the kind takes (decided with the owner). An action's plan and result are not columns of `change_actions`: the change keeps them as lists of their own, so they are `change_plans` and `change_results`, a result naming its action by number. The approvals and the rejection are `change_decisions`, by `verdict`; nothing joins a change to Approvals yet, and `approval_request_id` is empty. `change_events` has `position`, `by_name` and the actor's name and kind; the commands run from a change are `change_commands`. `change_cases` is `change_resolves`: it holds cases and known issues, by the id people read (`resolved_key`) and not by a key, in order, with who linked each (`linked_by`); `is_listed` is false for one that only names who linked it. The changes that replaced a change and that it replaces, and the standing approval that applied it, are ids as text (`replaced_by_change_key`, `replaces_change_key`, `approval_policy_id`): each may be gone. The model's `replaces_change_id` is gone with them. The counter the ids come from is the settings scope `changes`.
- **Sherlock's kept conversations** (step `0028`): the model's `change_chats` (time, role and body) is gone. A conversation Sherlock keeps for another record is a row of `chats`. Step `0028` knew it by Sherlock's session, a name (`proposal:PC-12` for a waiting change's, `case:C-12` for a case's); step `0033` joins it to that record by a key (below). A message is a row of `chat_messages` with a column for what is asked of a message and `parts`, one JSON value for its steps, references, view changes, things shown and hand-overs (decided by the owner on November 19, 2026: a chat is read and written whole, and the parts change shape as Sherlock gains features). `parts` is `json`, not `jsonb`, so that it reads back as written: a thing shown carries the input the model gave. `tokens_in` is empty for a message with no use reported.
- **Fixes and exceptions** (step `0029`): a fix and an exception are each known by the id the console gives them (`fix_key`, `exception_key`: "FX-12", "EX-12"), which cases, findings, acknowledged alerts, the wiki and the audit log name; `fix_id` and `exception_id` are the rows' own, and stay through a change. `fixes.steps` is one text, as people write it, not a list; `reason` says why a fix is pending or inactive, `contradicts` and `accepted` are the ids of the fixes it contradicts and of those a person accepted beside it, and the fix a duplicate repeats is `duplicate_of_fix_key`, an id and not a key, since that fix may be gone. `fix_cases` has `position`, the case by the id people read (`case_key`), `cluster_id` and `seen_by`; the model's `case_id` waits for Cases. An exception names the finding, the run, the job and the case it came from, and the exception a duplicate repeats, by their own ids (`finding_key`, `run_key`, `job_id`, `case_key`, `duplicate_of_exception_key`), not by keys: each may be gone, and Cases have not moved. It also has `detail`, `created_at`, `removed_by`, its page in the wiki (`wiki_path`, `wiki_error`), what it left out (`match_count`, `last_matched_at`, `last_run_key`) and `updated_at`. Both lists keep their order in `position`. The counters the ids come from are the settings scopes `fixes` and `exceptions`.
- **Mycroft's sources, syncs and page changes** (step `0030`): a source is known by the id the console gives it (`knowledge_source_id` is text), which the wiki's manifest, the syncs' state and the audit log name. Every field of a source is a column; `is_enabled` is false for a source switched off; the repository it reads is `repository_name`, its name in Administration › Settings › Repositories, and its credential `credential_id`, the id as text. The repository's name is not a key, since the repository may be gone; the credential was not one either until step `0034`, which made it a key to `credentials`. The model's `last_read_at`, `last_status` and `last_error` are not columns of `knowledge_sources`: the state of a source is kept by its id whether or not the settings still list it, so it is the table `knowledge_source_reads`. A live source's addresses are `knowledge_source_addresses`; `source_exclusions` has `position` and its source's id as its key. The syncs are `knowledge_syncs`: the last one whole (`slot` `last`) and the newest few in short (`history`), with `knowledge_sync_batches`. Where the wiki is kept is the settings scope `knowledge`, and whether a sync runs the scope `knowledge-status`. The model's `wiki_changes` (a row a proposed page change, keyed to `wiki_pages`) is a page change of a run: `wiki_runs` is the run, known by `run_key`, and `wiki_changes` is keyed by its run and its place in it, with `wiki_change_sources`, `wiki_change_approvals` and `wiki_change_contradictions`; `wiki_run_decisions` holds what people decided. `wiki_changes.path` is not a key: `wiki_pages` holds no rows, since the manifest of pages is kept beside the pages, in the wiki's store. The requests to retire a page are `wiki_page_requests` and the corrections `wiki_corrections`, each known by the console's id (`request_key`, `correction_key`).
- **Cases** (step `0031`): a case is one object with several keys and one version, as it was one ConfigMap: `cases.object_name` is the object's name (the case's number as text) and `cases.version` its version, which a save of the case, of the work on it or of its conversation moves on. `is_case_kept` is false while only the work or the conversation is kept. Every field of a case is a column: a person is four columns (`_key`, `_name`, `_email`, `_is_system`), the first empty where there is none; the finding's key, what the runs saw, how the case it is a regression of was closed, the run that verified the fix and the change that was applied are groups of columns, the first of each empty where there is none. The model's `case_links` is gone: the case a case duplicates, is a regression of, is the same as or may duplicate is a number in a column of its own, since that case may be gone. `service_key`, `known_issue_key` and `exception_key` are ids as text for the same reason, and the model's keys to `services`, `known_issues` and `exceptions` are gone. `line_title` and `involved` are worked out when the case is saved: the list of cases is read from the cases' rows, and no table holds its lines. `case_people` holds the watchers and the approvers, by `role`. The work on a case is `case_work` (one row a case that has any), with `case_analyses` (one row a case, not the model's row an analysis), `rcas` (keyed by its case; the cases it covers are an array, and the model's `rca_cases` is gone), `case_events`, `case_proposals`, `case_drafts`, `case_draft_drafters` and `case_commands`. The conversation with Sherlock is `chats` and `chat_messages` under the session `case:C-<n>`.
- **Known issues and services** (step `0031`): a known issue is known by `known_issue_key` ("KI-3"); its window is two columns, what the runs still find of it three, the services it affects an array of their ids (the model's `known_issue_services` is gone), and `known_issue_followers` and `known_issue_keys` are new. A service is known by the id the console gives it (`service_id` is text), with `service_runs_on`; its contacts and aliases are arrays. The index, the known issues and the issue service's settings are at one version, the version of the settings row `docset/issues` (`db.DocSet`).
- **A conversation's key** (step `0033`, DB-57): a kept conversation is joined to the change or the case it is of by `chats.change_id` or `chats.case_id`. Exactly one of the two is set, each is unique (a change and a case have at most one conversation), and each goes with its row (`ON DELETE CASCADE`): a change or a case that is deleted takes its conversation and the messages. `chats.session` is dropped. Sherlock still names a conversation by its session, which is worked out from the key and kept nowhere: `'proposal:' || changes.change_key`, `'case:C-' || cases.case_number`. A conversation is read and written through its key (the changes' by joining `changes`, a case's by its `case_id`), never by a name, so case 1's is never taken for case 12's. The step gave the conversations a database held their keys from their session's name, matched whole, and deleted those whose change or case was not there. A case's row is there when its conversation is written: the first save of any key of the case's object makes it (`is_case_kept` false), and the case keeps that row. A change's conversation written while the change has no row is not kept, so the changes are copied from their ConfigMap before their conversations. This is the one key from an engine's table up into the flow, decided by the owner: a name beside the record is not a join.
- **Sign-in sessions** (step `0037`, DB-66): `auth_sessions.auth_session_id` is text, not a UUID: the SHA-256 of the session's id in hexadecimal, which is what the session's Secret was named for, and a check refuses anything else as a key, so the id itself, which is the cookie's value, cannot be one. Every field of a session's record is a column: beside the model's, `email`, `display_name` and `groups` as the sign-in's source gave them, `kube_name` and `kube_groups` (the user and groups the clusters know the person as), `is_admin`, and `record_version`, the record's format: a console reads a row of a later format and never writes it. The four times are never null. A session ended or expired has its row deleted; nothing of it is kept. The step empties the table first, which held no rows: nothing wrote to it before.
- Two tables are the database's own and not part of the model: `schema_migrations`, the steps applied, and `imports`, the record sets copied from the ConfigMaps, each with the time of the newest record copied where the set only grows.
- The columns of a domain that has not moved yet are the model's first cut: they are settled, and may change in place, when the domain's repository is written. Once a release ships a step, it is never edited.

### Identity

Sessions live in the database; local accounts stay in a Secret. Schema: `0002_identity.sql`, with `0037_auth_sessions.sql` for the table as it is.

| Table | Holds | Columns |
| --- | --- | --- |
| `auth_sessions` | Signed-in browser sessions, shared by all replicas, keyed by the SHA-256 of the session id, never the id | `auth_session_id` PK (text: the hash in hexadecimal), `record_version`, `subject`, `username`, `email`, `display_name`, `groups`, `kube_name`, `kube_groups`, `is_admin`, `roles`, `super_roles`, `method`, `directory_ref`, `groups_read_at`, `created_at`, `last_seen_at`, `expires_at` |

Local users, local groups and memberships stay in a Kubernetes Secret, so a database outage never blocks them. While the session store cannot be written, a sign-in of any kind gets a session kept in its cookie and signed with a key from the Secret `<release>-session-key`, which any replica checks without the store (DB-65, ADR-165): it lasts `auth.outageSession` (30 minutes) from sign-in, carries who the person is and nothing of what they may do, is refused at once for a local account disabled or deleted, and becomes a row at its first request after the store is back. Neither the key nor a cookie's value is ever in the database. With a database and the console's connections kept in Secrets, a session is a row (DB-66): a replica answers from the row as it last read it for 5 seconds, and drops what it holds at a notice (`auth-sessions`) that a session ended or changed, so a sign-out on one replica is refused on the others within 5 seconds at the latest. With the connections kept in memory the sessions are in memory too, and without a database they are in Secrets. Sessions have no key to users: directory users from LDAP or OIDC are never stored.

## Decisions

| Question | Decision |
| --- | --- |
| Should job runs and case analyses record the prompt version that produced them? | Not now: the code does not record it, so it would be a new feature. |
| What happens to fleets and hosts when a cluster connection is removed? | Selector fleets are deleted. List fleets and hosts outside Kubernetes stay, with no cluster, and show under every cluster. The administrator chooses for each node whether to delete it or keep it as a host. |
| Do RCAs belong in Cases or Knowledge? | Cases: they are written when cases close, although like fixes they outlive them. |
| Do validation rules belong in Jobs or Cases? | Jobs: they are offered to job kinds and shown under the Jobs tab. |
| Do variables belong in Automation or Inventory? | Automation: only script runs read them, although they key to fleets and hosts. |
| Does `clusters` hold connection metadata, or does everything stay in Secrets? | A table for the metadata, the credentials in Secrets. |
| Do local users and sign-in sessions move to the database? | Local accounts stay in a Secret, so a database outage never blocks them. Sessions move; during an outage a sign-in of any kind gets a short-lived signed session (DB-65). |
| Does one rejection close an approval request for good? | Yes, as the code does today; a new request is needed to try again. |
| Will any request need more than two approvers? | No flow needs it today; the required count allows any number. |
