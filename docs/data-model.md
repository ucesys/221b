# The data model

What 221B keeps in PostgreSQL: 126 tables in 12 domains and 3 tiers, and 2 tables of the database's own. The schema itself is the SQL in [`server/internal/db/migrations`](../server/internal/db/migrations), steps `0001` to `0046`, applied in order; a later step reshapes what an earlier one made, so no one file is a domain's schema. This page is the schema as it stands after the last step: every table, every column, the keys and the rules they follow. A test, `TestTheDataModelIsTheSchema`, compares it with a migrated database and fails when the two disagree on a table, a column or a key (DB-68). [database.md](database.md) says how the database is run and how a domain's repository is written.

## How to read it

Each domain has a table with one row a table: its name, what it holds, and every column in the schema's order. A column's marks follow its name:

- **PK**: the column is the primary key, or part of it.
- **FK → `table`**: a foreign key into that table, never empty. **FK? → `table`**: one that may be empty.
- **↗**: the key points into another domain.
- **≈ `table`**: the id of a record of that table, kept as plain text or a number and not as a key. The schema has many by decision: what is named may have no row, may be gone while the row that names it stays, or is known everywhere by the id people read.

A column's words in parentheses say what its name does not: a type where it matters (`text` for a key that is not a UUID, an array, JSON), what none means, or that nothing fills it yet. An unmarked column is plain data of its row. [Every foreign key](#every-foreign-key), with what happens when the row it points at is deleted, is listed at the end.

## The rules

- **Keys point down the tiers or stay inside one.** The AIOps flow keys into the engines and the foundation, the engines into the foundation, and the flow's domains into each other. No table keys up: where a foundation table records something higher (an acknowledgement's run, case or exception, a Toolbox session's change, a standing approval's agent), it keeps the id as a plain column.
- **Every key is named for its table.** A primary key is `<entity>_id` (`fleet_id`, `script_run_id`); no table has a bare `id`. A table that hangs from one row is keyed by that row's key (`host_facts.host_id`, `case_work.case_id`), and a list by its owner's key and `position`, a name or a kind. A foreign key has the name of the key it points to; a second key into the same table adds a role (`retry_of_script_run_id`), and one column departs, `change_position`, which with `wiki_run_id` points at a page change's `position`. A join table's key is its pair of keys. Six tables are keyed by a name or an id that is their whole subject: `settings.scope`, `check_found.check_name`, `dismissed_checks.check_name`, `counted_runs.run_key`, `checked_clusters.cluster_id` and `knowledge_source_reads.knowledge_source_id`.
- **Natural keys only where the code already has a stable id.** These keys are text, the id the console gives or is given: `clusters.cluster_id`, `credentials.credential_id`, `approval_policies.approval_policy_id`, `notification_channels.notification_channel_id`, `toolbox_sessions.toolbox_session_id`, `run_profiles.run_profile_id`, `ai_providers.ai_provider_id`, `agents.agent_id`, `test_cases.test_case_id`, `jobs.job_id`, `validation_rules.validation_rule_id`, `services.service_id`, `knowledge_sources.knowledge_source_id`, and `auth_sessions.auth_session_id`, a hash. Every other key is a UUIDv7 the console makes (`db.NewID`), never a sequence. An id people read is a column of its own beside the UUID, unique where it is the record's name: `case_number`, `change_key`, `fix_key`, `exception_key`, `known_issue_key`, `run_key`, `run_number`, `request_number`, `change_number`.
- **An id is a key only where the row it names is sure to be there.** A column marked ≈ holds another record's id as text or a number: the record may have no row (the default provider, a built-in rule or test case, a job nobody changed), may go while the row that names it stays (a run kept after its job, a fix after its case), or is written again with a new row id at each save (a job's run and its findings). Where it names a record that keeps its row (a case, a change, a known issue, an exception, a service), a key sits beside the id since DB-89 and DB-90, emptied when the record goes. Such a column is read by looking the id up, and finding nothing is not an error.
- **Names say what a column holds.** A flag starts with `is_` or `has_`; a time ends in `_at`; who did something ends in `_by`; money ends in `_usd`; a list of cluster or job ids ends in `_ids`. In a group of columns the group's name comes first (`owner_is_system`, `recheck_is_ok`, `trigger_is_rebuild`, `expect_is_refusal`, `tested_is_keyless`). The schema departs in a few names: the flags `tested_ok`, `skips_overlap` and `catches_up`; the times of a certificate (`…_not_before`, `…_not_after`) and `pilot_until`; `jobs.schedule_at`, a time of day as text; `approval_policies.applied_at`, an array of times; and the lists of other ids, which are named for what they list (`verified_cases`, `contradicts`, `services`, `runs`). `check` and `window` are reserved words in SQL, so the columns are `check_name` and `window_start_at`, `window_end_at`.
- **History outlives what it points to.** A run or a record that outlives its target holds a key that is emptied when the target is deleted, beside the target's name as text (`script_runs.script_version_id` beside `script_name` and `version_number`, `script_run_hosts.host_id` beside `host_name`, `applications.repository_id` beside `repository_name`), or names the target by its id alone (≈).
- **A cluster is `cluster_id` everywhere.** Only Platform and Inventory hold a real key to `clusters`: Platform's takes an application and an acknowledged alert with the cluster's row, Inventory's is emptied, so that list fleets and hosts outside Kubernetes outlive it. Every other domain keeps the id as a plain column, so history survives a removed connection. A removed connection keeps its row, with only its id.
- **Sign-in never depends on the database.** Local accounts stay in a Kubernetes Secret, and while the session store is away whoever signs in gets a short-lived session kept in its cookie, signed (DB-65). That holds for a console that is running. A console that starts while the database is away does not start (DB-02), and nothing lets it: the option that did (DB-67) was withdrawn by the owner on November 20, 2026.
- **Kubernetes state is never stored.** A node's row holds its identity only, its cluster and its name; labels, taints, status and topology are read live.
- **Observed host state is a fact, not a column.** What the facts run reports, network details included, is JSON in `host_facts`; the tables hold only what people set.
- **A record is one row for its whole life.** Approval changes its state: a request for a run and the run are one row, and there are no tables of drafts of records. `case_drafts` is not one: it holds text being written on a case, not a case. Where a service still saves its records as one document, a record that changed may be written again with a new row id; each domain says which.
- **Versioned things keep their history in a versions table:** scripts (`script_versions`) and agents' instructions (`prompt_versions`).
- **JSON only for what is read whole.** Six columns are JSON: `settings.value`, `approval_requests.summary`, `host_facts.facts`, `change_actions.args`, `changes.condition_args` and `chat_messages.parts`. Everything else that was a list inside a record is a table, or an array where it is a list of plain values. Anything joined, filtered or pointed to has a table.
- **Ledgers are only added to.** `audit_events` and `ai_spend` are inserted and read, never updated (a trigger refuses it), so writers at once never collide. Retention deletes.
- **True singletons are JSON rows of `settings`,** read whole and written rarely, each over its version; so are the counters and flags that are of no row.
- **Secrets stay in Kubernetes.** The secret part of a credential, an application's values file and parameters, a connection's credential and the value of a sensitive Automation variable (DB-71) stay in Kubernetes Secrets, and the tables hold the rest. No column holds a secret, the value of a secret script parameter is in no row, and a sensitive variable's value is in a row only as its keyed digest. A Secret's name follows from the row's id; `notification_channels.secret_ref` is the one column that names a Secret's key.
- **Bodies stay where they are.** Wiki pages remain in Git or S3 and Toolbox transcripts on their volume.

## Foundation tier

What every other domain stands on. A foundation table keys only into the foundation.

`clusters.cluster_id` and `credentials.credential_id` are the ids the console gives; a repository and an application have UUIDs. `(cluster_id, namespace, name)` is unique in `applications`, and `lower(name)` is unique among the kept rows of `credentials`. No name is unique in `clusters`: the console refuses a second connection of one name, and a copy from Secrets that held two must not fail.

**Rows with only an id.** Whatever points at a cluster or a credential makes that row first if it is not there, with `is_kept` false; the connections and the credentials' list are the kept rows. A removed connection's row is not deleted: its columns are emptied, `is_kept` is set false and `version` is raised, so the applications, acknowledged alerts, fleets and hosts that name the cluster stay as they are. A credential's row that something points at is updated in place and never deleted while it is pointed at.

**What stays in Secrets.** A connection's credential is the Secret `<prefix>-cluster-<cluster_id>`, whole, with what is read only together with it (the CA certificate, a kubeconfig's context, the OIDC issuer, client id and scopes). A credential's secret is the key `secret-<credential_id>` of the credentials' Secret. An application's values file, its parameters and its commands' parameters are the key `set.json` of the application's Secret, since people type passwords into them; a command's parameters are paired with its row by name, so `application_commands` is keyed by the command's place and two commands of one name each keep their own. No column holds any of these, or the name of the Secret, which follows from the id.

An application reads its repository's name through `repository_id` while the repository is listed, so a repository keeps its row through a new name, and from `repository_name` once it is gone. `applications.fleet_key` is the fleet's id within the cluster and not a key, as a run names a fleet. An acknowledgement keeps the run, case or exception that made it as plain ids, since a foundation table never keys up.

The scopes of `settings` are the pages' own documents (`general`, `sherlock`, `watson`, `email`, `setup`, `cases`, `backup`, `knowledge`, `issues`), the counters the ids people read come from and the flags that are of no row (`approvals`, `notifications`, `automation-changes`, `automation-runs`, `ai`, `ai-tests`, `ai-pilot`, `jobs`, `job-runs`, `case-found`, `case-index`, `known-issues`, `changes`, `fixes`, `exceptions`, `knowledge-status`), the notes of the upgrade to 0.12.1 (`repositories-migration`, `credentials-migration`), and the version of a set of documents saved together (`docset/issues`).

### Identity

Who is signed in. Local accounts are not here: they stay in a Kubernetes Secret, and people of a directory or an OIDC provider are never stored. Schema: `0002_identity.sql` and `0037_auth_sessions.sql`.

| Table | Holds | Columns |
| --- | --- | --- |
| `auth_sessions` | The signed-in browser sessions, shared by every replica: who the person is, what they may do, and the session's four times. A session that ends or expires has its row deleted (but for the short-lived `ended` record of a session made during an outage). | `auth_session_id` PK (text: the SHA-256 of the session's id in hexadecimal, never the id, which is the cookie's value), `subject`, `username`, `method` (how the person signed in; `ended` for the record below), `directory_ref` (the directory entry of a person of a directory), `roles` (text array), `super_roles` (text array), `groups_read_at` (when the person's groups were last read), `created_at`, `last_seen_at`, `expires_at`, `record_version` (the record's format: a console reads a row of a later format and never writes it), `email`, `display_name`, `groups` (text array: as the sign-in's source gave them), `kube_name` (the user the clusters know the person as), `kube_groups` (text array: the groups the clusters know the person by), `is_admin` (a SuperAdmin) |

The key is what the session's Secret was named for, and a check refuses anything but 64 hexadecimal digits, so the cookie's value cannot be a key. The four times are never empty. Sessions have no key to users, since none are stored. Neither the key that signs a session made while the session store is away, nor such a session, is ever in the database (DB-65). When the store is back such a session becomes a row at its next request, under a key worked out from the session, and that row expires when the signed session would have. A signed session that was signed out or ended, or the row it had become, leaves a row whose `method` is `ended`, with no groups and no roles, until that time, so that no replica takes or exchanges its cookie again.

A replica answers from a row as it last read it for 5 seconds and drops what it holds at a notice (`auth-sessions`) that a session ended or changed. With the console's connections kept in memory the sessions are in memory too. (A release before 0.13, which had no database, kept them in Secrets.)

A request is known to people by `request_number`; the next number is the settings scope `approvals`, and the notifications' link the scope `notifications`. A standing approval and a channel keep the ids the console gives them (`s…`, `n…`), which the audit log and the channels' Secret carry. A standing approval names its agent and its clusters by their ids, as plain columns, since a foundation table never keys up.

A request keeps its row when it is decided: the row is updated and its decision written (DB-91). Of the records that ask for an approval, only an agent's draft instructions are approved by a request of this domain, and the draft's row keeps its key (`prompt_versions.approval_request_id`). Script versions, run requests, variable changes, proposed changes, wiki page changes and Toolbox sessions keep their approval in rows of their own (a version's review, a run's approvers, a change's decision, `change_decisions`, a page change's state, a session's card and approver) and have no key here; step `0046` dropped the keys nothing filled, with `approval_requests.expires_at` (a request does not expire) and `approval_decisions.approval_policy_id` (a standing approval decides changes, not these requests).

A script and a group are known by their names, which are unique; a version by `(script_id, version_number)`, unique too. A profile keeps the console's id. A variable change is known by `change_number` and a run by `run_number`, both unique; a request by `request_number`, unique, numbered apart from the runs. `(script_run_id, host_name)` and `(script_run_id, fleet_key)` are unique, and so are `(fleet_id, name)` and `(host_id, name)` in `variables`, where a check holds a variable to exactly one of the two.

A node's own values are the node's, whatever fleets it is in; a fleet's are the fleet's, All nodes' those of the cluster's fleet of kind `all`. A run takes its own value first, then the host's, then its fleets', and the view `script_run_host_values` gives each host's actual values in that order. The value of a secret parameter is in memory for its run and in no row.

**A sensitive value is in a Secret, never in a row** (DB-71). A name a fleet marks sensitive is sensitive on its whole cluster: every fleet's and every node's value of it, and a run's own value for it. Each such value is kept in the cluster's Secret `<prefix>-automation-<hash of the cluster id>`, under a keyed digest of the name and the value (HMAC-SHA-256 with a key kept in the same Secret, cut to 96 bits); `variables.value_digest`, `variable_change_items.old_digest` and `new_digest`, and `script_run_values.value_digest` hold that digest where the value was, and checks hold a row to one of the two. A row is written, then the Secret, then the transaction commits, so a Secret that cannot be written leaves the rows as they were. What a waiting change would set, and a waiting run request's own values, wait in the Secret until they are decided; a decided change's and a run's digests stand for nothing kept, and only say that the value was set or changed. The start after step 0038 moves the values that were in the tables (variables, past change items and run values, a quoted value in a run's output and in Automation's audit events) into the Secrets.

**A run outlives what it names.** It is kept after its script's version, its profile, its fleet, its nodes and the run it retries are gone, so it has each as it named it (`script_name` and `version_number`, `run_profile_id`, `fleet_key` and `fleet_name`, `host_name`, `retry_of_number`) beside the key, which is emptied when the row it points at is deleted. A variable change outlives its fleet the same way, and names it by `cluster_id` and `fleet_key` with no key; its items say which nodes' own values it alters, by the node's name.

**A request and its run are one row** of `script_runs`: a request has `request_number` and `request_state`, and no `run_number` until it is approved and the run is written into the same row; one rejected or expired never has one. The runs and the requests are still written by two documents into this one table, each its own columns and its own scope of `script_run_values`.

A script's versions, a variable change and a run keep their rows through a save (they are matched by name and number), and the lists that hang from them are written again. Who decided a version, a change and a run is kept in the row's own columns.

A row that changed is updated in place, its notes and parts written again when they changed, and its test run, also kept, updated in place, a result or a replay added at the end as one insert; a run started again is a new row of `test_runs`. A draft that goes live is a new version's row, and the draft's row goes. A draft that waits for another SuperAdmin keeps its request's key, looked up by `request_number` whenever the row is written (DB-91). A result names its case by `case_key` and not by a key, since a built-in case has no row and a result outlives its case; a pilot entry names its agent and the version that answered, since it outlives the draft.

`ai_spend` is a ledger: a trigger refuses an update. No history is kept: rows from before the month before this one are removed when a cost is added, and putting a backup back replaces this month's rows with rows of its sums. Costs are `numeric(14,6)`, a millionth of a dollar, but for the ledger's `usd`, which is a float as the service adds it. The counters of test runs and pilot answers and the agents' two flags are the settings scopes `ai-tests`, `ai-pilot` and `ai`.

**People.** A person is four columns (`_key`, `_name`, `_email`, `_is_system`, the last true for the console itself), the first empty where there is none: who opened, reported, filed, owns and closed a case, who wrote and sent a message, a watcher, an approver.

The work on a case does not repeat its number: it is the case's row's. An RCA is a row keyed by its case, and the other cases it covers are rows of `rca_cases`, keyed as a case's links are, with the ids people read beside.

A service keeps the console's id and its row through a change; a case's service names it by that id, and a known issue's services are rows of `known_issue_services` keyed to it, emptied when it goes, with its id beside. The case index's counter, the known issues' counter and the issue service's settings are settings scopes (`case-index`, `known-issues`, `issues`), saved at one version with the known issues, the version of the settings row `docset/issues`. A case's conversation with Sherlock is a row of `chats`, under Conversations.

### Conversations

The conversations Sherlock keeps for another record while that record wants it: a waiting change's and a case's. Other conversations with Sherlock are not kept in the database. Schema: `0028_changes.sql` and `0033_chat_keys.sql`.

Exactly one of `chats.change_id` and `chats.case_id` is set (a check), and each is unique: a change and a case have at most one conversation. Sherlock names a conversation by a session, which is worked out from the key and kept nowhere: `'proposal:' || changes.change_key`, `'case:C-' || cases.case_number`. A conversation is read and written through its key, never by a name.

A message's parts are one JSON value by decision: a chat is read and written whole, never asked for by its parts, and the parts change shape as Sherlock gains features. The column is `json` and not `jsonb` so that it reads back as written: a thing shown carries the input the model gave, key for key. Checked again on November 20, 2026 (item 13 of the Phase 13 handover): no query reads into `parts` (it is selected whole in `sherlock/pgchat.go` and nowhere else), so it stays `json`; a query that asks for a chat by its parts would be the reason for `jsonb`, in a step of its own.

A page change is keyed by its run and its place in it, and what hangs from it by `(wiki_run_id, change_position)`. A page is a path and not a key: the manifest of pages is kept beside the pages, in the wiki's store. Where the wiki is kept is the settings scope `knowledge`, whether a sync runs the scope `knowledge-status`, and the counters the fixes' and exceptions' ids come from the scopes `fixes` and `exceptions`.

## Decisions

| Question | Decision |
| --- | --- |
| Is a record that another one names joined by a key, or named by its id? | By a key where the row is sure to be there and keeps its id; by its id as text (≈) where it may have no row, may go first, or is written again with a new row id. Ids the console already gives are the text keys of their tables. |
| Where do the conversations Sherlock keeps belong? | In the AIOps flow tier, as a domain of their own beside Changes and Cases, which they key to (decided on November 20, 2026). A conversation is joined to its change or its case by a key, never by its session's name. |
| What of a record that was kept in a Secret moves to the database? | Everything but the secret: the secret part of a credential, an application's values file and parameters, and a connection's credential stay in their Secrets, and the tables hold the rest (decided on November 20, 2026). |
| Is a sensitive Automation variable's value a row? | No: it is in a Secret of its cluster, and the rows keep a keyed digest of it (decided by the owner on November 20, 2026, DB-71). |
| What may be JSON? | What is read whole and has no fixed shape: a settings document, a request's summary, a host's facts, the arguments of a change's action and of its condition, and a message's parts, which are `json` and not `jsonb` so that they read back as written. |
| Is a request for a run a record of its own? | No: it is a row of `script_runs`, the same row the run is written into once approved, so that one list has every run, the rejected ones too. Requests and runs are numbered apart. |
| Should job runs and case analyses record the prompt version that produced them? | Not now: the code does not record it, so it would be a new feature. |
| What happens to fleets and hosts when a cluster connection is removed? | Selector fleets are deleted. List fleets and hosts outside Kubernetes stay, with no cluster, and show under every cluster. The administrator chooses for each node whether to delete it or keep it as a host. The keys allow it (`fleets.cluster_id` and `hosts.cluster_id` are emptied with the cluster's row); the console does not do it yet, and keeps a removed connection's row with only its id. |
| Do RCAs belong in Cases or Knowledge? | Cases: an RCA is written when its case closes and is a row keyed by its case, although like a fix it is read long after. |
| Do validation rules belong in Jobs or Cases? | Jobs: they are offered to job kinds and shown under the Jobs tab, although the case work counts what the runs found under them. |
| Do variables belong in Automation or Inventory? | Automation: only script runs read them, although they key to fleets and hosts. |
| Do known issues and services belong in Cases or Knowledge? | Known issues in Knowledge, with the fixes and the exceptions: they outlive the cases they came from. Services in Cases: the catalogue says what a case is about. |
| Does `clusters` hold connection metadata, or does everything stay in Secrets? | A table for the metadata, the credential in a Secret, whole. |
| Do local users and sign-in sessions move to the database? | Local accounts stay in a Secret, so a database outage never blocks them. Sessions move; during an outage a sign-in of any kind gets a short-lived signed session (DB-65). |
| Does one rejection close an approval request for good? | Yes, as the code does today; a new request is needed to try again. |
| Will any request need more than two approvers? | No flow needs it today; `required_count` allows any number. |
| Are the tables nothing writes yet kept? | `data_centers`, with `hosts.data_center_id` and `rack_name`, stays for the page that will fill it. A table nothing will use is dropped. |
