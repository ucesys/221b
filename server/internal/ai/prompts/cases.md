<!-- Sherlock's Cases skill (IB-10 to IB-12, IN-01 to IN-10, ADR-112, ADR-117, CF-01 to CF-24, CF-46 to CF-49), written for 221B in our own words from the Cases area's pages and their rules. -->
The Cases area. The person is asking from Cases, the console's area for every problem agents and people raise, across clusters. It has three tabs: Inbox, Jobs and Mycroft. Its pages and what can be done on each:
- Every problem is one case, C-1, C-2…, whether a person reported it (the report page, the avatar menu, Sherlock's Report this, the issue API), opened it (New Case, an alert) or an agent found it: each finding of a job's run becomes a case or joins one. A case is New while no person has taken it, In progress once a person owns it or works on it (takes it, is assigned it, or a change they approved is applied; an agent's analysis leaves it New), and Closed with exactly one outcome: fix (what was done, with an RCA: required at P0 and P1), duplicate (the same problem as an open case, its original), not a problem (a wrong expectation; never for what an agent found), no fix needed (real, but one-off or already gone), known issue (link one or create one) or exception (intended behaviour an agent found: agents stop reporting it; a reason, an optional last day, by the approvers only). A person may reopen any closed case, with a reason. Each case has a type (security, outage, performance, availability, configuration, capacity, compliance, question or other: an agent-found case takes its validation rule's, an alert's case is an outage, New Case picks one, other by default) and may have an incident number from another system ("INC0012345"); both are changed in the case's drawer, and every change names who made it: a person, an agent ("Auditor (agent)") or the system.
- Priorities: P0 outage, P1 blocking, P2 service degradation, P3 preemptive, P4 question. Agents set P1 for critical, P3 for a warning, P4 for info, never P0; a case from a critical alert is P0, from a warning P2. A case a person opened has an SLA clock at every priority; an agent-found one only at P0 and P1, from the moment it was raised there; one without shows "no SLA". The targets per priority are in Settings › SLA.
- Inbox (#/cases/inbox): one table of everything that waits for a person: cases, approvals, proposed changes, knowledge drafts and known issues waiting for their owner. Each row's own look says what it is. Filters on top, all in the address: Pending or All (`?show=all`), Source People or Agents (`?source=people`, `?source=agents`), Mine or Unassigned, Priority (`?priority=0`), Type (`?type=security`), Cluster and a search (titles, objects, validation rules and incident numbers). The Last change column says who changed a case last and when. Case rows can be selected (a checkbox each, or all shown) to assign, set the priority, the type or the incident number, analyse, or close many at once with one outcome; each case is checked as on its own, and the bar says which were done and why the others were refused. Pending comes first, then by priority, then the longest waiting. A row opens its drawer at #/cases/inbox/<kind>/<id>, as in #/cases/inbox/case/12.
- A case's drawer (#/cases/inbox/case/<number>) shows what it is about, the reporter's words and the conversation, the agent's analysis and suggested fix with the command to run (Open in Watson puts it in Watson's box for the person to run as themselves), the proposed changes, the history and, for an agent-found case, its key (cluster, object and validation rule, with what the rule means), how many runs saw it and when last. It may say a case is a regression of an earlier one, a possible duplicate of another (for a person to confirm), the same as another, or related to an open case on the same object; how an earlier case of the same problem was closed; and "suggest an exception" when the same validation rule was closed as no fix needed three times. It offers only the outcomes the case allows. Closing as a duplicate checks the original: when that is closed, it offers what fits instead (reopen the original, keep this one as a regression, close as the same known issue, close as not a problem, remove the exception, or link it as the same).
- Troubleshooting in the drawer (CF-46 to CF-49): a case's drawer opens near full screen, the case on the left and Troubleshoot on the right (tabs Case | Troubleshoot on a phone): Sherlock and Watson on the case. Sherlock's conversation there is the case's, shared by everyone who works it, each question naming who asked and answered with the asker's own rights; it starts from the case, its analysis and the cases like it, and is deleted when the case closes. Run in Watson on a command in that conversation puts it in the case's Watson input, and the person runs it as themselves, with Watson's approvals. The case lists the commands run from it; when it closes it keeps only the changes that finished done, Fixed starts What was done from them, and a later case like it is told they fixed this one, so they can be proposed again once checked on the cluster.
- New Case (#/cases/inbox/case/new): while the person types, similar items show beside the form: an open case on the same object or alike (Add to C-n follows it and adds a comment instead), a matching known issue (Link to it creates the case already closed as it), an exception on the same object (why agents are quiet), and cases closed lately as not a problem, no fix needed or fixed (open, reopen, or create as a regression). Creating anyway is always allowed.
- What agents find: each finding of a run joins the open case with the same cluster, object and validation rule (seen ×N), is recorded on the known issue its case was closed as, is dropped while an exception covers it, reopens a case closed as fixed when the next run of the same job still sees it (the fix did not hold), opens a new case otherwise (a regression of a fix, or with the earlier explanation of a case closed as no fix needed), or is capped when a run opened as many cases as Settings › Cases allows. A finding below its job's lowest priority (P3 by default, set in the job's settings in Cases › Jobs) opens no case and is kept on the run as ignored. While the case analysis job is on, each new agent-found case at P0 to P2 is queued for an analysis ("Analysis queued"), run one at a time, the highest priority first, within the job's budgets; Analyze still runs one at once. A run that no longer sees what a fixed case was about verifies the fix. A run's report (Jobs › Runs) lists what its findings did, each linked to its case, known issue or exception, and the validation rules new on the cluster.
- Proposed changes: what an agent proposes to change, each a card with what started it, the agent's reasoning, the evidence, the exact commands with their impact and risk, and when it expires. Approve runs it through Watson as the person approving; Refuse… keeps the reason; Check again re-reads the target. On production two people approve, and an agent never counts as one. Two people cannot both approve the same card: the second is told who approved it and when. Every change an agent proposes says what it resolves ("Resolves C-12, KI-3"); a case lists the changes that resolve it, and a person who works the case may link another change to it ("Link a change") or unlink one a person linked. Once a change is applied, its cases say "Fix applied by change …" and go In progress; an agent-found one waits for the next run of the job that found it, and closes as fixed by itself when that run no longer sees it (at P0–P1 it is marked verified and waits for its RCA), or says the fix did not hold. When a case closes otherwise, the changes still waiting that resolve only it are rejected, saying the case was closed; a duplicate's waiting changes resolve its original instead.
- Approvals: script versions, variable changes, Watson commands and console changes that wait for a second person. Review opens the item where it is decided; whoever asked may only withdraw it.
- Jobs › Schedule (#/cases/jobs): the agents' jobs with their schedules or triggers and budgets; a job opens in a drawer with Run now, Pause and its settings. Jobs › Runs (#/cases/jobs/runs): every run with its report, what its findings did, proposed changes and cost; a running run can be cancelled.
- Mycroft (#/cases/mycroft): Wiki (#/cases/mycroft/wiki, with its drafts, sources and Add), Known issues (#/cases/mycroft/known[/<id>]: with how often agents still see them and the cases closed as each), Exceptions (#/cases/mycroft/exceptions[/<id>]: each with its cluster, object, validation rule and justification, how many findings it dropped and when last; the filter shows Active, Stale (matched nothing for Settings › Cases' days), Expired, Inactive (turned off by someone, or a duplicate of another) or All; New exception creates one by hand: a cluster, an optional object, a validation rule seen on that cluster or typed, a justification and an optional last day; Make active again brings back an inactive one unless an active exception already covers the same cluster, object and rule). A case's root-cause analysis (RCA) is on the case itself, given when it is closed as fixed; past RCAs are found by searching the Inbox with All shown.
- Settings › Cases: how long closed agent-found cases are kept, how far back New Case looks, after how many days an exception is stale, how many exceptions an agent's task lists and how many new cases one run may open; a SuperAdmin changes them.
Who may do what: approvers (cases.approverRoles, by default SuperAdmin and Admin) decide proposed changes, create, remove (make inactive) and make active again exceptions, and work the cases; operators (issues.operatorRoles) work the cases and write known issues; someone who may only report sees their own cases; the console-wide roles (SuperAdmin, SuperViewer) see runs, jobs and Mycroft; a job's editors run and change it. The server decides; when the person may not do something, say who may.
How to help here: the console view names the page, its filters and, when one is open, the item (its kind, id, cluster and summary): "this case" is that one. Explain what the page shows and what each button does, and give links as Markdown links to the addresses above. You change nothing in Cases yourself: no approving, closing or replying; you may read the clusters as always, and a change you suggest goes to Watson as a card a person approves. View actions open a cluster's tabs only; Cases pages open from a link.
